02 / Problem and examples

Separate checks can miss an interaction.

A coding agent changes a repository and runs validation tests. Each test can pass while a combination still exposes a defect.

The plugin starts before patch submission. It can read the original visible trajectory, including deleted tests and earlier failures.

The plugin must construct a meaningful combination and a valid expected result. A failed generated test alone does not prove a patch defect.

N01: an error can bypass cleanup

HTTPX tests exercise response consumption and malformed data. The generated combination observes the same response after a parsing error.

r = response_with_malformed_stream()
with raises(ParseError):
    consume(r)
assert r.is_closed

This code is a schematic explanation of the real witness. It is not the exact emitted test.

The normal path closes the response. The error path can bypass that operation. The final state check exposes the missing cleanup.

Analysis need: connect the input, error path, response identity, and later observation.

P3: values can hide an interaction

A Textual test already combines an alternate key with modifiers. Its modifier value does not activate shift normalization.

alternate = "plus"
modifier = 5  # ctrl
modifier = 6  # ctrl + shift

The decoder subtracts one from the encoded modifier value to obtain the bit set. A test with value 5 cannot distinguish the relevant shift behavior.

Analysis need: select a value that changes the condition and reaches the observed alias.

A list of feature names cannot express this value requirement.

Three observations that survived the method revisions
  1. The same operations can form different relations. Order, shared objects, and input values change the relation.
  2. A relation must refer to specific objects and a specific observation phase.
  3. A test can execute a combination without making its effect visible to the assertion.

These observations describe the problem. They do not, by themselves, specify a construction algorithm.

03 / Retained algorithm

Source construction, execution, and oracle review

This workflow describes the retained family. The 16/17 result belongs to the frozen version at commit 7a8ff95.

1Replay the submitted state

Restore the repository and candidate patch. Use the original visible trajectory as an input.

2Recover tests and observations

Parse assertions, input definitions, calls, and state operations. Preserve the code that gives each assertion its context.

3Construct candidate tests

Apply source-based edits to inputs, operations, and object bindings. Allocate the budget across tests and construction types.

4Run and request review

Run candidates with source controls. Send selected complete candidates to the model when the expected result needs review.

5Materialize revised assertions

Insert supported expected expressions into the test source. Run the revised tests. Keep interface and execution failures in the records.

6Use feedback and evaluate

Use earlier outcomes to guide the next search round. Independently review the complete witness before counting a defect.

The fixed main experiment used two search rounds.

Each trial had at most 128 program candidates and 16 semantic candidates per round. Each model request reviewed one complete candidate.

The second round continued search with prior outcomes. It was not a separate hidden-test evaluation.

The complete run used 540 model requests. A limit of 16 candidates per round does not imply 16 requests for the whole experiment.

Latest construction prototype: observation-address unification

The new prototype extracts an address that an assertion reads. It searches source operations for a possible write to that address.

Read demand:   obj.items["b"]
Source action: other.put("a", value)
Substitution:  other := obj, key := "b"
Construct:     obj.put("b", value)

These constraints determine the object and key edits before test construction. Version 2 also uses an index before it allocates pair attempts.

Both versions produced zero candidates on the 17 real source corpora. Their supported fragments and source transport rules blocked construction.

The authored examples show that address changes can affect an observation. They also show that the old expected result can become wrong.

This prototype is separate from the retained 16/17 method. It does not establish a new academic contribution.

Relational residual slicing

Before and on 2026-09-23

Core abstraction. A Boolean residual D_r(x) = [L(x) != R(x)] for an existing valid relation.

Algorithm

  1. Build two bounded executions with shared symbolic inputs and separate mutable states.
  2. Cancel terms that preserve equality.
  3. Trace the remaining free variables to test input slots.
  4. Replace one or two slots with values from source tests.
  5. Find a small input that violates the same relation.

Implementation. The residual solver and relation-based generator were not implemented. A separate test-anchor retrieval stage was implemented.

Evidence

  • All seven target tests and assertions were present in the extracted inventory.
  • The full retrieval rank had Test Hit@10 = 0/7 and Assertion Hit@10 = 0/7.
  • The patch and keyword baseline had Test Hit@10 = 7/7 and Assertion Hit@10 = 2/7.
  • Removing input-gap priority gave 4/7 and 1/7. Removing observation-group rotation gave 2/7 and 1/7.
  • The full method had Test MRR = 0.0336. The baseline had Test MRR = 0.3833.
  • The seven analyses took 98.88 seconds of internal analysis time.

Limits

  • Retrieval results do not test residual cancellation.
  • P2 did not require two-run residual reasoning. Ordinary assertion slicing was enough.
  • P6 and P7 lacked a suitable fixed oracle for the desired interaction.
  • Input diversity did not imply oracle validity. Global group rotation delayed useful assertions.
  • The seven cases were used during development.

Why the method changed. The residual hypothesis did not explain all pilots. The retrieval result favored patch-first test order and a new rule inside each test.

Observation frontier

2026-09-23

Core abstraction. A partial order of assertion dependency footprints within a test.

Algorithm

  1. Extract each assertion and the source needed to compute it.
  2. Order assertions by dependency-footprint inclusion.
  3. For equal footprints, prefer a value observation to an error or null check.
  4. Visit maximal elements first. Use static expected-value diversity to break a tie.
  5. Keep the patch-based test order. Rotate the assertion budget across tests.

Implementation. Implemented in anchor_retrieval/frontier.py. This stage retrieves test and assertion entry points.

Evidence

  • Final Test Hit@10 = 7/7. Final Assertion Hit@10 = 7/7.
  • Both MRR values were 0.3833. Test MRR did not improve over the patch baseline.
  • Without the frontier relation, Assertion Hit@10 was 2/7.
  • Without expected-value diversity, Assertion Hit@10 was 6/7.
  • Without test rotation, Assertion Hit@10 was 3/7.
  • Repository-only analysis also gave 7/7 for both metrics.
  • All 23,853 assertion ranks matched in the final source rerun.
  • The first full-hit run used 87.26 seconds of internal analysis time.

Limits

  • A larger dependency footprint does not prove a stronger assertion.
  • Source order breaks unresolved ties.
  • There was no combination generation or subject execution in this retrieval study.
  • The seven cases cover four issue families and were used for development.

Why the method changed. The entry-point problem improved. Generation and oracle transport remained open.

Observation-preserving context lifting

2026-09-23

Core abstraction. A source observation a, a context C, a comparison construction B_C, and an applicability condition g_C.

Algorithm

  1. Retrieve a source observation with the frontier method.
  2. Construct C[t] and B_C[t] with fixed source transformations.
  3. Check g_C and run source or neutral controls.
  4. Compare the specified observations.
  5. Freeze tests before candidate and reference evaluation.

Implementation. Implemented as the combination-v0.1-pilot prototype. It used path, protocol, closure, clone, and recursion adapters.

Evidence

  • The final unified contract_v6 run detected 7/7 known targets.
  • It ran 263 combination checks and 168 controls.
  • 49 candidate alerts had controlled reference differences. Review found no wrong oracle in those alerts.
  • Three reference alerts had issue support and were retained.
  • The final three successful model requests reported 25,992 tokens. The new sample used 27,200 tokens.
  • Development stored 36 request records and 32 responses. Reported use was 616,176 tokens. Four requests had unknown use.

Limits

  • The adapters were added after the pilot faults were known. This was method-level overfitting.
  • Only seven pilots from four issue families were studied.
  • Two comparison paths can share a fault. Bounded recursion can miss deep cases.
  • A model condition can be too broad or too narrow.
  • No repair-loop or issue-resolution improvement was measured.

Why the method changed. The user rejected pilot-specific transformations. Later work had to learn edits from source tests instead.

Source test analogy square

2026-09-23 to 2026-09-24. See each run record

Core abstraction. Three source test units A, B, and C define a fourth unit D through A:B::C:D.

Algorithm

  1. Anti-unify A and C to obtain a common syntax P and substitutions.
  2. Find a source syntax Q that reconstructs B with the same A substitution.
  3. Apply the C substitution to Q to construct D.
  4. Keep lexical binding constraints and full parent context.
  5. Ask a model to check the complete fixed proposal.

Implementation. Implemented. Units include whole tests, helper calls, and assertion windows. The edit-square kernel is a separate alternative.

Evidence

  • All generic variants had zero contract-supported defects.
  • The three cross-project tasks produced no candidate in v2.1, v3, and v4.
  • The final combined cost ledger reported 229 formal experiment and diagnostic attempts and 6,531,082 tokens.
  • 23 historical requests had unknown use. Three unintended synthetic-fixture connection attempts were separate.

Limits

  • Three valid examples do not determine a valid fourth expected result.
  • Exact AST or byte reconstruction is not proof of semantic transport.
  • Scope-safe source edits can still break later assertions.
  • Low alert counts can result from no output, gate rejection, control failure, or compile failure.
  • The repeatedly used cross-project tasks were not a fresh blind test set.
  • No issue-resolution experiment was done.

Why the method changed. The family did not construct valid fault-revealing pilot combinations. Later work separated actions, observations, and expected-result changes.

Actions, observations, and small expected-result transforms

2026-09-24

Core abstraction. A test is T=(S,q,e). A source context changes S. A source observation can become q-prime. A pure expression tau changes e.

Algorithm

  1. Extract source actions, bindings, an observation, and its expected result.
  2. Compose a closed source context with the actions.
  3. Bind a source observation to compatible object ports.
  4. Ask the model only for tau(pre,arg).
  5. Evaluate tau on static source values. Build and check the complete test.

Implementation. Implemented in the semantic_transport prototype. Observation transport and expected-value vector adapters were added within this family.

Evidence

  • Seven batches completed. Every evaluated round had 0/7 confirmed pilot target hits.
  • The last batch had two unresolved alerts, not two confirmed defects.
  • Seven batches reported 1,615,647 tokens. Three separate diagnostics reported 692 tokens. Twelve first-batch failures had unknown use.
  • A synthetic sequence test showed why a count observation cannot detect wrong order. A transferred snapshot observation could detect it.

Limits

  • A legal pure expression can still give a wrong expected result.
  • Changing only the expectation cannot recover information lost by q.
  • Observation binding was limited to one file and enclosing scope, up to three source ports and 24 bindings per template.
  • Generated Go call types still caused compile failures.
  • Passing source-example checks would not prove a general relation. Some runs had no applicable check.
  • The synthetic success was not a pilot success.

Why the method changed. Small oracle transforms did not solve missing candidate structure or weak observations. More trajectories were collected to study relations tied to object and phase.

Observed relation cells and bounded relation closure

2026-09-26 proposal. Limited implementation on 2026-09-28

Core abstraction. A cell (q,rho) couples an executable observation with a relation on inputs, objects, or events.

10 / Next decisions

Test one construction hypothesis before adding more machinery.

The next method must use analysis to decide which edit to construct. The experiment must measure useful witnesses per fixed budget.

The current research question

Can constraints on objects, arguments, and operation order guide search backward from an observation?

With the same source components and semantic budget, can this search find more valid witnesses or find the same witnesses at lower cost?

Status: unvalidated hypothesis. The current implementation supports only a restricted form of address unification.
