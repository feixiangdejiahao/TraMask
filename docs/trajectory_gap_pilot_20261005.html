Trajectory 与 combination gap：两部分 pilot 实验

2026-10-05 · 已完成提取、生成、原生执行及逐项审查 · 本轮优先观察效果，不设 plugin 形式或低开销目标。

当前结果支持继续研究“验证信息如何丢失”。结果尚不支持“直接加入原始 trajectory 就能稳定提高检出”。

自动规则找回 11/13 个手选测试和 21/28 个手选历史步骤。按机制审查，1 例恢复完整，3 例恢复部分，4 例未恢复。完整恢复只指历史材料齐全，不代表已经证明缺陷。

格式修复后的成对生成实验得到 24 个可执行候选。7 个候选重复失败。完整审查确认 1 个有效目标反例、4 个无效测试和 2 个依据不足的测试。有效反例来自仅提供源码的 P7 组。加入 trajectory 的组得到 0 个有效目标反例。

实验回答两个独立问题。第一部分检查非大模型方法能否定位测试和历史证据。第二部分检查人工选好材料后，大模型能否生成有效反例。第二部分没有使用第一部分的自动输出。因此，本报告不声称端到端自动性能。

本次使用既有开发任务。我们按缺口类型选择 8 个案例：N01、N03、N04、N06、N08、N09、P2、P7。选择不随机。手工目标中也含尚需确认契约的缺口假设。因此，1/8 表示这批目标假设上的有效产出，不能称为总体召回率。

全文采用短句、主动语态和直接用词。中文不具备 ASD-STE100 英语受控词表的正式符合性。

第一部分的结果说明：当前 AST 和词法规则可以恢复材料，但不能稳定恢复组合条件。下一步需要改善对象、字段、资源和版本之间的连接。仅扩充关键词或输出更多片段，不足以解决该问题。

依据：提取记录；逐例人工评价；独立 N 组复核。

第二部分：固定源码，成对加入原始 trajectory。源码组接收公开 issue、手选完整测试和原始支持源码。历史组接收完全相同的材料，并增加人工选定的完整原始步骤。每对输入只差 trajectory。手工选择理由、预期目标、后续研究生成的测试及后续研究执行结果均未进入提示词。

历史组可以看到开发 agent 当时的运行输出。这些输出属于原始 trajectory。它们不等于正确答案，也不等于最终版本上的验证。

每个案例每组发送一次生成请求。每次最多生成两个完整测试。模型使用 .env provider 的 deepseek-v4-flash。参数为 temperature=0、thinking enabled、reasoning_effort=low、输出上限 16,384 token。两组设置相同。我们没有根据失败结果要求模型重写断言。

生成器可以替换整个测试体。它保留原注册、名称和签名。导入必须来自原上下文或已核对的原始源码绑定。P7 允许 transform。它不能增加其他生产代码修改。发射器检查测试边界和导入身份。

首轮 16 次请求中，7 次因提示词缺少 JSON 字样而被 provider 拒绝，1 次输出被截断。我们保存首轮结果，并向全部 16 个提示词追加同一条格式说明。第二轮使用相同源码、步骤和模型参数。第二轮仍有 1 次截断，位于 N08 源码组。

原解析器还拒绝了无语义变化的格式差异。我们对两轮全部响应统一检查三种修复：删除 Python 定义末尾多余空白；将精确匹配许可绑定的导入对象转为名称；恢复原注册末尾的 TypeScript 分号。AST、断言和导入身份保持不变。首轮恢复 1 个测试，第二轮恢复 7 个测试。严格解析成绩和修复后成绩分别保留。

本 pilot 不使用第二个模型提前筛除候选。所有结构有效的候选都进入原生环境。每次运行保留原测试作为控制组。所有失败均重复一次。审查者先判断完整测试的契约依据，再查看运行结果。报告不删除失败后尚未执行的可疑断言，也不将测试通过当作断言有效的证明。

P7 是本轮清楚的有效反例。模型将外层 transform 设为大写转换，并检查解析后的树。原控制测试两次通过。新测试两次失败。日志明确显示根值仍为 a，而期望为 A。源码显示 _resolveRecur 用 Object.assign 覆盖 pipeline 的运行函数，丢失外层动作。日志省略了子节点，因此本报告不声称已动态确认子节点差异。失败后的 safeParse 检查没有执行。

P7 首轮历史组也曾生成非恒等变换，但它把变换放在字段内部。该测试通过。这个结果表明，操作出现的位置很重要。“递归”和“变换”同时出现，仍不等于覆盖目标交互。

首轮严格执行 11 个候选，格式修复后共执行 12 个。源码组在 N04 得到 1 个有效目标反例，历史组为 0。第二轮源码组的有效案例变成 P7。两轮提示词不同，且首轮有 provider 错误。不能合并两轮各自最好的案例并称为一次统一的 2/8 成绩。

两轮共发送 32 次 provider 请求，执行 36 个候选实例。计入失败复现，共有 45 组原生运行。每组均通过原测试控制。provider 已返回的用量合计为 718,934 token；7 次错误请求没有用量记录。本轮没有以开销作为优化目标。

依据：机器可读汇总；首轮 N 组执行审计；第二轮 N 组执行审计；P7 反例及 P 组汇总；P2 与导入格式修复执行审计。

如何解释当前失败。第一处问题是关系抽取不足。规则找到名称相同的调用，却没有证明它们作用于同一对象或资源。第二处问题是缺少具体生成约束。模型收到原始历史后，仍需自行发现哪些前提分开测试、哪些观察已经失效。第三处问题是断言扩张。模型增加许多检查，却引入编码、生命周期、顺序或状态语义错误。

目前不能从这些记录推断 agent “遗忘逻辑”或“只追求覆盖率”。我们能直接观察的是：验证先于修改；某个返回分量未被检查；计划表达式没有出现在后续字面命令中；类型检查没有对应的运行时值观察。这些事实足以指导算法，不需要猜测心理原因。

下一步先改问题抽象。将目标表示为一项具体的验证义务：在某个版本上，对某个对象或资源，在规定前提下执行操作，并观察契约要求的结果。组合缺口表示这项义务缺少某个前提组合或结果观察。单独统计操作或 API 共现，不足以证明义务已被验证。

可以用六个字段保存该义务：契约来源、前提、操作、观察、对象或资源、代码版本。trajectory 提供计划、修改和执行之间的关系。程序分析负责建立可检查的绑定。大模型负责把这些绑定转成完整测试。生成器不能自行把当前实现输出当作期望。

建议下一轮优先验证的三个机制
优先实验非大模型分析提供给生成器的约束成功判据
N06：恢复已有验证恢复临时脚本；连接后续被修改的实际调用路径；区分打印与断言。保留历史脚本中的原输入组合；补齐与公开契约相符的结果观察。历史组必须实际重放添加加文本修改，而非再次生成独立添加。把重放恢复与新组合生成分开计数。
N04：让约束能区分写入绑定同一 DB 和表；分开 SQL 读取字段、写入字段及 WHERE 条件；检查写入是否能改变约束真假。选择能使约束变假的合法写入；只检查拒绝和无序的最终状态。每个候选都改变目标约束的判别条件；完整测试不再依赖未承诺的行顺序。
P7：连接类型观察与运行观察按 schema 结构和参数位置对齐 type-only 与 runtime 测试；识别外层非恒等动作。固定动作位于外层 pipe；在递归结果上检查可推导的变换。新增运行时值观察；分别验证根与子层；不以只读类型或对象身份代替变换结果。

N01、N09 和 P2 可作为下一批扩展。N01 需要连接异常边与资源关闭。N09 需要从 schema 字段集合产生部分参数，并在 flush 前后保存值快照。P2 需要按协议编码字段，并根据 helper 的 EOF 行为建立新 parser。上述设计应先输出可核对的事实，再生成测试。

N08 应先单独解决期望依据。NoSync 的负面时间窗口不足以证明未耐久。边界测试需要明确的批次身份、写数及同步先后条件。在这些前提建立之前，不应把等待返回或超时直接当作目标缺陷。

下一轮建议保留三个输入组：仅源码、源码加原始步骤、源码加结构化义务及其原始证据。三组使用同一模型和生成次数。先比较目标交互是否真正进入测试，再比较完整断言有效率和有效反例数。不要只比较失败数量。

结构化义务可以先由人工制作，以检查该表示是否有用。随后让冻结的程序分析生成同样的字段，再测自动流程。人工目标标签必须继续留在评价侧。完成机制试验后，再按独立任务或项目划分未见数据，避免重复任务同时进入开发集和测试集。

对 novelty 的含义。本 pilot 尚未证明新的有效算法。新颖性也不取决于是否有人使用过 AST、变异或大模型。更有价值的贡献候选是：从开发历史恢复被修改破坏或未落实的验证义务，并据此生成有特定判别目标的测试。论文需要证明这种关系比当前测试和原始历史文本提供了稳定增量。现在的结果还没有达到这一点。

本报告保留所有无效、未定、通过、截断和格式拒绝记录。它没有更新既有最佳配置，也没有把本次 pilot 并入此前已结束的搜索窗口。

复核材料：原协议；统一格式修复协议；N 组手选材料；P 组手选材料；输入与语义保持核验。

外部契约依据：Kitty 键盘协议规定 modifier 为 1 加各位标志。Valibot readonly 文档和TypeScript readonly 文档支持类型限制，不支持运行时冻结要求。仓库公开 issue 和原始源码是其余个案的主要依据。

结果以完整测试为单位。失败前缀、源码推断和已执行断言分别记录。报告采用保守计数，不将未执行观察当作实验事实。
