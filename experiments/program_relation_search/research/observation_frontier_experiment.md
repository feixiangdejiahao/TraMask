**观察前沿实验：七例双 Hit@10 达到 1**

日期：2026-09-23。旧目标标注、候选代码、补丁和 trajectory 保持不变。当前方法在七例上达到 **Test Hit@10=7/7、Assertion Hit@10=7/7**；去掉 trajectory 后结果相同。全部分析在本地完成，无模型调用或代码上传。

原始全量结果：[最终复核](../results/anchor_retrieval/frontier_final/report.md)、[首次达标运行](../results/anchor_retrieval/frontier_v2/report.md)、[repository-only](../results/anchor_retrieval/frontier_v2_repository_only/report.md)。本报告对应 [方法定义](method_design.md)，不能用来证明组合生成或 issue resolution 已完成。

**1. 改进来自什么抽象**

核心抽象是观察前沿：同一测试中，聚合字段或后续调用的输出可能包含中间检查的依赖来源，应优先访问这些观察。偏序由代码依赖足迹计算，没有测试意图 schema、模型生成语义标签或 case 专属排序规则。

同一依赖足迹内部，值观察优先于错误/空值状态检查；同层使用参数化期望区分数，再以源码顺序打破平局。测试顺序沿用已有 patch/关键词基线，预算按测试轮换。算法与全部修订理由在 [事前约定和迭代记录](observation_frontier_plan.md) 中保存。

**4. 各例为什么选到目标**

- P1：phase 断言的参数化期望区分三个结果；同层 key 的期望是常量，派生布尔检查区分度较低。
- P2：character 的来源集合包含 key；character、modifiers、base_key 仍不可相互包含，源码顺序把 character 放在前面。这里有明确的排序歧义，不能声称算法已理解完整契约。
- P3：aliases 的生产计算汇合多个元数据来源，因此位于 key、shifted_key 等中间字段之后的观察前沿。
- P4：根据生产值来源识别 status 是实际观察，而右侧字典是期望。不同时间的 status 调用保留不同发生位置，后面的状态不会仅凭 may-state 边覆盖前面的状态。
- P5：returned 对象继续被调用，其值足迹包含对象创建/返回过程；目标返回值检查进入前沿。
- P6：同一次调用的返回值检查与 NoError 具有相同足迹，值观察得到优先位置。该结果仍只是原有 clone 测试入口的检索。
- P7：parse 消费构造出的 schema，足迹包含构造过程并增加执行调用，所以优先于单独检查 schema 内部引用。

**5. 避免针对七例修改的具体措施与剩余局限**

已核验：

- 原始目标标签逐字节等于 Git 基线；原七例输入哈希与旧实验一致。
- 检索模块不读取标注；算法没有 pilot 名称、目标行号、人工目标关键词或权重搜索。
- 38 个回归检查通过，覆盖独立的字段聚合、调用消费、状态顺序、参数化期望、常量分派、期望表达式识别和重命名例子。
- 七例各进行五种候选记录顺序打乱，共 35 次；完整排名不变。
- 混淆每个测试的 name/test_id 元数据后，七例完整排名不变。这是提取记录层面的检查，不是假称对全部仓库进行了语义保持重构。
- 完全不读取 trajectory 的七例运行同样双 Hit@10=1。
- 最终从源码重新分析七例，全部 23,853 个断言的完整排序与首次达标运行一致；核验代码与实现快照的哈希相同。

这些措施防止标签泄漏、显式样本特例和若干表示层脆弱性，**不能证明不存在开发集过拟合**。七例均已人工阅读，只有四个 issue 家族；第二轮对 P6 的 outcome/value 精度关系也受失败分析启发。需要未见 issue 的冻结评测才能评价泛化。

源码顺序仍处理不可比较候选，换一种断言书写顺序可能改变 P2 等例的第一代表。数据流包含也可能因错误屏蔽而选到更弱的 oracle。当前没有完整 guest-language capture/alias 分析，不保证负结果说明组合不存在，也没有测所有候选的 precision。
