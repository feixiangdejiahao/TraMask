# 有限 oracle 模板：独立批判与最小研究设计

2026-09-30。本笔记只阅读本地论文笔记和已封存结果；没有请求模型、执行 subject 或修改生产代码。讨论对象是正在实现的原型，不能将下文的待实现分析和实验算作已有能力。

**判断：值得作为有限、可审计的原型尝试；代码因子化本身仍是摊销机制，尚不能作为新的核心程序分析贡献。** 它与精确等价去重不同：不合并不同输入的行为，也不把某个成员的 oracle 推广给其他成员，而是要求模型完成有限域内每个成员的完整预期。但这仍没有自动解决哪些 family 应获得预算，也没有保证一次请求会正确回答所有成员。

## 1. 当前证据要求我们避免什么主张

三个现有负结果直接约束新方向。

- [精确材料去重](exact_oracle_material_v1.md)：4,502 个候选仍有 4,502 种严格 oracle 材料，首轮 271 次实际请求全部不同。有限模板不能宣称这些程序等价；它共享的是明确相同的源码部分。
- [同上下文分组](context_candidate_groups_v1.md)：4,502 个候选形成 4,160 组，3,995 组为单例。旧分组每组只让模型选择一个成员；新方向应明确改变为逐成员完整回答。若放宽分组条件，必须保留差异，不得因分组把 import、接收对象或观察阶段抹掉。
- [三臂上下文消融](relation_search_v3_evaluation.md)：同一批 17 条请求中，完整依赖上下文与仅保留同组声明的正确判断均为 9/17；声明臂减少 token，却还产生了一个错误削弱预期。增加依赖文字或减少文本均未证明更可靠。

因此，增加“16 组、每组若干成员”的曝光，可以有实际价值，但它首先改变了成本分配。不能把它与 16 个单例称为相同候选预算，也不能把更多成员被看见称为更多正确测试。

## 2. 最小可实现抽象与严格有限的保证

用一个完整源测试 `T` 和若干源码编辑孔 `h1…hr` 表示一个测试家族。每个成员保留它实际已有的**联合替换向量** `d_i=(v_i1,…,v_ir)`，而非各孔值的笛卡尔积。骨架与有限成员表满足：

```text
expand(T, d_i) = 该成员原来的完整修改后测试源码
```

这条等式是机械可检验的字节还原条件。原 source owner、imports、fixture、源控制、完整断言和每个成员的差异都必须能还原。不同 imports 等上下文可以逐成员保存，或据此拆组；两种做法都不能忽略差异。相同形状的另一对象、callee 或 history 不自动成为相同语义问题。

给定每个成员共有的断言清单 `a1…ak`，请求的是有限表：

```text
member i -> [assertion 1 的完整预期, …, assertion k 的完整预期]
```

清单还应包含模型接口无法修改的断言；如果该断言需要改变却不能表示，成员应为未完成，不能保留错误断言后宣称完整正确。漏行、未知和截断同样是未完成。程序回填后核验各成员自己的输入、调用、绑定、观察表达式和非预期语句仍与还原源码相同，不能仅验证第一条失败断言。

这能给出的保证只有：原成员不丢失、成员与预期对应明确、孔外代码保留、输出覆盖可以核查。它不保证期望正确、断言足够强、模型可复现、自动选择覆盖所有 gap，或分组内存在某种行为等价。每个完整向量仍需要独立语义评价与命名执行证据。

骨架表示可把重复源码规模从约 `nL` 降为 `L + Σ|d_i|`，但输出规模仍至少随成员数与断言数增长。模型也仍可能需要逐成员推理不同路径。若没有额外计算，这就是表示和请求的摊销，不是已证明降低了语义复杂度。

## 3. 程序分析真正简化推理的最小下一步

[STARS 笔记](stars_abstraction_review.md)给出的有用标准是：可计算结构应直接导出模型不再需要猜测的构造或连接步骤。STARS 的类型链规定怎样扩展 observer；我们的骨架只规定怎样还原已有成员，尚没有同等的语义任务分解能力。

可以在有限家族内尝试一个很小的分析，而非再增加关系 schema：**将共同测试骨架中的局部对象绑定、实际调用与观察位置展开成一次共享的、带源码位置的操作序列，逐成员仅替换输入孔。** 模型仍读取完整源码，但不再需要自行重建局部别名和 helper 实参传递。

例如共同测试中有：

```python
box = Box()
alias = box
alias.add(h)
saved = box.items()
box.add("tail")
assert saved == ...
assert box.items() == ...
```

程序能够确定 `alias` 和 `box` 来自同一次局部分配，第一次观察位于第二次 add 之前，第二次观察位于之后。它不能仅凭方法名证明 `items()` 返回副本还是共享列表；这项契约判断应保留给模型，候选实现也不能作为正确答案。分析输出是原代码的确定性绑定展开，不是模型生成的“共享状态关系”标签。

最小算法可以只支持三项规则：局部赋值替换；解析到确切 helper 后按实参绑定形参；保留调用和断言的源码先后位置。分支、返回值别名、动态调用与未知副作用保持显式未知，并保留相应完整源码。不要为了产出漂亮序列猜测跨函数对象身份。若实现只完成这三项，就只声称这三项覆盖，不能把它称为完整符号执行或完备切片。

更强的 hole→observation 依赖可以以后加入，但现有图义务排序没有收益，不能直接将它改名为新核心。只有当确定性展开减少模型的绑定/阶段错误，并提高完整预期正确率，才有证据说分析简化了推理。普通局部别名和实参分析仍是已有技术；这个研究假说的增量在于是否能为**有限候选家族的联合 oracle 推理**提供有效分解，而非分析技术本身的新颖性。

## 4. 最小公平对照

先固定未经目标真值选择的一组 family 和每组完全相同的成员；封存原始源码、孔表、顺序、上下文、模型设置与上限。17 trial 是已见开发材料，不能据其结果调整分组边界后声称泛化。

第一组对照只检验因子化：

| 臂 | 模型看到的程序 | 请求的答案 |
| --- | --- | --- |
| Expanded-joint | 每个成员的完整程序逐一展开 | 同一组成员的全部完整预期向量 |
| Template-joint | 一份精确骨架与全部联合替换向量 | 完全相同的预期向量 |

两臂都是一次请求，成员、源码证据与输出范围相同，仅改变代码表示。这样才不会把 joint reasoning、调用数、候选数和代码共享混在一起。对原单例生产接口的比较可另列为实际成本基线，不能将其差异全部归因于因子化。

第二组对照才检验程序分析：固定 template-joint，比较有/无上述确定性绑定展开；孔表、全部断言和源码声明不变。如果没有实现该分析，就不要开展“程序分析收益”的实验或作相应结论。不要用“另一臂删掉完整 helper 源码”制造信息缺失对照。

首先做相同成员曝光和相同模型设置的配对试验，报告实际 token；另做固定实际模型成本的调度试验，检查节省是否能购买更多**正确** oracle。固定 token 预算与固定候选数量不是同一条件，单次长度上限相同也不意味着实际成本相同。

最低限度报告：逐成员完整 oracle 正确率、整个 family 全正确比例、未知/截断/漏行、结构接纳率、经源控制与命名执行确认的正确缺陷见证、首次正确见证的 token/时间成本。单独检查输入绑定和观察阶段错误，作为“程序分析确实帮助模型”的机制指标。成员共享大量源码，不能把它们当相互独立的缺陷样本；统计单位同时报告 trial、去重后的任务和 family。

排序/搜索实验中，两臂还须使用相同候选池、原排序与执行预算。若改成按 family 排序，每组曝光不同成员，需另列收益来自调度还是预期推理。禁止拿特定目标 rank 决定某组大小或例外规则。

## 5. 何时应该停止这条方向

若实际 family 几乎都是单例，则因子化不解决预算瓶颈；不应继续放宽身份来凑成员。若只降低输入 token 而完整 oracle 正确率不变，则可以保留为成本改进，但学术主张应相应收缩。若 joint 请求更容易截断、遗漏后续断言或让一条错误推理污染整组，须报告它的可靠性损失。

更合理的最低目标是先证明：准确的局部绑定展开让模型少犯一种明确的程序理解错误，并在同成员、同模型的条件下提高完整预期正确率。若做不到，当前证据支持的仍是有限批处理原型，尚不是满足用户要求的核心学术算法。

## 附录：独立配对评价器已经实现的边界

`scripts/evaluate_finite_oracle_pairs.py` 只读已封存的 paired inputs 和本次实际 completion，不调用 provider 或 subject，不读取历史 oracle 回答或目标真值，也不改变生成器。它重新核验 prepare seal、源码快照与输入 SHA，并逐成员检查 template 展开与 expanded 程序、共同提示字段、模型设置、原候选身份及声明源码位置。源码编辑由评价器独立应用；布尔 `all_common_fields_equal` 本身不作为证明。v2 的 17 个多成员 pair、每臂 50 个成员已通过这项只读核验；该 v2 目录没有模型调用。

实际响应另外核验 raw body、JSON、completion text 和实际 wire 与 preview 的对应。审查包逐成员提供输入完整测试、实际模型行、预期编辑、模型提出的完整测试、实际接纳测试、全部原断言和源码证据位置。缺失、unknown、格式无效、结构拒收、正确但不可运输的预期分开记录；不会把 source control 通过或结构接纳自动当语义正确。

人工 ledger 可以只列已经审查的成员，未列成员保持 `unreviewed`。每行使用简单 JSON：case、candidate_id、arm、response_sha256、proposed_test_sha256、verdict 和 reason。`correct/incorrect/uncertain` 必须针对修改后完整程序和全部预期给出原因；正确 verdict 不能用于 unknown 或缺失的完整 oracle。它绑定该响应和该完整 proposal，而非只绑定候选 ID。合理但被结构接口拒收的完整预期可以单列为语义正确，最终可生成的正确修订仍为零。这个人工评价不会回馈候选选择，也不增加主臂 gap 或 issue-resolution 得分。

本地合成响应的评价器测试覆盖 14 项，包括：无回答不计分；keep/revise 不自动得语义分；完整人工 review 的证据绑定；合理但接口拒收与接纳分离；unknown 不可升级；一个 malformed 成员不抹去另一成员；实际模型设置不一致；直接重算展开而非信任旧审计；接纳 artifact 不得改 imports、动作或成员清单。测试只证明评价边界，并不证明模型正确性。

评价器 v2 还修正了一个运输与语义的混淆：唯一明确的 `keep/revise` 行若只遗漏 prose `basis`，完整预期仍可恢复供人工审查；recorded structural 状态仍为 `invalid_answer`，不生成接纳测试。重复 alias、未知状态、不完整或非法 updates 不享有这一恢复规则。这个通用评价修复应用两臂全部成员，没有改变模型提示、冻结请求或 validator。

v3 第一项已完成的 N01 pair 提供了具体例子。两臂都对缺少 RS 的 JSON-seq、invalid charset 的三成员提出第二次迭代也应 `DecodingError` 的完整异常预期；issue 明确规定对应错误，并要求 in-memory 可重复，因此三条 proposal 的两个观察阶段一致。但当前冻结 assertion guard 不能运输 `assert` 到 `with raises` 的变化，三条均被拒收。第四成员的固定首次 `raises` 与合法 NDJSON 相矛盾，双方明确 unknown，不能算作完整正确 oracle。该例的判断根据本次 issue 和完整 proposal，未依据候选实现的当前输出，且尚未 subject 执行；它不证明 template 优于 expanded，也不是新增缺陷检出。
