# 数值关系分桶：拆开了形状，但没有改善本次模型预算分配

**对固定 17 个案例、4502 个源池候选进行静态比较后，所有案例的前 16 名候选都没有变化。** 数值方向确实把一些原本相同的形状拆开：总桶数从 3789 增为 3801，4 个案例的完整排序变化；但这没有增加本次预算内的语义判断覆盖。不能把“分桶更细”直接等同于找目标更快。

## 最小改动与三种关系的区别

现有 `semantic_selection` 擦除字面量值，先调度所有形状的首个代表，再调度同形状的第二个代表。原型保留原 family、seed、代表排序、material hash、候选内容与预算，只给形状加入有限数值关系。源码池来自 `candidate_inventory_v1` 全部 17 例 `source_pool.json`；[执行前协议](../results/relation_search_20260929/numeric_relation_buckets_v1/protocol.json)封存所有输入和代码 SHA。生成过程不读目标标签、issue、缓存或执行结果，不运行被测程序、不请求模型。

| 关系 | 由程序如何获得 | 实际能说明什么 |
|---|---|---|
| 新值对原值的 `<,=,>` | 验证整段编辑对应数值 AST 字面量，比较替换前后数学值 | 输入变化方向；**不是**被测程序的决策边界或行为等价。 |
| 同调用其他数值实参的 `<,=,>` | 解析同一调用中的实参位置；同时被编辑的实参使用其新值 | 调用输入间的关系；仅仅同在一个调用，尚无程序读写依赖证明。 |
| 局部赋值到比较式的 `<,=,>` | 在受支持 Python 直线局部绑定中，连接数值赋值和后续直接读取该变量的比较式；遇到重赋值/闭包写入停止 | 有限的局部 def-use 证据。这里连接的是测试内变量与谓词，仍没有恢复跨调用的被测代码比较条件。 |

基线只用原来的字面量擦除；`delta` 增加第一项；`context` 再增加后两项。比较在隔离加载的同一调度器上进行，只替换 shape 函数，没有修改生产文件或通过改 candidate.relation 间接改变 material 排序。数值字面量以精确数学值比较，不声称类型转换、溢出或运行时浮点行为已经验证。字符串中的数字、任意表达式、调用与布尔值不伪装成数值字面量。

各例完整排序、variant round、候选 ID、关系提取位置与三臂选择都在 [numeric_relation_buckets_v1](../results/relation_search_20260929/numeric_relation_buckets_v1/summary.json)。[逐项次序等价检查](../results/relation_search_20260929/numeric_relation_buckets_v1/order_equivalence_v1.json)确认前 16 名的 ID 与次序均未变化。静态 rank 是模型判断名额的可达性，不能解释为缺陷检出或 oracle 正确性。

独立评价者在排序结果封存后，以完整程序编辑、base 与 imports 匹配已有参考 parent，未仅依赖 ID。[独立对照](../results/relation_search_20260929/evaluation/numeric_relation_buckets_review_v1.json)确认 17 个参考 parent 均存在于固定池中，三臂的 parent 覆盖 @16 均为 **9/17**。仅 N05 改善（170→109，variant round 1→0），N03 退化（53→54）；其余 15 例排名不变。delta 与 context 的对照结果完全相同。N05 由同桶第二代表变为首代表，仍在预算之外，直接说明拆桶没有解决全局调度问题。

这里的分母是 17 个既有材料参照，不是 17 个本次确认有效的缺陷测试：N08 旧 parent 的完整搬运前缀仍存在契约争议，仅作排名参照；后续净化的 v2 N08 测试没有回填本次冻结池。上述 9/17 既不是执行检出率，也不证明这些 parent 的原断言正确。

## N05 表明真正需要保留的是哪种关系

`5→4` 与 `5→100` 应分开，理由不能只是一个更小、一个更大。N05 的被测代码里真正控制路径的是 `ansi/ansi.go:281`：

```go
if ANSIWidth(s) <= width {
    return s
}
```

后面还有 286 行的 `remaining := width - ANSIWidth(tail)`、305 行的 `tw <= remaining-w`。这些是输入 width 与**程序计算得到的可见宽度**之间的比较。源码及 SHA 封存在[比较式证据](../results/relation_search_20260929/numeric_relation_buckets_v1/N05_program_predicate_excerpt.json)，仅用于本节人工诊断，没有进入排序。

因此，`sign(new_width-old_width)` 只是在这个例子上可能与真正边界相关；两个都大于旧值的宽度，仍可能分居 `ANSIWidth(s)` 两侧。把同调用字符串的字符数当作阈值也不可靠，因为源码明确使用去除 ANSI 后的可见宽度，而非字节数或普通字符串长度。现有原型未把实参 width 传到形参、再沿 `ANSIWidth(s)` 的数据依赖恢复这条比较，不能称它完成了这种程序分析。

更有研究价值的下一步是：**只保留可由 actual/formal 绑定和真实读取连接到的程序比较关系**。对于不能静态求值的派生量，记录待测表达式与来源，或在原有执行中捕获该比较的真实两个操作数；不能用任意邻近常量代替。之后再验证这些关系是否能改变有限预算下的目标名额。该方案还需要独立实验；当前证据仅否定了“按输入数值方向细分即可修复预算问题”的乐观推断。

调度本身也必须与分桶分开评价：全局“所有首代表优先”会让局部有意义的第二种情况排在许多其他形状之后。把一个案例拆成更多首代表，仍可能落在预算外。下一次若改调度，应保持候选和关系分桶固定做独立消融，不叠加新构造器或按目标 ID 提前候选。

实现为 [numeric_relation_buckets.py](../experimental/numeric_relation_buckets.py)及[批处理入口](../scripts/analyze_numeric_relation_buckets.py)，24 项测试通过，涵盖三种语言的值方向、同调用阈值跨越、局部重赋值阴性控制、重命名不变性、字符串数字拒绝、同时编辑、输入不变及无数值证据时完整调度不变。原型只做静态排序，没有新的模型请求、Docker 运行或检出结论。
