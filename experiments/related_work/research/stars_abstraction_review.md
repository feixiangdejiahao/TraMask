# 从 STARS 重新审视方法抽象

2026-09-28。阅读对象为 [STARS: Static Analysis-Guided Assertion Synthesis using Large Language Models](https://www.software-lab.org/publications/issta2026_STARS.pdf)，ISSTA 2026，25 页。下文页码指论文印刷页码。

**结论：保留三个问题观察，但将 `(q, ρ)` 降为问题描述与评价记号，不再将它作为已经成立的核心算法贡献。** 它表达了希望得到什么测试，却没有规定如何有效地生成该测试。已有代码及 4/17 结果作为原型和基线保留；本次阅读没有开展新实验，也没有提出一个已经验证的新统一算法。

## 1. STARS 的抽象为什么能够导出算法

论文解决的是：给定已经存在的 test prefix，为它合成断言；不是从头合成测试输入和动作。其困难包括：断言需要调用测试前缀和 focal method 之外的方法，而模型缺少足够信息猜出完整调用链。问题定义见第 5 页 §2.1，实例见第 2–3 页。

例如，测试已经构造 `Cell`，并向其中放入一个带文本的对象。希望检查保存的文本，可能需要下面的路径：

```java
cell.getTextElements().get(_).getText()
```

STARS 从已有变量及其类型出发，在项目中解析方法，按返回类型继续寻找可调用方法。这个例子的连接依据为：

```text
Cell → List<TextChunk> → TextChunk → String
```

关键在于：完整链不必已经出现在源测试里。类型信息让程序可以合成它；模型接到这个具体结构后，再补索引、期望和断言种类。论文的三个组件集合是变量 `V`、同型变量对 `P`、observer 方法调用链 `M`（第 7–10 页 §3.1，算法 1、2）。

下面是对其调用链构造的解释性概括，并非照抄论文公式：

```text
起点：测试作用域中已有 x:T，得到表达式 x。
扩展：已有 e:T，找到可访问的 observer m(...):U，得到 e.m(参数孔...)。
递归：沿返回类型 U 继续扩展，直到深度上限或不可继续搜索。
裁剪：排除无可用参数类型的调用；按论文规则去掉被较长链包含的短链。
具体化：模型为保留下来的结构补参数、期望及断言形式。
```

因此，表示和算法之间有直接联系：

| 表示中可计算的信息 | 直接支持的算法操作 |
|---|---|
| 测试作用域内的变量与类型 | 确定有限搜索起点 |
| 方法的接收者类型和返回类型 | 沿类型连接做有界 DFS |
| 方法是否直接或间接执行字段写指令 | 按论文 observer 判据排除改变状态的方法 |
| 参数类型与已有变量类型 | 按参数类型可用性规则裁剪链 |
| 调用链的组成与包含关系 | 去重和启发式裁剪 |
| 保留下来的方法链与参数孔 | 明确模型还需要完成的内容 |

这些判据也有边界。observer 判据不是任意语言中的完整纯度证明；较长链也不一定在所有意义上都比短链更有信息。论文选择了受限标准库范围并限制链长。其价值是提供具体、可实现、可测量的搜索机制，而非给出无漏报保证。

论文还把构件发现与最终断言质量分别评价，并使用与特征统计不同的数据做方法评价（§2.2、§4.5）。这允许检查收益是否确实来自构件合成，而非只比较最后的模型输出。

## 2. 不能从论文中误学什么

**不能把它说成完全静态或只在最后使用一次模型。** §3.1 写明模型参与相关变量选择；模型还参与断言生成、选择、修复和排序。§4.5 关于第一步不涉及模型的文字，与 §3.1 及第 19 页 Table 6 的 gathering 请求数不一致。因此这里只将“调用链结构由静态搜索构造”作为明确的方法结论，不把整条流水线描述成确定性算法。

**不能照搬运行失败后修期望的过程。** 第 10 页 §3.3 明确采用回归测试设置，假设被测代码正确，因此可以根据运行错误修复断言。我们的候选补丁可能有缺陷；如果把 P2 的 `character is None` 改成当前错误输出 `'a'`，测试就会通过，但检测目标也被消除了。

**也不能把类型兼容当作语义正确。** 类型分析解决哪些表达式可以构造，不决定新场景下什么结果应当成立。STARS 对 oracle 的语义判断仍有模型和测试设置的依赖；它没有提供适用于我们任务的通用期望迁移证明。

## 3. 旧抽象具体缺在哪里

旧设计写的是：

```text
ρ = recover_relations(q, source, validations)
t = construct_small_witness(q, ρ)
```

这里恰好把全部主要困难藏进了两个函数：如何从程序得到值得组合的关系，如何把关系变成可执行输入和操作。为目标写出 `sA < sB < eA < eB`，并没有实现从仓库自动提取端点或构造相应文本。写出“同一对象、异常出口”也没有实现把正常流构造和异常路径连接起来。

`(q, ρ)` 仍然有用：它能区分找到源测试、形成目标场景、观察是否充分等评价层次。但它没有提供类似 STARS 的“沿返回类型扩展一个方法调用”这样的通用构造运算。实际代码不得不依赖多个关系适配器；把这些适配器统一放在一个符号下面，并没有消除算法差异。

“依赖汇合点＋约束求解”“关系图＋最小见证”也已出现在旧文档中。若没有明确节点来源、生成规则和约束来源，重新命名不会使它们成为新的解决机制。

## 4. 对我们而言，什么才算具体的构造机制

下面用 N02 说明设计应达到的具体程度，**不是宣布一个新的统一方法或新增实验成功**。

可以研究从已有测试提取带输入孔的构造片段，以及调用的正常/异常出口后的观察。一个有限的拼接运算可以：

1. 从 AST、作用域与 CFG 得到片段的自由变量、定义、调用和出口位置。
2. 将畸形数据片段绑定到流构造片段的输入孔，保留必要的构造与分块操作。
3. 将消费调用和已有异常检查绑定到构造得到的同一 response。
4. 把 response 的状态观察接到捕获异常之后。
5. 根据 definite-assignment 排除异常路径中未赋值的结果变量所对应的观察。

示意代码如下。实际 body、构造器、异常类型和属性必须来自已有源码，不能凭 case 名填入：

```python
body = malformed_body
r = Response(..., stream=IteratorByteStream(chunks(body)))
with raises(DecodingError):
    parts = list(r.iter_multipart())
assert r.is_closed
```

正常测试里的 `len(parts)` 检查不能直接移到这里，因为调用抛异常后 `parts` 未赋值。对象绑定和 definite-assignment 能给出实际的连接及裁剪操作。这与“组合异常和关闭特征”相比，明确了程序到底要生成哪些语句、保留哪些绑定、删除哪种无效观察。

但这仍有两个实质限制。第一，正常消费后应关闭，不自动推出异常消费后也应关闭；新期望仍需 issue/契约等独立依据。正常转账后的余额断言就不能无条件移到转账失败之后。第二，这一连接运算不能自动构造 N07 的区间交叠，也不解决 P6 的闭包共享图。

已有动作/观察组合原型也做过片段及端口绑定。因此，仅提出“可连接片段”还不是新贡献；必须找到旧算法不具备的构造或搜索机制，并展示它如何减少搜索或增加有效测试，才值得作为新方向。不能为了统一 17 个案例而把所有缺口重新交给一个不可解释的生成函数。

## 5. 新设计的准入标准

下一版应先给出以下可审核内容，再给抽象取名：

- **提取规则**：仅凭未经目标标注的源码和验证，究竟能得到哪些具体代码构件；不支持的输入如何识别。
- **构造规则**：一次扩展产生哪段新程序，为什么保持变量绑定和执行上下文；不能只写“求一个见证”。
- **搜索收益**：该表示如何裁剪候选、减少重复或生成检索不到的结构；指出预算用在哪个维度。
- **观察和期望的分工**：哪些是可构造的观察，哪些正确性依赖独立语义判断；不得用 buggy candidate 的实际值校准 expected。
- **可反驳的证据**：同一构造操作是否能处理结构不同的案例，以及在哪里失败；与已有片段拼接、等预算枚举/符号生成比较，不能把新名称当作创新。

17 个案例继续作为发现集和反例集，不成为新方法的盲测。先评价结构是否生成出来，再评价期望与真实缺陷检出。若新的表示仍要求给每个失败模式添加单独生成器，就应承认统一抽象尚未成立。

本次决定是修正研究定位，不改写历史结果：三个观察保留；旧 `(q, ρ)` 降为描述和评价工具；实现与 4/17 结果保持原样。尚未选定一个满足上述标准的替代核心算法。
