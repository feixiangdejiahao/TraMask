Coding agent 的组合缺口检测：开发过程与程序计算对照

2026-10-10 · 8 项任务 · 4 组方法 · 每组重复 2 次 · 64 次检测运行

已完成 64 次检测。四组在两次重复中的正确任务数分别为：A：代码与测试片段 4 / 3；B：加入开发过程 3 / 4；C：模型先建行为模型 4 / 2；D：再加入程序计算 3 / 2。每次的分母均为 8。本轮没有证据表明加入有限程序计算能提高检测效果。

研究场景是 coding agent 修改仓库后、提交补丁前的测试补强。正确结果必须给出具体组合：原补丁不能满足，gold patch 可以满足，且原验证没有已经暴露同一失败。我们只做静态语义核验。本轮没有生成或执行补测，也没有测量 issue resolution rate。

1. 问题与本轮算法

一个 agent 可以分别验证多个局部行为，却没有检查它们在同一状态、同一对象或同一执行过程中的共同效果。例如，测试分别检查配置默认值和策略合并，却没有检查默认值是否在合并后保留。本文把这种遗漏称为组合缺口。

开发过程还有最终代码没有表达的信息。agent 可能只检查中间字段，绕过真实入口，或在失败后改变测试输入。这些记录可以缩小补测搜索范围，也可以证明某项失败已经出现。后者属于反馈处理问题。

原型先用程序收集修改代码、测试片段和开发事件。它保留完整命令时间线，并优先选取失败输出、相邻修改及相关测试。程序还解析测试调用中直接写出的值，例如 false、数字和字符串。下文称这些值为字面值。它不能据此证明测试实际执行，也不能解析任意变量、闭包共享或嵌入字符串中的程序语义。

模型随后提出最多两个行为区别。它可以提前选择需要查询的源码和历史步骤，也可以建立一个小模型：列出有限的输入取值，用两个表达式分别表示当前输出与要求输出。程序尝试从原测试绑定输入，再枚举原行为与要求行为不同的取值。模型最后形成并复核具体检测目标。

这里的两个表达式由模型提出。程序计算正确，不代表表达式忠实于源码或需求。实验因此单独核验表达式、测试绑定和最终目标，不把它们合成一个成功指标。

正确任务数：该次运行至少发现一个符合上述规则的目标。目标可以是旧标签，也可以是新发现。

固定目标命中与漏检：本轮有八个预先冻结的目标。严格命中须保留该目标的关键条件、操作和观察。漏检数等于八减去命中数。没有固定标签不代表任务没有错误。

同缺陷的短反例：如果报告指出同一根本错误，但少了固定目标要求的后续操作，我们另列。例如，直接检查恢复后的错误标记，不等于已经检查 React 挂载后的刷新。有效短反例仍计入正确任务数。

不合格报告：肯定报告不满足本轮差分规则。原因可能是 gold 也失败、原验证已经暴露失败，或源码推断错误。gold 也失败不等于原补丁正确。我们另列待定项，不把它们强行算成误报或正确结果。

全部肯定报告由本轮 Codex 逐条静态复核。复核读取原补丁、gold、公开需求和历史验证。它不是独立人工标注，也不是动态执行证明。gold 和 benchmark 信息仅用于评估，没有提供给被测方法。

如果已有能揭示同一错误的联合测试，但 agent 没有运行，我们将它归为选测问题。如果 agent 已经看到失败，却没有修复，我们将它归为反馈处理问题。二者都不能计为新发现的测试组合缺口。测试可以更强，也不等于原补丁存在错误。

4. 程序提取与计算是否发挥作用

字面值提取只覆盖很小一部分仓库测试。闭包共享、缓存所属容器、初始化后的状态，以及字符串中的 Tengo 程序都需要其他语义。模型提供的 suggested_values 没有参与原测试计算，因此不会被误计成程序提取成功。

部分绑定还使用了错误的结构：模型没有用因子名组织查询。程序拒绝这些绑定。格式正确也不一定代表语义正确，例如字段存在不能直接证明该字段处在 anyOf 内部。修正接口格式不足以解决行为表示问题。

接口说明没有清楚展示“输入名称对应查询”的完整例子。这是本轮实现的问题。因此，零成功绑定不能用来证明程序分析本身没有价值。它也说明 D 组实际检验的是枚举模型提出的假设，尚未完成从源码和原测试推导区别的核心设计。

我们另做了一项不调用模型的诊断。只对单输入模型修正查询的外层格式，保留查询路径、取值和表达式。11 个模型适用此规则，5 个得到形式上完整的绑定。逐项复核后，仅 1 个正确读取了模型所指字段，其余 4 个混淆了含义或上下文。这个诊断不改变正式成绩。

例如，T28 的查询读出 refetchOnRestore=false，却把它用于“现有状态比保存状态更新”。前者控制后续刷新，后者需要比较两个对象的时间。T20 的查询读出 terminal=false，却把它用于“高优先级配置为空”。字段值相同，不代表程序含义相同。

T28/repeat2/1整项问题的布尔标签延后回调会写时间并可能再次 fetch，这个源码观察成立。但表达式只把现有状态是否更新映射为成功标签，没有计算时间或后续效果；gold 同样在默认条件下 refetch。查询的 refetchOnRestore=false 不是 live 状态较新的证据，errorUpdatedAt 单个数值也不是两个时间的比较。
T28/repeat2/2输入类别与结果表在其他 OR 项为 false 的前提下，原实现会保留 live 的 invalidation，局部结果表成立。但固定前提没有绑定。查询检查传入 snapshot 是否显式含 isInvalidated，不能代表 live 查询的标记值。原联合测试已经断言保留 live true，问题还涉及测试预期是否可靠。

5. 逐任务复核

下列条目说明每类肯定报告为何被接受、排除或保留为待定。完整输入、模型答复和逐条对应关系保存在报告末尾的数据中。

Bandit：增量缓存与命令行

损坏时间戳与过期处理：符合本轮规则。出现于 A1。

原加载器接受字符串 timestamp，启用有效期后数值减法报错。gold 在载入时检查 timestamp 数值类型并丢弃损坏条目。两版私有持久化格式不同，此处只认定语义目标，不声称同一文件编辑可在两版执行。

重用缓存时修改容量上限：不符合本轮规则。出现于 A1、A2、B1、B2、C1、C2、D1、D2。

模型要求 20/1000/5000 字节的严格上限。gold CLI 将数值解释为 MB，且按四分之一条目淘汰，不保证所提字节上限。不能把真实的旧配置覆盖风险直接计为 gold 可通过的具体目标。

扫描选项与缓存键：不符合本轮规则。出现于 A2。

原补丁与 gold 均未将 ignore_nosec 纳入缓存键。gold 也会重用无问题结果。

缓存记录与不同路径的计数：不符合本轮规则。出现于 C2、D2。

模型要求 summary 按不同文件路径计数。gold CLI 同样用 len(cache_entries) 按缓存记录计数，而 list_cached_files 用集合去重。相同文件按两个分析键缓存后，gold 也不能满足 summary=1 的具体目标。公开 Cached files 文本本身未充分消除计数含义的歧义。

etree：XML 比较、补丁与合并

删除与兄弟新增的合并：不符合本轮规则。出现于 A1。

gold 虽不报告该父子路径冲突，但 applyAddOp 对作为父路径的 /root 再取父节点 /，把 y 追加到文档层而不是 root 内。所提合并树目标不能通过。

节点交换后应用补丁：不符合本轮规则。出现于 A1。

原轨迹 step 66 已实际执行双节点交换的 Diff→GeneratePatch→ApplyPatch，打印重复 id 和 match=false。这属于失败反馈未处理，不是新增组合遗漏。

位置替换后的节点顺序：不符合本轮规则。出现于 A2。

gold 的 LCS 同样把异名节点表示为删除加新增。新增使用父路径，parseAddSelector 返回 -1，结果追加到保留兄弟之后，不能满足所提顺序。

嵌套删除要求恰好一项冲突：不符合本轮规则。出现于 B1。

缺少结构冲突的核心观察成立，但本条明确要求恰好一项冲突。gold detectModifyDeleteConflicts 同时标记父、子两条路径，Merge3Way 随后按每条路径各加入一项，共两项。因此 gold 不满足本条完整预期。我们没有把恰好一项改为至少一项再计成功；旧实验的部分成立标签保持不变。

两侧相同新增后的合并结果：不符合本轮规则。出现于 B2。

相同新增导致原实现重复追加的观察成立。gold 的 opsEqual 会去重，但 applyAddOp 将新增操作的父路径 /root 再取父路径 /，把新增 b 放到文档层，而不是 root 内。因此 gold 仍不能得到本条要求的 <root><a/><b/></root>。

重复属性与相等判断：符合本轮规则。出现于 C1、D1。

原属性比较重复使用同一匹配项，重复 x 可以错误匹配 x/y。gold ElementsDeepEqual 按对应属性逐项比较，该输入返回 false；gold Diff 也从属性表产生新增 y 操作。原轨迹没有将 PreserveDuplicateAttrs 与比较/Diff 联测。

Tengo：闭包调用与实例复制

返回闭包容器后的共享捕获：符合本轮规则。出现于 A1、B2。

Go 调用返回包含两个不同闭包的容器后，原 bindObject 重绑定也拆开共享捕获。gold 返回的闭包保留同一捕获单元。此入口不等同于固定标签要求的跨实例复制/转移。

复制或转移后的共享捕获：符合本轮规则。出现于 A1、A2、B1、C1。

原重绑定对每个闭包分别复制捕获单元，破坏两个不同闭包之间的共享。gold 以 ObjectPtr 为键保留共享关系，同时隔离源实例。原测试只覆盖重复引用同一闭包或不修改的返回闭包。

复制后直接与间接共享捕获：符合本轮规则。出现于 A2。

Clone 一个外层闭包，外层直接读 n，同时调用同样捕获 n 的内层闭包 inc。原重绑定为两次捕获分别分配 ObjectPtr，使 inc 修改后外层仍读 0。gold 的 clone state 对 ObjectPtr 去重，使外层读到 1，且不影响源实例。这不同于轨迹中只调用 inc、不直接读共享 n 的旧探测。观察方式不同于固定双闭包逐次调用，另列同缺陷目标。

目的变量存在但索引不同：不符合本轮规则。出现于 C2、D2。

本条通过目的程序在 g 前声明 x，确实制造了不同索引，较旧的同布局反例更具体。但 gold 也沿用函数字节码，并绑定目的 globals，没有按名字重写索引。因此 gold 也不会返回模型要求的 103。

Go 调用的参数错误格式：不符合本轮规则。出现于 C2、D2。

Go 直接调用的参数数量错误缺少 Runtime Error 包装这一观察成立。但 gold normalizeCompiledFunctionArgs 同样用 fmt.Errorf 返回错误，compiledFunctionEnv.call 直接返回它。因此 gold 也没有所要求的包装与位置。

Tengo：解构与默认值

存在的 undefined 与默认值：符合本轮规则。出现于 A1、A2、B1、B2、C1、C2、D1、D2。

公开需求按键/位置是否存在决定是否执行默认值。原补丁按取出值是否 undefined 判断，gold 检查键或索引存在。已有 undefined 的项与缺失项需分别测试。

未单独观察早期绑定的测试建议：不符合本轮规则。出现于 D2。

该测试最后只观察 c 的事实成立，但原 compiler 对 [1] 依次绑定 a=1、b/c=undefined，并未表现出模型假设的前两个绑定错误。模型也明确说这不是已证明的 mis-binding。它可以支持增强断言，不能支持本轮要求的原补丁失败目标。

kgateway：配置校验与路由策略

小数时长经过配置准入：符合本轮规则。出现于 A1、B2。

原 CRD 正则先拒绝 1.5h 等合法 Go duration。gold CRD 不施加该整数单位限制，运行时 ParseDuration 可接受。原测试直接构造对象，绕过准入校验。

未检查 regexRewrite 的测试建议：不符合本轮规则。出现于 A2。

报告只说假如实现漏接 regexRewrite，现有测试仍可通过，没有指出原 patch 真的漏接。原 buildHashPolicies 已把 h.regexRewrite 和 terminal 放入 header 策略，merge 保留高优先级同名 header 并保留另一个 header。因此它提出了测试强度建议，没有建立原补丁失败、gold 通过的目标。

空配置的默认策略参与合并：符合本轮规则。出现于 B1。

高优先级 consistentHash={} 单独应产生默认 sourceIp；与低优先级 header 合并后，原实现到 apply 阶段才补默认值，因 header 已使列表非空而丢失默认 sourceIp。gold 在 construct 阶段已为高优先级空配置加入默认 sourceIp，随后 union 保留它并加入 header，排序后得到模型要求的两个策略。原测试分别检查空配置 apply、合并后字段，没有联测空配置的构造→合并→最终策略。

空配置、低优先级 disable 与最终策略：符合本轮规则。出现于 B2。

高优先级 consistentHash={} 应贡献默认 sourceIp。原实现把默认值推迟到 apply，合并时先继承低优先级 disable，随后直接返回空策略。gold 在 construct 时创建默认 sourceIp；merge 发现高优先级已有策略后保留它，不继承低优先级 disable。原测试没有联测空配置的构造、继承 disable 与最终 RouteAction。

Awilix：初始化与回滚

无返回值初始化与随后 resolve：不符合本轮规则。出现于 A1、A2。

原轨迹 step 53 已运行不返回实例的 initializer 测试并得到 undefined 失败。step 54 把测试改为 return instance 后通过。因此它是测试弱化/未处理反馈，不是新缺口。gold 虽修复该行为，仍不能计为新组合发现。

经过普通节点的初始化依赖：不符合本轮规则。出现于 A1、A2、B1、B2。

两版都只在直接具有 initializer 的节点之间建立边，均未跨无 initializer 的中间节点计算传递依赖。gold 也不满足所提层级和完成顺序。

子作用域回滚与父对象身份：符合本轮规则。出现于 C1、C2、D1、D2。

原子作用域回滚无条件删除 rootContainer.cache，同时只清除本作用域 SCOPED 初始化标志。父作用域随后得到未初始化的新对象。gold 失败处理只处置当前初始化记录，不删除父缓存。原测试分别覆盖成功作用域和单作用域回滚，未覆盖子失败后的父对象身份。

DynamoDB Toolbox：条件必填

所选分支的正向条件：不符合本轮规则。出现于 A2。

模型要求为所选 anyOf 分支产生正确条件。gold 不遍历 anyOf，因此也不产生该条件。固定 T24-G2 只要求不引入未选分支条件，二者不能混为一谈。

隐藏字段与格式化值 schema：符合本轮规则。出现于 A2。

原 JSON schema 与 Zod formatter 均在移除 hidden 字段后要求该字段。gold 两条路径都只从 displayedAttrEntries 收集条件，所提格式化值可通过。

anyOf 分支失败后的回退：不符合本轮规则。出现于 B1、C1、C2、D2。

模型要求首个分支的 requiredIf 失败后，即使另一个宽松分支可以接受输入，也必须报错。原补丁与 gold 均使用同一个 anyOf 回退循环，捕获失败后允许下一分支。该 parse/anyOf.ts 在两个 patch 中均未修改。所提多分支输入在 gold 也会成功，不能计为差分目标。单分支错误码同样会被包装，不能用它替代固定标签要求的未选分支不得附加条件。

其他更新入口的自动条件：不符合本轮规则。出现于 B1、C1、C2、D1、D2。

updateAttributesParams 确实没有 requiredIf 条件组装。但 gold 与原补丁均未修改该 builder 或其 parseUpdateAttributesOptions；它只合并用户选项与 update 表达式，不调用 updateItemParams。gold 也不产生所要求的自动 attribute_exists，故不符合本轮差分规则。

TanStack Query：持久化状态恢复

空错误与错误计数：不符合本轮规则。出现于 A1、A2。

gold normalizePersisterRestoreState 在 success 状态也将 errorUpdateCount 归零，不会保留模型要求的 4。

返回值与恢复后状态的一致性：不符合本轮规则。出现于 B1。

原补丁返回 marker 的数据，却保留较新的 live 数据，二者不一致。这个核心观察成立。但本条具体要求两者都为 live-data。gold 采用另一方向的修复：直接安装提供的状态，并返回 persisted-data。因此 gold 不能满足本条具体预期。若改为只检查返回值等于安装状态，会形成另一条可能有效的目标；本轮没有替模型改写后计成功。

自定义查询标识与已有状态恢复：符合本轮规则。出现于 B2。

原 bulk restore 仅传 queryKey 给 QueryCache.build；build 先按所传选项计算 hash，再应用 client defaults。自定义 hash 的已有查询未被找到，原实现创建默认 hash 的第二个查询，已有查询保留旧错误。gold 直接按 persisted queryHash 查已有查询，并分别按数据、错误时间合并。因此 gold 保留新 live data 并采用新 persisted error，满足模型所提状态与单一对象预期。原 persister 测试没有自定义 hash；轨迹讨论了该风险，但没有运行这一组合。

延后恢复与较新错误时间：不符合本轮规则。出现于 C1、D1。

两版 lazy restore 的延后回调均把 errorUpdatedAt 写回持久化快照值。gold 也不满足保留更新 live error 时间的所提目标。

默认刷新后的恢复状态：不符合本轮规则。出现于 C2、D2。

默认 refetchOnRestore=true 与陈旧且 isInvalidated=true 的快照会触发后续 fetch，这一源码观察成立。但 gold 同样保留 scheduled callback 和 query.isStale() 后的 query.fetch()。gold 也会在后续成功抓取后清除错误。因此不能要求该快照在默认刷新完成后仍保持错误状态，并将此计为原失败、gold 通过。此目标不同于固定标签的显式 false 标记被原实现错误改为 true。

6. 研究解释与下一步

本轮结果没有证明有限枚举带来增益。C/D 共用计划和查询；D 未新增正确任务，且丢失了 C 第一次在 T13 保留的有效目标。这只是八项开发任务上的观察。由于正式运行没有成功绑定原测试，不能把它推广为程序分析无用，也不能声称完整的“源码推导行为区别”方法已被验证。

把模型前移确实改变了搜索内容。C/D 能找到 T23 的子作用域失败与父缓存的组合，也在第一次找到 T11 的重复属性问题。但它们同时漏掉其他组能发现的目标。这说明建模方式改变了搜索偏好，尚未形成稳定优势。

开发过程可以提供搜索依据，也可能占用搜索范围。T11 的节点交换和混合文本已经失败；T23 的无返回值初始化也已失败，agent 随后修改了测试。带时间线的组通常能识别这些属于已有反馈。但 T11 第二次的 C/D 把两个候选位置都用于已有失败，最终没有继续搜索新组合。记录已有失败有价值，重复报告它不能算新检测成功。

T28 第二次的 B 组提供了一个有价值的新例子。恢复入口遗漏自定义 queryHash，因而创建第二个查询对象。轨迹显示 agent 先考虑过这个风险，后来认为 build 会先应用 client 默认选项，因此删除了 queryHash。实际代码先计算 hash，之后才应用默认选项。这个案例把错误判断、调用方式变化和验证只用默认配置连接起来。它支持继续研究 trajectory 的搜索价值，但单次发现不能证明整体增益。

有些目标在发现后被复核阶段丢弃。T13/D 第一次已经指出复制后共享捕获被拆开，却把跨实例隔离解释成可以破坏同一实例内部的共享。T28/D 第一次已经提出 error 与显式 false 标记，却用现有 reducer 的习惯及原测试取值反推 false 不应出现。原测试的限制正是待检查对象，不能反过来成为排除新组合的依据。

T20 的判断还存在需求解释问题。C 第二次先提出空配置参与合并，以及低优先级 disable 覆盖高优先级策略两个有效目标，最后改读条款而排除它们。gold 支持前面的预期。但公开条款的组合含义需要说明，不能只要求模型更加坚定。来源明确的需求判断与源码效果判断应分别保留。

两个固定目标的持续漏检不能简单归因于缺少代码。T10 输入已经包含 warm-cache 的提前退出及随后的输出调用。T24 输入已经包含调用者的默认 mode=put，以及下游仍读取原 options 的代码。相关文本出现，并不等于程序或模型已经连起控制流和参数传递。程序应给出这些实际关系，而不只展示相邻源码。

当前表示没有完成核心工作。31 个局部模型中，28 个只有一个输入变量。但变量常常代表整个错误场景，例如“是否发生交换”，而不是原程序中的对象、取值或操作。这种单变量表示不证明问题只有一维。16 个模型直接编码成功或失败，14 个给出输入类别与结果表，只有 1 个尝试表示操作的条件计算。枚举这些模型主要重复了模型先前的判断。

适合本场景的研究切入点是 agent 自己选择的验证限制。coding agent 同时修改实现、编写测试、选择入口并解释反馈。这些选择可能相互强化。例如，agent 总显式传入默认参数、只断言中间对象，或为通过测试而关闭后续操作。trajectory 能记录这种限制如何形成。它的研究价值在于指导需要打破哪个限制，而不只是增加背景文本。

下一版可围绕一个问题组织算法：原验证限制了哪个条件，使两种不同的实现效果看起来相同？先从轨迹提取这个限制，再沿修改代码寻找受它影响的输出。模型负责选择有意义的观察和源码边界。程序负责计算该边界内能核对的取值、分支和对象来源。这样可以把模型放在分析前面，又不让模型自行给出的布尔结论充当程序证据。

以 T20 为例，原验证分别检查空配置的默认策略，以及合并后的中间字段。补测应连接配置构造、优先级合并和最终路由策略。程序需要表示“空配置何时变成 sourceIp”以及“何时执行 disable”，再比较最终列表。只返回“空配置与合并有关”没有提供足够信息。

以 T23 为例，原验证没有组合父作用域已有实例、子作用域初始化失败，以及失败后再次访问父实例。程序应追踪缓存条目的所属对象，并定位异常路径删除了哪一层缓存。模型再判断该行为是否违反父实例保持有效的要求。这个表示保留对象身份和操作先后，能够服务多个仓库中的初始化、事务和资源管理问题。

下一步先做小范围的表示检验，不增加任务专用变异规则。对已经冻结的若干目标，检查程序能否从原测试和源码产出具体条件与效果，并正确标明尚未得到的关系。只有该表示成立后，才比较它能否指导模型发现新的组合。当前失败不支持继续扩大自由行为模型的提示词或枚举额度。

学术创新不能只按是否有人使用过程序分析、反例或模型引导来判断，也不能只按仓库场景更复杂来判断。可争取的贡献是利用 agent 的验证选择，推导它没有区分的跨步骤行为，并据此补强测试。这需要一个确实计算该区别的机制。本轮 prototype 尚未实现这一核心证据，不能仅把四阶段流程作为方法贡献。

以上原因来自源码、输入和中间答复的事后核对。它们不是逐项隔离的因果实验。本轮样本小，且均用于过往开发。报告因此保留逐次结果和失败例子，不用最好一次成绩代替稳定效果。
