2. 一个足够集中的软件工程观察

同一个 agent 同时构建补丁和验证。某个简化假设可能同时进入实现和测试。测试因此可以通过，却没有检验这个假设在另一合法上下文中是否仍成立。

这里的关键不是“少测了两个功能”。关键是测试让两个不同的程序事实总是一起变化，或只观察其中一个事实。原验证因而不能说明两者何时会分开。

案例原验证范围需要分开的事实证据边界
T28恢复测试使用普通查询 hash。第 131 步认为 build 会使用客户端默认 hash 函数。创建已有查询所用的 hash，与恢复时查找所用的 hash。轨迹明确提出理由。源码显示 hash 计算早于默认选项合并。
T24requiredIf 的非法输入通过显式 mode='put' 测试。调用者默认化后的 mode，与 helper 收到的 mode。最终测试和源码已经足以提出该问题。不能将它算成轨迹独有收益。
T13跨实例测试搬运同一个函数的两处引用。另一测试验证两个不同函数共享捕获单元。函数对象相同，与不同函数共享同一捕获单元。第 104 步明确讨论副本内部共享。Go 语法分析不能直接证明字符串内 Tengo 的捕获关系。

我们不把这个模式解释成“agent 只追求 coverage”或“agent 忘记需求”。现有记录不能支持这种因果判断。方法使用可核对的测试限制、代码修改和推理主张。

3. 研究对象：一个可执行的区别目标

搜索单位不是函数对，也不是任意参数组合。搜索单位是一个待检区别。每个区别只绑定一项原验证、两个可记录的程序事实、一个可修改位置和一个公开观察。

h = (原验证及证据, 事实 a, 事实 b, 关系 R, 可修改位置, 公开观察)

例：
原验证：显式 mode='put' 的 requiredIf 测试
事实 a：itemZodParser 的局部 mode
事实 b：withRequiredIf 收到的 mode
关系 R：a == b
可修改位置：parser 调用的配置参数
公开观察：缺少 requiredIf 字段时是否报错

“记录点”指源码中读取一个已求值结果的位置。它可以读取参数、局部变量、对象身份或已执行分支。记录点不能仅是模型生成的一句行为描述。

首版只比较基本值、对象身份和已有布尔事实。值相同不表示对象相同。对象身份必须来自同一次运行的标识。集合关系和复杂时序逻辑先不加入通用语言。

对种子测试 t，程序先核对两个事实是否确实被观察。只有关系实际成立，才能说原测试验证了这一受限情况。未进入分支、空容器没有触发递归、记录失败，都不能当成关系成立。

已观察的受限情况：R(a(P, t), b(P, t)) = true

搜索目标：找到合法 t'，保留相关操作，且
R(a(P, t'), b(P, t')) = false

这里的 P 是原 agent 的最终补丁。关系分开只说明原验证不足以支持该关系的推广。它还不说明补丁错误。公开需求必须支持最终断言。

“两个事实”也不表示“只有两个输入维度”。T13 的共享、传递、读写可以共同决定一个身份区别。程序关系的数量可以大于二。首版不宣称已解决任意多关系搜索。

trajectory 的作用需要单独归因

来源具体含义可以支持的主张
A：明确理由原记录明确给出有关实现或验证的理由。T28 的 hash 判断属于此类。轨迹提供了需要挑战的具体命题。
B1：历史新增信息测试修改、入口替换或执行版本暴露了最终测试看不出的限制。轨迹恢复了验证范围如何改变。
B2：最终测试已有信息只读最终测试就能发现范围受限。T24 的显式 put 属于此类。原验证能指导搜索。不能据此声称轨迹有独立收益。
C：程序推导区别来自最终源码，历史记录没有增加证据。可作为统一方法的目标和不带轨迹的对照。

这些标签描述目标的证据来源。它们不直接决定目标正确与否。同一个任务可以有多个来源不同的目标。

4. 算法如何实现

4.1 程序先提供可选择的位置

程序解析补丁修改的函数、能直接解析的调用者和被调用者，以及相关原测试。它提取参数、赋值、调用结果、分支和断言的位置。每个位置携带 node_id、文件路径、文件校验值、字节范围和原代码。

程序通过测试文件修改和执行命令关联 trajectory 步骤。它保留测试创建、修改、运行和之后的实现修改。只有名称相近时，它只把记录当作检索线索。

模型需要额外 helper 或 wrapper 时，可以请求其源码。首版允许少量补充查询。初始邻域只是检索起点，不是证明“邻域外没有相关行为”的边界。

程序不需要为每项测试建立完整的语义记录。它先提供位置目录。只有模型选中的少量目标需要记录执行值。局部变量或回调不能静态求值时，候选仍可进入执行检查。

4.2 模型提出目标，不建立整套语义表

模型读取原需求、局部代码、原验证和关联步骤。它返回最多两个目标。每个目标必须选择目录中的 node_id 和已有 step_id。若来源是 B2 或 C，模型必须明确标注。

{
  "source": {"kind": "A | B1 | B2 | C", "step_ids": [...], "test_id": "..."},
  "facts": {"left": "已有位置 ID", "right": "已有位置 ID", "relation": "value_equal"},
  "edit_root": "原测试的一个输入或观察位置 ID",
  "observation": "公开结果位置及需求出处"
}

程序核对 ID、文件版本和位置。它还核对可直接确认的参数绑定和局部使用关系。程序不把“ID 存在”当成行为解释正确。

模型不填写 current_expr、required_expr、feasible_expr 或完整真值表。前次 31 个行为模型均缺少完整的原测试输入绑定。新设计将这项负担改成选择少量实际位置，再通过执行取得值。

目标选择优先保留与修改位置相连、能指出具体原测试限制的候选。A/B1 作为轨迹特性的独立组记录。最多两个目标只是首轮 pilot 的预算，不是已经优化的最佳数量。

4.3 单步操作：局部改变测试，并记录区别

一个搜索状态包含当前测试、固定区别目标、执行记录和已做修改。一次扩展只改变一个输入构造，或增加一个结果观察。它可以删除显式配置、复用同一对象，或增加已有返回值的断言位置。这些是例子，不是不断增长的任务规则表。

可用表达式优先来自仓库现有测试和公开 API。模型也可以提出新的局部表达式。程序不要求所有实参静态闭合。它通过实际执行检查输入是否成立。

程序限制修改范围，并核对已知绑定。例如，T28 的创建和恢复必须使用同一个 client 与 queryKey。仅有相同变量名或相同字符串，不足以证明两次操作关联到同一对象。

原断言的期望值不能自动搬运。T17 将输入改成显式 undefined 后，原来的期望值 5 或 2 不再适用。模型需要根据公开默认值语义确定预期。搜索阶段只记录事实，不从原补丁输出反推期望。

for h in 已定位目标:
    baseline = 执行并记录(h.原测试, h)
    先处理已有失败、错误预期、漏选测试和缺少观察
    frontier = [h.原测试]
    for round in [1, 2]:
        edits = 提出最多3个局部修改(frontier, h, 实际反馈)
        records = 执行并记录(edits, h)
        优先保留真正形成目标输入、到达记录点、分开两个事实的候选
        if 存在契约支持的错误观察:
            去除记录代码，独立运行最终测试
            保存测试与证据
            break

每轮总共最多三个提案，不是每个候选再展开三个。每个目标最多六次候选执行，另需种子和最终测试执行。失败的尝试也消耗预算。这个上限用于控制首轮研究范围，不表示已经证明最有效。

4.4 执行反馈必须回答具体问题

反馈下一步
测试无法建立输入修正局部夹具或调用。不能报告没有缺口。
目标入口没有执行根据实际提前返回或调用路径调整输入。
只读到一个事实核对对象、调用和阶段。不能将缺失记录解释成 false。
两个事实仍一致保留已到达的路径，改变隐藏区别的输入。
两个事实已分开检查公开结果。关系分开本身不是 bug。
提前退出或超时阻止公开结果若目标输入已形成，按公开契约审核该退出。不能机械丢弃。

搜索优先比较“是否真正到达”和“是否已分开”。它不为字符串、对象或复杂语义发明连续距离。模型根据具体值和分支反馈提出下一次局部变化。

4.5 记录实现必须保留程序语义

记录器读取已经求值的参数、局部变量、赋值结果或分支事件。它不再次调用被测表达式。否则，记录本身可能改变状态、异常或执行次数。

基本记录包含测试 ID、代码版本、调用阶段、源码 ID、值的种类和实际值。对象使用运行内身份标识。undefined、null、缺字段和无法读取必须分别表示。

程序按同一次测试和相应调用关联记录。T28 中，创建查询和恢复查询是不同调用，但必须属于同一 client 和逻辑 key。无法消除多次调用歧义时，程序报告未绑定。

TypeScript 可以在已有赋值后或函数入口记录局部值，并在分支入口记录事件。它不能任意包装方法调用并改变 this。Python 可复用现有按行记录能力。Go 和嵌入语言需要各自适配。现有实现尚未提供这些完整能力。

最后一次验证使用不含记录代码的测试。记录帮助搜索，不能成为测试通过或失败的必要副作用。

5. 两个完整示例

T24：检验默认值是否真正进入 helper

原测试构造 requiredIf 规则：type 为 a 时，details 必须存在。它将缺少 details 的输入交给 parser({mode:'put'})，并断言抛错。

调用者执行 const { mode = 'put' } = options。它随后把原 options 传给 withRequiredIf。helper 再从 options 读取 mode。原测试使两个位置都得到 put。

目标固定 schema、非法输入和 parser 调用。局部编辑只把 parser({mode:'put'}) 改为 parser()。

输入调用者 modehelper mode需要检查的公开结果
显式 putputput缺少 details 时抛错
省略 modeputundefined默认入口是否仍执行相同 requiredIf 约束

表中的值来自本轮静态源码推导。它们不是新运行的探针结果。实现后必须实际记录这些值。

这项搜索改变一个输入位置，就能检验跨函数默认化关系。它不需要枚举所有 mode 与所有 schema。公开默认模式和 requiredIf 契约决定错误预期。

该例支持“原验证驱动的区别搜索”。最终测试已显示显式 put，所以该例不能单独证明 trajectory 的额外价值。

T28：检验删除 queryHash 时使用的理由

第 131 步认为 build 会使用客户端默认选项中的自定义 hash 函数。agent 据此删除传入的 queryHash。原测试仍使用普通 hash，所以没有检验这个区别。

源码的实际顺序是：先根据传入 options 计算 hash，再查缓存；创建新查询时才调用 defaultQueryOptions。程序可以直接定位这些步骤。记录这两个 hash 后，搜索就有明确目标。

候选保留同一个 client、queryKey、已有查询和恢复操作。它把客户端构造改为仓库已有的自定义 hash 配置。搜索比较“创建已有查询时的 hash”和“恢复时查找的 hash”。

若两个 hash 分开，程序继续检查恢复是否更新原查询，以及缓存中是否产生另一个条目。正确预期来自同一客户端配置下的恢复语义。它不来自某一条实现路径的输出。

这里 trajectory 确实增加了信息：它指出 agent 为什么删掉一个参数，也给出需要挑战的具体理由。对照实验仍需检验，这个线索能否稳定超过只读最终代码和测试。

6. 首版边界与现有代码的改动

首版应先支持能直接读取参数、局部值、对象身份或分支的目标。T13 和 T17 是重要扩展案例。若程序不能把 Tengo 的运行语义接到 Go 记录点，就必须标记未支持。不能把模型解释当成程序已确认的事实。

T10 还提醒我们，控制测试必须实际到达相关行为。带 mock、但不请求 JSON 的 warm-cache 测试，不能证明真实 CLI 的 JSON 输出关系。方法需要一个实际 CLI 控制；找不到时，应报告控制尚未建立。

接口可复用部分需要实现的变化

catalogue_source_nodessyntax.py、program.py、relations.py提供可选择的位置和局部绑定。允许未知值继续进入执行。

研究核心不再依赖持续增加的候选类别，也不要求所有输入先被静态求值。旧类别可用于描述结果。旧生成与执行工具可以复用，但它们不自动构成新机制的有效性证据。

机器可读规格明确列出输入、搜索状态、单步操作、记录格式、终止条件和模块接口。以上是实现设计；本轮实际代码改动集中在统计修订和报告更新。

7. 可以主张什么，尚不能主张什么

候选贡献是把 coding agent 的验证限制变成可执行的反例目标。trajectory 用于解释目标从何而来。程序分析将目标接到具体值、对象和调用。执行反馈决定目标是否真的形成。模型在目标提出和局部构造阶段参与，而非只在末尾判断。

本轮主张的新意不在于首次使用变异、切片、模型或运行反馈。我们要验证一个更具体的问题：针对原 agent 未区分的事实进行搜索，能否比一般生成更稳定地得到正确组合测试。

仓库级 issue resolution 包含跨模块调用、状态寿命、测试辅助函数和版本变化。trajectory 记录 agent 如何选取验证范围。这是方法需要利用的场景信息。其他工作出现相似组件，不足以直接否定这一研究方向。

但命名一个区别目标也不足以建立贡献。若模型选的两个位置无法执行绑定，或加入记录后不提高有效测试产出，这个机制就没有得到支持。若收益都来自 B2/C，论文应把核心写成验证驱动搜索，并将 trajectory 降为可选信息。

旧探索已经给出具体警告。上下文扩展和测试类比已尝试过输入与观察的迁移。后来过强的静态地址匹配又使 85 个候选调用得到 0 个匹配。前次八任务 pilot 也没有显示附加轨迹文本的稳定收益。这些结果要求新机制改变可核验的搜索目标，不能只扩大提示材料。

先检验核心连接，再投入更广的执行系统

第一步只检验目标提取。对任务盲提取最多两个区别。输入仅包含 issue、原补丁、原验证和 trajectory。审查目标是否来自真实材料、能否定位两个事实、是否有非空控制，以及是否属于 A/B1/B2/C。

第二步在可绑定目标上比较一次直接生成与运行反馈搜索。两组使用相同目标、相同代码、相同候选数和总模型预算。这样才能判断反馈是否改变测试质量。

另一个对照固定最终代码和测试，只改变有无相关 trajectory。加入无关轨迹作为负对照。目标发现率和正确测试数必须分开报告。

错误检出必须有公开契约支持。gold 和 benchmark 失败测试只进入离线评价。动态执行确认的“原补丁失败、gold 通过”，与静态语义推导的同类判断必须分开记录。两者使用不同的证据等级，不能合并称为执行成功。实际 resolution rate 仍需另做 agent 修复实验。

8. 独立讨论如何改变了方案

独立线程没有继承历史对话。它收到问题定义、原型目标、实现路径和已有正负结果，并可继续读实验数据。它知道本项目追求 simple yet effective，不需要覆盖所有场景。

被提出的方案实质质询结果
独立线程：按对象端口拼接已有测试片段。项目已做上下文扩展和测试类比。新方案没有说明 trajectory 如何改变搜索。输入变化也会使旧断言失效。独立线程撤回它作为本轮新核心。
主线程：恢复验证替代时丢掉的区别。恢复旧测试常得到已知失败、错误预期或复验问题。它也不能解释所有有效组合。双方只把测试替代当作目标来源。
独立线程：用真实运行量检验局部等价假设。需要处理身份、已有分离和无法静态求值。没有显式理由的任务也可能有可用验证限制。双方接受少量可记录事实和局部搜索，并明确不支持的子类。
主线程：允许从历史操作和测试范围推导目标。最终测试已有的信息不能算轨迹独有贡献。空路径不能构成控制。双方加入 A/B1/B2/C 归因和实际到达检查。

最终共识不是“已经找到有效新算法”。共识是一个集中的、可实现和可否定的研究候选：用原验证留下的具体区别指导反例搜索，并通过执行核对目标是否真实发生。

独立审阅仍保留两个主要疑问：可绑定目标是否足够多，以及目标反馈能否超过相同目标下的直接生成。我们没有用讨论代替实验回答这两个问题。
