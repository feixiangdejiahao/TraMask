十二任务 pilot：验证改动、诊断执行与组合补测

2026-10-16。12 项已研究任务。主实验 4 组，反馈表示对照 1 组。每组重复 2 次，共 120 次任务运行。

本轮扩大了案例数和候选数。模型可以提出假设、查阅程序、设计诊断、生成补测，并根据执行结果修正一次。程序自动恢复历史测试、保存版本差异、提供局部语法信息，并执行测试。

结果支持继续研究“原验证没有区分哪些行为”。结果尚未支持把“增加历史文本”或“加入诊断执行”作为稳定有效的核心贡献。诊断执行减少了一些错误报告，也曾使模型撤回正确目标。

下一步应集中检查一件事：历史验证中需要区分的条件，是否真正保留在新测试的输入、操作和最终观察中。程序应给出可核验的值、对象身份和执行顺序。LLM 负责提出这个区别，并选择要查证的部分。

1. 本轮要回答什么

coding agent 已经根据 issue 修改了项目，并写过或运行过验证测试。我们在提交补丁前补充验证。目标不是让测试数量增加，而是找到合法条件的组合，使原补丁的问题可以被观察到。

本轮将研究问题写成：agent 在局部验证中把哪些不同情形当作同一种情形？历史测试的修改能否帮助发现这种混同？实际程序观察能否帮助构造揭示区别的测试？这些问题适用于有多个文件、多个入口和多步开发记录的 issue resolution。

例如，T13 的原测试把同一个闭包放进两个容器。这个输入不能区分“同一函数的两个引用”和“两个函数共享同一捕获变量”。需要补测的关系是共享状态在转移后的保持。它不是函数调用覆盖率。

3. 四个效果指标如何计算

正确检测：模型明确提出一个合法的组合目标。需求或接口语义支持预期。语义分析或执行证据支持存在测试，使原补丁失败且 gold 通过。单个非法参数、已有联合测试未运行、错误预期，分别处理，不自动算组合缺口。

正确补测：模型实际交付的最终测试建立了关键条件，并观察正确对象和结果。原执行必须揭示目标问题。gold 侧可以采用动态比较或静态语义判断。我们不替模型修正测试后再计成功。

误报：模型声明 gap，但该肯定报告被本轮修复相关标准否定。原因可以是错误预期、条件未建立、原补丁已满足，或 gold 也不能通过。最后一种情况不表示报告的通用缺陷一定不存在。证据不足的 3 项另列为未定，不算成功或已证实误报。

漏检：计算未命中的 7 个事先固定目标。它们位于 6 项任务：T06 路由复制、T10 预热与 JSON、T13 共享捕获、T17 存在性与默认值、T24 默认解析模式、T24 分支选择与条件规则、T28 错误快照与框架挂载。这个分母不是全部可能缺陷。未设固定目标的任务也不是无缺陷负例。

下表的检测、补测和误报以任务计数，每次分母为 12。漏检以固定目标计数，每次分母为 7。同一次任务可以发现正确目标，同时报告其他错误目标，所以成功任务与误报任务允许重叠。格式失败仍保留在任务分母中。

6. 哪些观察改变了问题理解

T13：同一个对象不等于共享状态的不同对象。历史测试把预期从 151 改为 152。改动保留了同一闭包的共享状态，却没有覆盖两个不同闭包。B 找到这个目标但排在第二；C 将它排在第一。当前数据与历史材料有用的解释一致，但不能仅凭一个案例证明因果。

程序恢复了这段原始 diff。但是结构化的赋值、调用和检查差异栏全部为空。关键变化位于 Go 的 if 条件，后面调用 Fatal。当前提取器没有将这种惯用检查表达为期望变化。这是表示缺陷，不是原始文本缺失。

T13：完成执行不等于满足行为要求。诊断打印 inc=3、get=2。它只记录数值，没有断言，所以框架报告通过。D 第一次运行随后撤回共享捕获目标。E 使用相同诊断结果后保留目标，并生成失败见证。第二次重复中，D 和 E 都成功。这个对照支持反馈解释影响决定，但证据仍只覆盖一个有效变化。

T17：断言读取了另一个值。错误测试执行 out=a，随后执行 out=len(rest)，最后要求 out=9。实际最终值为 0。模型把失败归因于编译器栈和默认值处理。D 和 E 都保留了这个错误。只改执行报告的表示不能修复观察对象错误。

T28：模型声明的输入没有进入程序。多个候选声称持久化失败次数为 5 或 3，但 errorState 固定写入 2。另一测试把 Error 对象放进 JSON，message 在序列化时丢失。模型随后把缺少 message 当作恢复逻辑缺陷。这些失败要求检查输入构造及其转换。

T29：必须追踪同一对象和实际操作序列。有些测试每次调用谓词工厂，得到不同实例，却期待复用查询历史。另一些测试只迭代健康实体，却期待修改未进入循环的不健康实体。程序关系必须绑定具体对象、集合成员和调用次序。

T29：被删除的测试不自动成为正确目标。trajectory 记录了删除 entity.set 回调测试的请求。C 确实重新探索这条路径。但生成的控制测试和 gold 都失败。删除记录可以指引搜索，不能充当正确性依据，也不能直接当成新的输入缺口。

把一个候选撤回后再加回，也可能触发当前严格 ID 检查。这一工程限制会低估可用内容。下一次独立实验应由程序持有候选身份，并把候选结果分开接收。这个修正本身不构成论文贡献。

程序的 slice 查询只提供局部参数、赋值、调用及外层条件。它没有证明跨函数别名、完整控制可达性或运行时值。当前“条件清单”仍是模型生成的文字，程序尚未验证清单中的条件。这一点限制了本轮对程序分析作用的结论。

所有语义判断由本 Codex 线程逐项完成，依据需求、源码、两个补丁和执行记录。没有独立人类标注者。我们把动态证据和静态判断分开报告，保留完整记录供复查。

8. 收敛后的研究抽象与算法方向

研究对象：验证所依赖的区分条件。agent 常在局部上下文中获得通过结果，随后据此接受更广的补丁行为。我们要发现这个推断依赖了哪个尚未验证的条件。条件可以是对象共享、字段存在性、恢复入口、更新顺序或实际观察对象。它不需要预先限定为一条程序边的两端。

集中机制：让一个行为区别贯穿搜索。每次搜索只维护原验证、待区分条件及最终观察三项内容。trajectory 用来提出原验证为什么可能混同两个情形。程序用来核对这两个情形是否在输入和执行中不同。LLM 根据证据选择下一次查询或局部测试修改。

步骤LLM 的职责程序的职责可检查的产物
确定区别从历史验证改动和 issue 中提出两个不能混同的情形；指出依据。对齐测试版本；保留输入、操作、控制条件和断言的源码位置。原验证检查了什么；新情形改变哪一个条件。
核对条件指出哪个对象、值或操作能区分这两种情形；选择查阅或小型诊断。从输入构造向前跟踪关键值，从最终断言向后跟踪观察值；有歧义时记录实际值、对象身份和先后顺序。条件是否真的成立；变化是否传播到观察点。
补强验证保持需求支持的预期，生成最小组合测试；根据证据修改未成立的条件。执行测试；分别报告输入条件、实际结果和框架状态。可重放的失败见证，或明确的撤回理由。

这个设计允许 LLM 进入程序分析过程。模型先指定需要核对的语义关系，程序再执行局部查询或收集运行时证据。程序不需要先建立整个项目的精确模型。模型也不应仅凭函数名称推断关系已经成立。

例如，对 T28，程序需要报告“传入恢复函数的 count 实际为 2”，而不是只报告 errorState 调用了 restore。对 T17，程序需要报告“断言读取的 out 最后由 len(rest) 写入”。同一个值来源与观察来源机制可以处理这些问题，无需为每个案例添加专用规则。

创新性边界。单独增加 LLM 阶段、查询工具或测试执行，不足以形成核心贡献。值得继续验证的信息利用方式是：从 coding agent 自己的验证改动中提出尚未验证的行为区别，再用程序中的值、身份和时序核对这个区别。贡献是否成立，取决于它能否稳定减少无效搜索，并增加真实错误检出。

上述机制是下一步的研究假设。当前实现只完成历史版本恢复、局部查询和执行对照，没有实现完整的区别保持检查。我们不把本轮成绩归功于尚未实现的机制。
