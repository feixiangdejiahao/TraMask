自动补充验证测试：DeepSeek 小规模实验完整报告

实验日期：2026-10-05。报告重写日期：2026-10-06。本文沿用已保存的实验数据。此次只重写说明，没有重新调用模型或运行实验。

本实验检查：智能体完成补丁后，能否自动找到原测试漏掉的条件组合，并生成测试补上这些检查。方法先用程序分析收集测试和开发记录，再让 DeepSeek 判断缺口、编写测试计划并生成代码。

主要运行生成了 78 个可执行的新测试。审查支持其中 56 个测试的全部输入和期望。41 个测试增加了原测试没有检查的条件组合。4 个测试稳定失败，涉及 2 类实现错误。

评价者在生成前写下四项原测试遗漏的检查：流解析异常后的关闭、数据库更新违反约束、快捷键附带文本，以及递归解析中的值转换。模型没有收到这份清单。两种输入都只重新找到数据库更新这一项。

完整自动流程结束后，评价者另行直接提供具体测试计划。模型据此为流关闭和快捷键两项遗漏生成了揭示错误的测试。这两次成功不计入自动流程成绩。

这些结果支持优先改进“确定要补测什么”。提供开发记录的一组生成了更多有效组合测试，但没有找到更多事先指定的遗漏检查。

本文报告一次完整自动流程的小规模实验。此前另有一次使用手选测试和手选开发步骤的实验。两次实验的材料选择、调用次数和结果不同。本文不合并它们的成绩。前一次实验见手选材料实验报告。

下文称这些 AI 分析助手为“评价者”。它们是本次工作的编程与分析助手。它们不是生成新增测试的 DeepSeek，也不是独立真人评审。

研究问题：测试通过，为何仍可能验证不足

智能体可能分别测试两个功能，却没有测试它们同时发生的情况。例如，一个测试检查非法 JSON 会报错。另一个测试检查流正常读完后会关闭。这两个测试都通过，仍不能说明“流尚未读完就解析报错时，响应是否关闭”。

本文把这类遗漏称为组合验证缺口。它必须对应任务需求或已有接口约定。两个功能在同一个测试中出现，也不一定足够。测试还需要让它们作用于同一相关对象，并检查联合操作的结果。

一个简单的例子是数据库约束。若测试更新的是姓名，却只检查总行数不变，它就无法判断姓名约束是否生效。有效补测需要让更新改变约束的真假，再检查程序是否拒绝修改。

验证缺口描述测试缺少什么。程序缺陷描述实现违反了什么要求。补上缺失检查后，测试可能通过。这仍可能增加有效验证。只有期望正确的新测试在补丁上失败，才提供程序缺陷的证据。

开发记录可以说明智能体读过什么、改过什么，以及运行过什么。我们希望利用这些事实，确定哪些要求尚未落实为有效测试。记录本身不能证明智能体为何遗漏它们。

当前问题抽象：缺少的是哪一项具体检查

我们把待检查的关系写成一个具体问题：在某个代码版本上，对哪个对象，同时满足哪些条件，执行什么操作，应检查什么结果。期望结果需要有需求或接口依据。只记录“两个函数同时出现”，无法回答这个问题。

例如，N04 需要对同一个数据库和表注册姓名约束，再执行会违反该约束的更新，最后检查程序是否拒绝修改。注册约束和更新若作用于不同数据库，就没有测试这个组合。只更新姓名并检查行数，也不能测试姓名约束。

当前程序只能恢复其中一部分关系。它能找到相关测试、调用名称、结果检查和开发步骤。它不能可靠确认全部对象关系和条件影响。因此，当前实现仍让模型完成关键判断。这是算法的主要限制。

本实验选了哪些任务，如何事先确定评价范围

本实验使用六份已完成补丁的开发记录，来自五个项目中的五个开发任务。N01、N04、P1、P2、P5、P7 只是用于对应文件的案例编号。字母不表示有缺陷或无缺陷。P1 和 P2 是 Textual 同一任务的两次不同开发运行，补丁和过程记录不同。

这些任务来自已有研究记录。本次工作的 AI 分析助手此前已经研究过其中的缺陷和验证不足。我们按已知问题选择案例，用于检查方法是否可行。这是对已知问题的再发现实验，不是随机抽取新任务的性能评估。

在本轮生成任何新测试之前，分析助手依据原需求、原测试和已有开发记录，写下四项遗漏检查。它们分别属于 N01、N04、P2 和 P7。我们用这四项检查评价方法是否重新找到已知缺口。下表给出每项检查的具体内容。

这四项参照描述测试缺少什么。它们不表示每个案例的所有测试都有问题，也不表示补丁一定有错误。下表说明原测试和遗漏检查的区别。

案例与开发任务原测试已经检查什么评价时要求方法重新找到什么
N01 · HTTPX（Python）。为 HTTP 响应增加逐项读取 JSON 的功能。一个测试检查内存中的非法 JSON。另一个测试检查流正常读完后关闭。让尚未读完的流出现非法 JSON。检查解析报错后，同一个响应对象是否关闭。
N04 · sqlite-utils（Python）。增加安全写入模式。数据必须满足用户注册的约束，失败时撤销修改。一个测试检查插入数据违反约束时失败。另一个测试检查批量 UPDATE 成功，但没有注册约束。先注册约束，再用合法的 UPDATE 破坏该约束。检查命令是否报错，并恢复修改前的数据。
P2 · Textual（Python）。完善终端键盘协议，正确区分快捷键和文字输入。分别检查没有附带文本的快捷键，以及只报告文本的事件。同一按键事件同时包含 Alt 等修饰键和附带文本。它仍应表示快捷键，不能被当作文字输入。
P7 · Valibot（TypeScript）。让数据检查规则支持递归树，并能与数据转换一起使用。运行测试组合了递归树和 readonly 操作，并检查输出等于输入。readonly 本来就不改变实际数据。另有测试只检查转换前后的类型。在递归数据检查中加入真正改变值的转换。实际解析至少含一个子节点的输入，并按转换的具体位置检查结果。

例如，评价者为 N04 事先写下的目标是：“注册姓名约束，再把姓名更新为违反约束的值，并检查拒绝与恢复。”方法需要从原材料自行提出这项检查。只有加入其他数据库测试，不算找到这个目标。

N01 的异常后关闭预期，来自本次评价对“流式 JSON 迭代应关闭响应”这一需求的解释。原需求没有逐字列举解析异常路径。报告沿用事先保存的这一判断，并明确其解释边界。

N04 的原开发记录还包含“注册行数规则，再更新姓名”的验证脚本。两种操作已经同时出现，但更新姓名不会让行数规则失败。因此，本次要找回的是会真正违反规则的更新检查，不能把问题简单描述成从未组合这两个功能。

P2 中的“附带文本”指终端在按键消息中另外发送的文字。它与键码、Alt 等修饰键属于同一条消息的不同字段。本次目标使用非零的按键编号，例如字母 a。编号为 0 的纯文本消息属于另一个情况。

P2 的任务要求字符键与 Alt、Ctrl 等键组成的快捷键保留快捷键名称。这些组合也可以同时包含 Shift。事件的 character 字段表示可输入字符。该字段此时应为 None，即没有可输入字符。

P7 中的“数据检查规则”对应代码里的 schema。它描述节点字段和子节点结构，也可以包含数据转换。pipe 按顺序组合检查和转换。本案例中的 readonly 只改变类型层面的只读说明；transform 才会执行给定函数来改变实际值。

P7 事先指定的检查没有限定转换必须放在整个节点之后。它要求实际观察递归输入中的值变化，并按转换位置确定正确期望。后文直接提供的“整个节点之后进行转换”是一个具体补测方案，不是事先参照的唯一形式。

我们还选了两项已经由原测试联合检查的行为。它们用于检查方法是否会误报“缺少联合验证”。评价只涉及下表中的具体行为。一个案例仍可能在其他行为上存在缺口。

案例与开发任务原测试已经联合检查的行为本次为何加入这个案例
P1 · Textual。与 P2 是同一开发任务的另一次运行。同一按键消息包含 Shift、重复按键阶段、附带文本和替代键码。原测试检查解析后同一个事件的多个字段。检查方法能否识别已有的联合验证，避免再声称这些字段只被分开测试。
P5 · Tengo（Go）。让 Go 程序调用脚本函数，并正确处理函数状态和返回值。原测试从脚本变量读取嵌套容器，从容器中取出函数，实际调用它，并检查返回值。检查方法是否误把这条已测试的调用路径说成缺口。函数调用后返回容器属于另一条路径，需要另行判断。

Tengo 中，Get 用于读取脚本中的变量，Call 用于实际执行函数。P5 的原测试已经完成“读取容器、取出嵌套函数、调用并检查返回值”这一整条操作。它不能代表所有函数返回值和跨实例调用场景都已测试。

上述四项遗漏检查和两项已有检查只供评价使用。自动程序和 DeepSeek 不读取这份清单。程序也不接收分析助手手选的开发步骤。实验结束后，分析助手再对照清单评分。模型发现表外的缺口时，我们另行记录。

本报告中的评价工作由本次工作的 AI 分析助手完成，包括阅读代码、编写评价参照及审查测试。它们知道已有案例，也参与了方法实现。这不是独立真人专家的盲评。后文“直接提供测试计划”的计划也由分析助手整理。

实际运行的方法

步骤谁完成读取什么产出什么
1. 选择待检查的原测试普通程序提交补丁和仓库测试。一组与修改相关的原测试。此时尚未确认缺口。
2. 收集相关材料普通程序原测试、相关实现和开发记录。A 组的当前代码材料，以及 B 组额外使用的公开开发步骤。
3. 判断遗漏并写计划第一次 DeepSeek 调用对应组的材料。已有检查、信息不足或具体遗漏的判断。若有遗漏，再给出补测计划。
4. 编写新测试另一次 DeepSeek 调用同一组材料和已经保存的计划。只含新增测试的代码。普通程序检查结构后写入文件，保留原测试。
5. 执行与评价项目测试工具和评价者固定补丁、原测试、新测试、需求及接口约定。实际通过或失败的结果，以及输入、期望和新增检查是否有效的评价。

前四步构成待研究的自动方法。第五步中的测试执行也是自动操作。评价者核对测试期望属于本次实验评价；当前方法没有自动完成这项核对。

第一步：程序选择可能需要补测的原测试。程序读取补丁提交状态下的源码。它选择被补丁修改的测试，以及分析认为可能直接或间接调用到修改代码的测试。若只能匹配到同名函数，程序也保留该线索，但标记为无法确认。这个步骤只分析代码，不调用大模型。

可供生成使用的原测试来自此前保存的测试索引。这个索引有范围限制，没有穷尽整个仓库。程序在源码中另行识别到的测试会进入材料清单；若它们没有对应的执行设置，就不能直接成为本轮生成的起点。因此，284 个候选不代表对全仓库测试的穷尽筛选。

候选来自提交状态中的仓库测试，既可能是智能体新增或修改的测试，也可能是与补丁有关的已有测试。程序选择它们，是为了让模型进一步检查。选择本身不表示这些测试确实存在组合缺口。

第二步：程序收集相关材料。它提取完整原测试、相关实现代码、函数调用和结果检查。它按文件路径和函数名关联开发记录，保留相关公开步骤及能够恢复的旧代码。仅凭名称关联，仍可能带入无关材料。

第三步：DeepSeek 判断并写测试计划。模型先说明自己评估的是哪一项行为，再判断它属于“缺少检查”“已有检查”还是“信息不足”。它不能只给整个任务贴标签。若模型找到缺口，它最多为每批测试提出两项补测计划。

每项计划需要说明：原测试已检查什么；还缺什么条件组合；怎样构造合法输入；操作和观察是否针对同一对象；执行哪些操作；应看到什么结果；期望依据是什么。例如，N04 的约束注册、UPDATE 和最终查询必须针对同一个数据库和表。

第四步：DeepSeek 把计划变成测试代码。这次调用读取原材料和已经保存的计划。模型以选中的原测试为参考，返回一个新测试。程序检查代码结构和导入来源，再用不同名称把新测试写入测试文件。

生成时，模型保留测试框架识别该测试的定义部分，包括函数名和参数。它可以改写测试内部代码。程序接受后，再为新增测试另取名称。原测试继续保留。

写入测试的程序只检查代码结构、导入来源和修改范围。它不判断测试期望是否正确。这项判断由实验评价中的逐项审查完成。

程序保留完整原测试。同次执行原测试和新增测试，有助于判断新增失败是否只来自基础环境问题。保留原测试不会自动保证新增测试没有误报。

Python 和 Go 新测试使用原测试已有的导入与定义。TypeScript 可以增加从原仓库确认存在的导入。模型不修改产品代码。模型也不接收本轮失败日志来重新修改测试期望。

本轮对已经完成的补丁执行原测试和新增测试。我们没有重新让开发智能体逐步重演整个开发过程，也没有让它根据新测试修改补丁。因此，本轮结果回答的是测试补强能否发现问题。

以 N04 为例，程序先找到更新测试、约束测试和相关实现。模型再判断需要让更新破坏已注册约束。另一次模型调用生成该测试。程序运行原测试与新测试。评价者最后核对输入、全部断言和失败日志。评价者的核对不属于自动发现算法。

当前方法的学术新意及其证据

我们希望研究的是开发完成后的验证遗漏。方法需要结合原测试、实现关系和开发过程，确定一项有依据的联合检查，再生成测试。这个研究目的可以区别于仅扩大输入数量的测试变异。

程序分析、测试变异和大模型生成都是可复用的技术。使用相似技术本身不能否定新意。论文需要说明：这些技术在本问题中恢复了什么关系，以及这些关系为何能改善测试补充。

当前实验尚未证明一项新的有效关系分析算法。关键缺口仍主要由模型判断。10 个参照测试都与补丁改动重叠，也削弱了复杂分析带来额外收益的证据。现有结果支持研究方向，不能单凭流程组合宣称算法创新。

三次互不传递结果的请求：对每一批、每一种输入，流程尝试三次。每次先调用模型判断，有可处理的测试计划才继续生成代码。三次的原始输入和参数相同。前一次的结果不会传给后一次。因此，“第三次成功”表示重复调用时出现了成功结果，不表示方法经过了两次学习或修正。

这三次请求不是三个新任务，也不保证统计上独立。相同模型和相同输入可能产生相近结果。即使 temperature 为 0，保存的回答也不完全相同。

一套完整实验包含 8 批 × 2 种输入 × 3 次重复 = 48 次判断请求。只有模型返回可处理的测试计划，程序才发出后续生成请求。每批每次最多两个计划，每个计划最多一个新增测试。

N04 占三批，因此它每种输入、每次重复最多有六个计划。其他案例各占一批，最多有两个计划。不同案例的请求次数和计划上限不同。同一案例的 A、B 两组具有相同上限。

这里的相同预算只指请求次数和每次生成数量上限。B 组增加开发记录，输入更长。两组的输入长度和实际模型用量不同。因此，这个比较同时改变了信息内容和上下文长度。

两次完整运行：第一次运行中，大量回答不符合程序要求的 JSON 数据格式，部分回答超过输出长度限制。我们保留全部结果，再对所有输入统一重跑一次。第二次缩短测试和证据的编号，增大输出长度上限，并容许一种不改变内容的额外格式字段。

第二次运行保留原有任务说明、程序内容和测试选择。它没有根据某个案例的失败来追加解题提示。本报告把第二次完整运行作为主要结果，并单列第一次结果。两次结果不取各自最好的案例后拼成一个成绩。

重复执行失败测试：同一个新增测试实际运行失败后，程序再运行一次，以检查失败是否稳定。这次重跑不调用模型，也不增加新增测试数量。

怎样评价提取、补强、误报和漏报

对材料提取，我们事先整理了 10 个相关原测试、14 条可公开读取的历史步骤和 28 处源码内容。这份清单用于检查程序有没有找回关键材料。它只用于评价，不提供给自动提取程序。

对四类指定缺口，我们先检查模型是否提出了对应测试计划，再检查新增测试是否真正实现了它。每种输入有 4 个案例 × 3 次重复 = 12 次发现机会。一个案例即使分成多批，每次重复也最多记一次成功。

对两项已经检查的行为，每种输入有 2 个案例 × 3 次重复 = 6 次判断机会。模型明确承认已有联合检查，才算判断正确。没有输出、没有处理该案例或格式错误，都不能算正确判断。

对每个新增测试，分析助手先核对输入是否合法，以及全部期望结果是否能从需求或已有接口规则推出，再读取测试运行结果。测试中的自动结果检查称为“断言”。只要其中一个关键断言缺少依据，整个测试的有效性就不能确定。

我们再检查新测试增加了什么。有些测试增加了新的条件组合。有些只加强已有结果检查，例如把“行数没变”改成“原来的行仍完整保留”。还有些只补充一个普通属性检查。这些类别分别统计。

所有通过代码结构检查的新增测试，都会使用项目对应的测试框架实际运行。同次运行还执行用作生成起点的完整原测试。原测试通过，有助于排除基础环境不能运行的问题。这里没有重新运行整个仓库的全部测试。

误报需要分层判断。模型说“缺少某项检查”，但原测试已有该检查，属于缺口判断错误。新增测试对程序提出需求中不存在的要求，则可能产生错误的缺陷告警。单看测试失败次数，无法区分这两种问题。

本实验没有用“容许几个误报”来换取更多发现。程序先保留线索和可执行测试，评价者再核对全部期望。这个评价标准减少报告中的错误告警，但尚未实现自动零误报。

漏掉指定缺口也需要区分原因。程序可能没有选中相关测试；模型可能没有提出对应计划；生成代码可能不合法；期望可能缺少依据；实际测试也可能没有检查到目标。格式错误或信息不足单列为“无法判断”，不当作已证明不存在缺口。

本轮优先保留潜在线索和可执行测试，以观察遗漏发生在哪一步。最后只把输入合法、全部期望有依据且稳定失败的完整测试计入有效检出成绩。其余结果保留并单列。这个报告标准仍不能证明自动方法达到零误报。

补充实验：直接告诉模型补测什么，是否更容易成功

完整自动流程结束后，我们对未找回的 N01、P2、P7 各做一次补充实验。分析助手直接提供具体测试计划，包括要组合的条件、操作次序和预期结果。模型继续使用原来自动收集的材料来生成测试。它不接收旧生成测试、旧失败日志或参考补丁。

这个实验检查“计划明确后，模型能否实现”。它跳过了自动发现目标的难点。因此，它的成功不能加到前面的自动成绩中。N04 已被自动找到，没有再做此项补充实验。

P2构造同一个合法按键消息，同时包含 Alt 等修饰键和附带文本。检查快捷键名称，并要求 character 为 None。生成 1 个有效测试。两次运行都得到正确快捷键名称，但 character 错误地为 "a"。
P7在整个树节点的数据检查规则之后加入实际改变值的转换，再检查根节点和子节点的具体输出。模型返回空白内容，程序无法读取测试。没有测试进入运行，生成能力仍无法判断。

N01 和 P2 的结果说明：给出明确计划后，模型能够编写揭示已知问题的测试。它们支持优先研究目标确认与选择。但计划也直接提供了期望依据，所以这两次成功不能单独证明问题只出在信息检索或只出在推理。

P2 在字符检查处失败后，最后的修饰键检查没有执行。P7 的空白响应属于输出失败，不能用来断言模型无法实现该目标。

对 P7，我们还单独做了一次“只补材料”的实验。分析助手增加六段原始源码，包括 readonly、transform 的实现及相关导出声明。原有材料完整保留。模型这次仍需自己判断缺口，没有得到具体补测计划。

补齐源码后，模型仍提出两个类型检查计划，未提出运行时数据转换计划。它生成的两个测试中，一个抛出错误，另一个通过。但当前执行工具 Vitest 只运行代码，没有启用 TypeScript 类型检查。因此，这两个运行结果都不能证明模型所声称的类型问题。

这项补充实验暴露了另一处问题：测试计划与执行方式不匹配。检查类型错误需要运行类型检查器；检查运行结果需要实际执行的结果断言。单次补齐源码尚未解决目标选择，也不足以证明补齐材料普遍无用。

遗漏发生在哪一步，原因能否确定

每批测试较多，计划数量受限。每批包含 10–80 个原测试，模型最多选择两个计划。一个关系没有出现在计划中，可能是没有识别，也可能是识别后没有选中。现有结果不能确定缩小批次是否会改善发现。

模型有时把现有实现当作限制测试范围的理由。N04 的 B 组第二次已经指出，批量更新路径没有执行约束检查。模型却据此只建议检查 SQL 执行错误后的撤销行为。第三次两组又成功提出约束违反测试。这说明目标形成不稳定，而非始终缺少源码信息。

相关信息同时出现，不保证模型联合使用它们。N01 多次保留坏输入与正常流关闭的分开检查。P2 多次选择单独的修饰键属性。P7 多次转向类型规则。模型产生了其他合理测试，却没有把本次指定的条件组合落实为测试。

程序分析尚未确认关键对象和作用位置。数据库约束注册、更新和查询必须针对同一数据库与表。流的报错和关闭必须属于同一个响应。数据转换的位置也会影响递归结果。仅关联函数名，无法建立这些关系。

未找到的检查本轮记录直接显示什么目前可以支持的判断
N01：异常后关闭两类原测试已进入材料。自动流程未提出目标计划。直接提供计划后，模型生成有效失败测试。目标确定值得优先改进。但补充计划也提供了期望依据，不能只归因于检索。
P2：快捷键附带文本原测试已找到，两条相关开发步骤遗漏。自动流程未提出目标计划。直接提供计划后，模型生成有效失败测试。材料收集与目标确定都需检查。现有对照不能分清哪一项主导。
P7：递归中的值转换原材料缺少两项操作的完整实现。补齐实现后，模型仍提出类型检查计划。直接给计划的一次调用返回空白。同时存在目标偏移和输出失败。尚不能确认计划明确后能否稳定生成目标测试。

下一项小实验应把材料整理成少量相关测试及可核对的事实。每条事实说明条件、对象、操作和结果检查，并链接原始代码或历史步骤。我们再比较直接提供原材料与提供这些事实时，模型能否更稳定地形成有依据的测试计划。

测试计划还应说明一个具体判断：原测试为什么无法区分某种错误实现，新测试怎样区分它。例如，更新姓名不会改变总行数，因此行数检查不足以检验姓名约束。这个要求比继续增加任务专用变异规则更贴近本次发现的不足。

下一步仍应分别评价材料是否找全、计划是否正确、测试是否实现计划，以及执行方式是否真正检查目标。已有记录能够支持这些可观察的诊断，不能直接证明原开发智能体“遗忘了逻辑”或“只追求代码覆盖率”。

从研究贡献看，本轮实现了一个能够产生有用测试的流程，但尚未证明新的有效关系分析算法。更值得验证的贡献是：程序如何从代码和开发记录中恢复联合检查所需的关系，并稳定指导测试补强。是否使用程序分析或大模型，本身不足以说明这一贡献已经成立。

本次结论能推广到什么范围

这些案例来自已经研究过的任务，数量少，选择不随机。P1 与 P2 还共享同一开发任务。因此，结果适合定位方法问题，不能直接代表新项目上的成功率。

测试期望的最终确认仍依赖分析助手逐项审查。当前实验没有证明自动程序能够保证零误报。与新增测试一起运行的原测试均通过，也只说明选中的完整原测试可运行，不表示整个项目通过所有测试。

本轮没有评价智能体根据新测试修好补丁的比例，也没有测量最终任务解决率。它只评价材料提取、缺口判断、测试生成及测试在固定补丁上的表现。
