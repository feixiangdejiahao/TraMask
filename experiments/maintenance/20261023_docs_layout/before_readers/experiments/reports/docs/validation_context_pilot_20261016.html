新 pilot：从原验证范围搜索组合缺口

2026-10-16。六项任务，四组设置，每组重复两次。研究原型，不是完整 benchmark 评估。

本轮扩大了 LLM 的职责。模型可以提出缺口假设、选择程序查询、生成测试，并根据原补丁的执行结果修正测试。程序保留材料来源、查询结果和实际执行结果。

实验确认了一些有效补测，也暴露了错误预期、目标与 gold 标准不一致，以及输出格式失败。当前结果不足以证明“加入更多 trajectory 就会稳定提高效果”。

目前最有价值的研究对象仍是：原验证在什么条件下无法区分正确行为与错误行为。下一步应检验哪种历史信息能帮助选择这种区别。

本轮检验的问题。coding agent 已经生成补丁和验证测试。我们在提交前检查这些验证是否遗漏了相关条件的组合。我们检验三个假设：开发历史是否增加有效线索；按原验证范围搜索是否优于开放搜索；原补丁的执行反馈是否帮助实现补测。

软件工程问题抽象。一项验证只在具体输入、状态、入口和观察方式下成立。代码调用过某个函数，不能证明相关条件已经在同一次执行中成立。我们尝试保留原验证所检查的行为，再寻找一个合法上下文，使原来未被区分的行为产生可观察差异。

例如，两个函数分别可调用，不等于它们在复制后仍共享同一变量。恢复后的数据正确，也不等于后续读取使用了同一个缓存对象。我们搜索这些具体差别，不预定所有目标都必须由两个源码位置组成。

实验材料。本轮从已分析的 30 项任务中选择 6 项。它们都是方法开发任务。T13、T17、T24、T28 含有已复核的固定目标。T11、T23 用于检查已有验证、错误断言和其他目标；它们不是无缺陷负例。

实验使用保存的最终补丁状态。轨迹用于提取材料。任务选择和调用预算与此前 30 任务实验不同，因此两轮比例不能直接作为同条件的提升幅度。

四组设置。各组使用同一模型、调用上限和测试上限。实际输入长度和消耗可以不同。表中的“历史”指代码阅读、修改、测试执行、反馈及相关推理。

A：源码与测试公开需求、补丁源码片段、原测试代码。模型自行选择目标并请求源码查询。开放搜索对照。
B：再加开发历史A 的全部材料，加上自动整理的历史事件。搜索提示保持开放。检验历史事件的增量作用。

D：无执行反馈对照与 C 共享完全相同的调查、查询结果和测试草稿。最后一轮只自行审阅，不接收执行结果。隔离执行反馈的作用。

A 组仍含从 trajectory 恢复的历史测试代码。我们只去掉事件顺序、推理与执行记录。因此，A 与 B 比较的是历史事件的增量作用，不是“全部 trajectory 信息有无”的比较。

本轮实际实现。程序按补丁修改行收集源码。程序按修改文件、测试来源和需求词匹配选择原测试。程序再按路径、测试名和时间位置索引历史步骤。模型可以读取源码、搜索文本、查看原测试、查询历史，或查找有共同调用的测试。共同调用仅用于检索，不证明数据流或对象共享。

  1. 模型提出至多两个假设，并请求至多六项查询。
  2. 模型根据查询结果选一个目标。模型生成至多两个文件、三个命名测试。程序在原补丁上执行草稿。
  3. 模型获得一次修正机会。A、B、C 收到原补丁反馈。D 只自行审阅。程序执行最终测试。

LLM 因此参与假设形成、材料选择、源码解释、测试编写和修正。它不再只做最后判断。程序提供可核对的源码与执行事实。本轮尚未实现自动证明组合条件的分析器。

模型与执行环境。请求模型为 DeepSeek-v4-flash。provider 返回的模型标识为 deepseek-flash。实验保存了两者。温度为 0，启用高强度推理，每次输出上限为 65,536 token。格式错误或截断最多进行一次同输入重试。

六项任务的原生测试环境均先通过最小测试。生成测试在隔离容器中运行。在线阶段只接收原补丁的结果。gold 是 benchmark 的参考补丁，只用于离线评价。模型没有收到 gold、benchmark 失败测试或人工目标标签。

四项效果指标。正确检测要求模型指出一个原验证遗漏的合法组合，并有依据说明原补丁会违反公开要求，而 gold 可以满足该要求。缺少组合本身不等于补丁存在错误。已经运行过的联合验证，后来没有重跑，应记为重新选测问题。

正确补测要求至少一个原样生成的完整测试实现该目标，并在原补丁失败、gold 通过。我们还检查输入是否合法、关键条件是否成立、预期是否有需求依据。不能删掉错误断言后，把原输出计为成功。

统计以按协议交付的最终输出为准。中间草稿不替代最终输出。若草稿已提出正确方向，但最终输出格式失败，我们单列交付失败，不将其解释为语义判断错误。

“不合格肯定报告”对应本轮标准下的误报任务数。它包括错误预期、把旧验证当新缺口，以及不满足原失败、gold 通过的报告。最后一种可能仍指出真实软件缺陷。报告会说明原因，不把它与错误断言混为一类。

漏检按实验前固定的五个目标统计，不按六项任务统计。T24 有两个目标。历史目标之外的有效补测可以计入正确检测，但不能抵消固定目标漏检。未形成最终决定的调用单列为未完成或待定，仍保留在六项任务的分母中。

T28 的自定义查询身份目标也满足原失败、gold 通过，因此与修复相关。它没有命中预定挂载场景，不表示它没有修复价值。当前实验没有测量这些补测是否提高最终解决率。

一份输出可能既有正确测试，又有错误附加测试。此时，正确补测与不合格报告两列都计数。两列不互斥。两次重复也不是十二项独立任务。

此表报告误报任务数，不估计无缺口任务上的总体误报率。当前原型仍会产生不合格报告，尚未达到零误报目标。

哪些观察得到直接支持。T13 的成功补测让两个不同函数共享同一个变量，再将它们一起传递或复制。测试先通过一个函数写入，再通过另一个函数读取。原测试分别检查了共享和传递，但没有检查这些条件共同成立后的结果。原补丁拆散了共享关系，gold 保留了共享关系。

T17 的成功补测区分“字段不存在”和“字段存在但值为 undefined”。原补丁按取出的值选择默认值。gold 按字段存在性选择默认值。原验证中的普通已有值与缺项，不能区分这两种实现。

T28 的一组成功补测使用自定义查询身份。原验证使用默认身份，因此查询键计算出的身份与缓存中的身份相同。批量恢复在自定义身份下创建了另一个对象，原对象没有得到较新的错误状态。gold 按存储的身份更新原对象。这项结果不属于预定的挂载刷新目标。 此前的静态分析已经记录这一线索，本轮进一步核验了实际生成的测试。

这些成功说明，搜索具体的行为区别可以得到有效补测。但 A 组也发现了 T13、T17 的目标。不能仅凭模型引用了历史步骤，就把这些命中归因于历史事件。

执行反馈解决了什么。第二次重复中，T13 的 C、D 共享一份含有非法 Tengo 语法的草稿。C 看到解析错误后改成合法构造，最终测试在原补丁失败、gold 通过。D 自行审阅后保留了错误。两组的检测目标都正确，补测结果不同。

第二次重复中，T17 的草稿混淆了公共返回值与解释器内部对象。控制测试发生类型转换错误。C 看到反馈后复用已有测试辅助函数，得到有效补测。D 自行改写辅助函数，却引入返回类型错误，最终测试无法编译。

这些对照支持“执行反馈帮助构造测试”。它们没有证明执行反馈能判断正确预期。T11 的精确冲突数量，以及 T24 的 anyOf 拒绝要求，仍需要独立的需求和程序语义依据。

误报与漏检的主要原因。第一类问题是预期过强。T11 的部分测试要求恰好一个结构冲突，但公开要求不足以支持这个数量。T24 的部分测试只看到第一分支的必填规则，却忽略第二分支也能合法接收同一输入。原补丁上的失败反馈没有纠正这些预期。

第二类问题是目标与本轮 gold 标准不一致。其他更新入口、跨无初始化函数中介的完整排序，以及成功快照中的历史错误计数，可能对应真实问题。但 gold 也无法通过相应测试。本轮按用户指定规则不计成功。我们不据此宣布这些软件没有缺陷。

T23 的两份输出同时包含合格与不合格测试。一份正确揭示无返回值的初始化函数把缓存覆盖成 undefined。另一份正确揭示合法依赖链在初始化内部遭到错误拒绝。它们的附加检查分别要求额外的作用域行为或更完整的传递排序，gold 没有满足这些检查。成功项不能掩盖附加问题。

第三类问题是目标分类错误。T11 的一份输出再次提出历史上已经运行过的联合验证。后续代码修改使重新验证有意义，但它属于选测或重验证问题，不是新组合输入缺口。

第四类问题是调查或交付没有完成。目录搜索接口错误、输出截断、无效 JSON 和测试构造错误，都可能使正确线索无法变成最终测试。报告保留这些失败。它们不是模型已经证明“没有缺口”。

T24 的关键区别已经在原始输入中。调用者用默认 put 解释 mode，却把原 options 传给下游；下游直接读取 mode，省略参数时跳过规则。原测试显式传入 put。这不是单纯缺少相关源码。模型没有把这三项事实稳定连接成候选。A 的第二次调查还提出了 anyOf 更新方向，但没有完成最终交付。候选选择与输出失败需要分开诊断。

如何理解当前创新点。候选贡献是利用原验证的具体限制，选择能暴露错误的行为区别。对 coding agent 而言，测试与补丁在同一条开发记录中共同变化。这些变化可能说明哪些条件被简化、哪些执行被替代、哪些预期被修改。三轮调用与执行构成实现流程，贡献还需要来自信息利用方式的可验证效果。

已有论文使用相近的测试生成思想，不会自动否定这个方向。我们仍要说明仓库级 issue resolution 带来了什么新困难，以及 trajectory 中哪一项信息改变了搜索。当前实验支持若干目标的可行性，还不能支持稳定的历史信息增益或一个已经验证的完整新算法。

本轮程序工具主要提供源码检索和执行结果。模型只请求了两次共同调用查询。共同调用没有证明对象共享或条件同时成立。我们因此不把本轮所有成功归因于程序分析，也不把增加分析复杂度当作贡献。

下一轮只收敛一个机制。下一轮效果对照前，需要先固定输入与输出协议，并做小规模可解析性预检。本轮长响应的格式失败和截断已经影响组间结果。这项修正服务于有效比较，本身不作为学术贡献。

建议优先检验：从验证的修改中提取被排除的条件，再用局部程序证据判断这个条件是否值得恢复或扩展。研究对象是一项具体的验证选择。我们不要求先为整个仓库建立完整行为模型。

程序按需处理当前选中的一项验证。程序对齐同一测试的历史版本，提取输入构造、执行操作和断言的变化，并附上相邻补丁修改与执行反馈。LLM 解释其中可能限制验证范围的选择，提出一个合法替代上下文。历史推理只提供线索，不提供正确答案。

LLM 随后提出一项能支持或推翻候选的程序查询。程序返回实际参数、对象身份、可选分支或执行事件。对 T24，应沿调用链区分调用者解释后的默认值与传给下游的原参数。对 T28，应检查恢复前后是否操作同一缓存对象。LLM 据此保留、修改或撤回目标，再生成补测。该机制尚未在本轮实现。

下一轮应拆开三类材料：最终源码与最终测试；额外的历史测试版本；再额外加入修改原因与执行反馈。本轮 A 组已含历史测试代码，因此不能用 A、B 的结果否定所有 trajectory 信息。这个材料对照可以先确定有用信息来自哪里。

评价仍使用原失败、gold 通过的标准。另行记录公开要求支持但 gold 也失败的目标。程序反馈只有在相同候选与预算下改变了选择，并增加有效补测，才能支持这种信息利用方式有效的主张。若对照没有显示增益，就应收缩这一贡献主张。

逐项复核。以下记录保留每份最终输出的判断依据。复核由 Codex 完成，结合源码、原测试、trajectory 和执行结果。没有独立人员盲审。

冻结版本：48 份输出的逐项结论

T11，A：源码与测试，第 1 次：未符合检测标准；未生成合格补测。原补丁没有识别父、子两次删除之间的结构冲突，这个核心观察有依据。但完整目标要求恰好一个冲突，公开要求不支持这个精确数量。gold 按父、子路径报告两个冲突。不能把等于一改成至少一后计成功。

T11，A：源码与测试，第 2 次：未符合检测标准；未生成合格补测。新元素插入保留兄弟节点之前，再执行diff/patch往返。原补丁把新元素追加到末尾，gold也如此；中间插入还触发gold路径索引错误。按用户规定的原失败、gold通过规则，本项不计成功。这不表示报告的原补丁错误不存在。

T11 的 gold 把公开差分 API 放在 diff 构建标签下。离线比较因此对原补丁与 gold 同时启用该标签。测试源码保持原样，最初的构建结果也保留。我们没有把构建配置差异记成模型发现的缺陷。

冻结版本的一份 T28 输出把测试放在两个独立 JS 子包。原运行器拒绝一次执行两个子包。评价阶段按现有包分别执行，测试源码保持原样。两项目标仍在 gold 失败。此项运行修正没有产生新的成功记录。

目录修复后，对应输出又调用了原补丁独有的 Query.restore 方法。我们按用户要求只做静态语义判断，没有把 gold 缺少该方法当作行为失败。公开恢复入口的目标同样受到 gold 清零错误计数的语义影响。

解释边界。本轮样本小，而且已经用于方法开发。我们只运行补测，没有让 agent 继续修复，也没有测 resolution rate。原补丁失败、gold 通过只是与修复相关的证据。它不等于解决率已经提高。
