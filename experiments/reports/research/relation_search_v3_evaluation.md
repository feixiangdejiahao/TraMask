## 什么算一个目标被准确检出

逐例需要同时成立：

1. 同一个冻结配置自动生成或选择了这个组合；评价者手工指定的测试不能代替算法选择。
2. 完整测试确实构造该例目标关系，输入、对象、调用次序和观察时点的前提合理。
3. 完整预期合理。前面的断言偶然先失败，不能掩盖后面仍然错误的断言。
4. 模型修订确实进入最终发射的源码；candidate JSON 中有修订不等于实际执行了它。
5. 对指定候选 patch 实际执行命名测试，相关源控制全部通过，组合测试在目标缺陷处失败。
6. 编译错误、超时、其他同组测试失败、未观察到测试，都不能算目标检出。
7. 所有输入、参数、代码快照、请求、响应和执行材料可追溯；本轮没有读跨探索回答库。

原生 Go 测试继续要求每个精确测试的隔离进程及终止事件。Python 继续使用命名
pytest 结果。重复 source/control 需要绑定到同一 emitted group 的实际执行，
不能借用另一个执行的通过结果。

N08 的旧复制前缀要求首次提交前 `WaitForDurability(0)` 成功，这个前提没有契约
保证，仍不计作可靠见证。带有合理前提的新组合可以计入。N06 的对应关系在原
trajectory 中已经执行过，计作历史关系重新验证，不能声称首次发现一个未组合场景。
P1、P6、P7、N04、N05 的正确目标见证涉及预期修订，要审查完整测试，不能只看
某条关键预期或模型解释。

## 分开观察每一步是否失败

每例记录程序候选池、实际执行队列、语义候选队列、实际发送给模型的候选、有效
回答、接收的预期修订、发射源码和命名执行。目标没有进入语义预算与模型推理错误
必须分开。保留源断言即可检出的候选不需要进入模型队列。

| 指标 | 含义 | 不能据此推断 |
| --- | --- | --- |
| 目标候选覆盖与 rank / Hit@k | 已有程序池或语义队列能否覆盖已知目标关系 | 测试有效或实际检出 |
| 完整正确 oracle 数 | 独立审查完整输入和全部断言后合理的预期 | 新缺陷数 |
| 实际目标检出 / 17 | 满足上述七项证据要求的任务数 | 泛化零漏报、整体误报率 |
| 已确认错误报警数 | 实际失败且已独立确认预期或前提错误 | 其它失败全部正确 |
| 未审查失败数 | 失败但尚未获得完整语义裁决 | 正例或负例 |
| 请求、token、执行数与时间 | 本轮新增语义与执行成本 | 历史累计计算成本已消失 |

本轮 17 例为已用于方法开发的样本。即使达到 17/17，也只能说覆盖这些已知目标；
不能说任意任务上不会漏报。当前目标尚不包含修复 patch 并实际运行 hidden tests，
因此检出率不能称为 issue resolution rate。

## 对照和终止口径

先冻结主配置，让 17 例至少都获得运行机会。建议在同一完整候选池上做零模型的
排序对照：保持生成材料和预算不变，仅替换排序。模型输入上下文对照应保持同一
候选、模型设置、prompt 任务及请求预算，只改变分析证据。单次输出差异只能提供
局部证据，不能排除随机性。

新算法增益不使用“旧 warm 17/17 减新 fresh”计算。资源不足时，优先完成固定17
主臂；额外预算、局部调试和重复请求单列，不把成功的局部实验拼成统一运行。
待主配置冻结后，将其配置与代码快照哈希写入评价检查点。

完成条件是同一个冻结首次推理配置的17例全部完成，并且每例都有通过完整独立
审查的自动组合见证。允许部分其它候选误报不降低完整见证要求。到时限仍未达到
则保留最好代码、精确报告已完成与未完成案例；截止后结果另列，不能回填窗口分数。
