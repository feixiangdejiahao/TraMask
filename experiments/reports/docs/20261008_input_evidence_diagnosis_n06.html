六条任务诊断对照：材料、条件与执行反馈

2026-10-08 · DeepSeek-v4-flash · 实际答复标识 deepseek-flash · 所有实验材料按授权发送到 .env 配置的 provider

相关材料有帮助，但本轮没有观察到稳定的逐组提升。T17 受益于材料选择。T13 需要改变候选问题。T24 的执行反馈帮助模型从测试失败定位到默认模式错误。仅列出更多分支和状态表达式，仍没有解决 T10、T20、T28 的关键组合定位。

实验设置

选择 T10、T13、T17、T20、T24、T28 六条原失败任务。评价使用此前确认的 7 个参照目标：T20 有两个目标，其余各一个。T24 的 anyOf 目标只作额外观察，不进入这次分母。gold 与 benchmark 信息仅用于离线评价。

组别输入与流程
A：原自动输入每条任务选一个与诊断范围相关的原候选。首轮 provider 请求与其原始请求逐字段相同。第二轮只做自查，不提供执行结果。
B：人工材料保留 A 的候选原因、关系、判断问题和系统提示。替换相关源码、原测试和历史步骤。第二轮仍不提供执行结果。
C：增加程序条件在 B 上加入程序提取的分支、默认值、状态赋值和 YAML 约束。其余输入不变。第二轮只做自查。
D：加入执行反馈共用 C 的首轮答复。第二轮提供该答复生成测试在原补丁上的结果。没有生成测试时，明确说明没有运行证据。

每组每任务有两次调用预算。单次上限为 32768 个输出 token，temperature 为 0，reasoning_effort 为 high。C/D 共用首轮，主对照共实际调用 42 次。该共用设计使第二轮反馈比较从同一份测试开始。

C 首轮只在 T20、T24 生成测试。因此，D 只有这两条任务获得实际运行反馈。其余四条只有“没有生成测试”的状态说明。本轮不能据此判断执行反馈对那四个遗漏目标是否有效。

材料由本次 Codex 助手按前次诊断手选。程序随后在选定文件内选取最近 12 次相关命令及最后 3 次验证命令，并保留原反馈。条件提取也仅作用于手选区域。因此，B/C 是定位与表示能力的诊断，不是已经实现的自动算法成绩。没有独立人类审阅。

A 也不是重跑所有自动候选。六条任务的原完整运行共有 295 次调用，并命中 T24。当前 A 是每任务一个已选候选的匹配对照；其两次调用没有复现原 T24 命中。虽然请求字段相同，仍出现答复差异。本轮只有一次配对运行，不能据此估计稳定提升幅度。

主对照结果

“准确说明”要求答复中的原因或补测目标明确指出参照条件。“正确补测”要求测试包含必要条件，并用需求支持的断言揭示原补丁错误。说明可能没有准确定位原因，但测试仍可能触发错误。C 的 T24 就属于这种情况。

“准确说明”是本轮额外检查的解释质量，不替代前次按实际错误揭示评价的成功数。各组在两次预算内任一次成功即可计入；这里没有把首轮和次轮相同目标重复计数。

补充检查：候选问题是否限制了模型

主对照首轮显示，模型即使拿到相关材料，仍可能只回答原先狭窄的问题。因此增加一个单独的检查：保持 C 的全部材料和条件不变，仅把原特定关系假设改为“检查本区域的条件与最终行为是否被联合验证”。六条任务各调用一次，上限仍为 32768。此组记为 N，不混入四组主结果。

N 在固定预算内准确说明并正确补测 2/6 条任务：T13、T24。T13 在原补丁执行失败，gold 的指针复制映射提供静态支持；按此前对新增辅助代码的要求，本项未运行 gold。T24 完成动态 gold 对照。T10、T20 的测试仍未触及参照目标。T17、T28 的调用耗尽输出额度，没有最终答复。

T13 是本轮最清楚的候选表示证据：C/N 的材料和程序事实相同。C 继续判断“Clone 结果已有断言”，N 则识别“两个不同闭包仍须共享同一捕获变量”。这支持优先修改候选问题。但一次对照尚不能给出平均收益或泛化结论。

技术补跑与格式问题

三次未完成请求单独用 65536 输出上限补跑。模型、输入文本及其他请求字段保持一致。此结果回答技术额度是否阻止输出，不能作为固定预算主对照的提升。

逐项解释与程序分析修改

T10：预热缓存与 JSON 输出

材料差异：原候选只讨论 profile 到日志函数的数据传递。它没有关联到 CLI 测试。人工材料加入 CLI 测试、缓存测试和 JSON 格式化器，并保留 warm_cache 分支。

观察结果：原输入已有 main 与 manager 的完整代码，完整补丁也包含输出变更。因此，不能说模型完全没看到错误路径。三组首轮仍只否定 profile 日志关系。第二轮条件组转向 profile 内容是否影响缓存键，测试通过原补丁。候选表述补充组转向缓存命中后的输出，但没有组合 warm-cache。

算法修改：改进程序分析：识别传给断言辅助函数的可调用入口，例如 assertRaisesRegex(..., bandit.main)。然后建立提前退出对后续 output_results 的控制影响。把具体控制条件与输出联系起来，不能只把 main 内任意值传递当作相关候选。

程序提取条件 · 人工材料输入

T13：复制闭包与共享捕获变量

材料差异：人工材料没有新增源码文件。它将 13 份文件收窄为 4 份，并减少同一隔离测试的历史版本。复制逻辑与单闭包验证原本就已进入自动请求。

观察结果：四组主对照都认为单闭包隔离测试已足够。仅改变候选问题后，模型明确提出两个不同闭包共享捕获变量。生成测试在转移后的写闭包执行后读取，得到 1 而非 2。

算法修改：改进候选表示：保留共享对象身份及复制前后的共享关系。结果已断言只能排除“完全未观察”，不能排除“共享结构发生变化”。此处需要改候选问题；增加源码检索不是首要修改。

程序提取条件 · 人工材料输入

T17：存在的 undefined 与默认值

材料差异：人工材料补入 vm.go、objects.go 和当前 destructuring_test.go。它把编译默认值、索引读取、缺失值转换和原测试放在同一范围。原候选主要是 emit 返回位置传给 changeOperand。

观察结果：人工材料组第二轮识别存在的 undefined，生成测试在原补丁失败、gold 通过。条件组提取了 70 项事实，但第二轮仍只测试普通值和缺失值；该测试通过原补丁。

算法修改：改进程序分析：沿默认值判断的输入反查来源，连接“查找是否成功”“返回的值”“默认值分支”。保留上游不同状态被转换为同一个值的情况。不要用分支数量替代这条联系。

程序提取条件 · 人工材料输入

T20：配置校验与运行时接受范围

材料差异：人工材料加入配置 YAML，并保留运行时转换及原测试。原自动源码列表没有 YAML，但原完整补丁已包含配置约束。条件组进一步提取 schema 路径与 pattern。

观察结果：主对照仍集中于 sourceIP 的默认 terminal 值。补充组改查 header regexRewrite 与 cookie 字段传递。补测都通过原补丁。它们没有让小数时长或重复配置先经过实际配置校验，因此两个参照目标仍未命中。

算法修改：改进程序分析：用序列化字段路径连接 schema 约束与运行时读取，例如 consistentHash.cookies.ttl。形成“同一输入先校验、后解析”的候选。分别列出正则和 ParseDuration 调用，仍不足以建立该组合。

程序提取条件 · 人工材料输入

T24：默认模式与条件必填

材料差异：人工材料把大量通用 Zod 测试收窄到 item/map 解析器及 requiredIf 测试。条件组列出了调用方的默认 mode 和下游 mode 判断。

观察结果：原输入组与人工材料组都生成 savedAs 联合测试，并显式传 put，所以原补丁通过。条件组的说明仍讨论 savedAs，但代码省略 mode，测试在原补丁失败、gold 通过。反馈组读取失败后明确定位默认值没有传给下游，保留正确断言并去掉部分无关重命名。

算法修改：改进程序分析：连接上游默认化结果与下游实际读取的对象。为候选区分“省略选项”和“显式传默认值”。反馈的已观察作用是帮助定位失败原因；本例没有显示反馈新增了另一个错误检出任务。

程序提取条件 · 人工材料输入

T28：恢复快照与后续框架挂载

材料差异：人工材料将 35 份文件缩至 5 份，并加入 queryObserver、createPersister 和 React 的 fine-grained persister 测试。原输入已有部分其他适配器测试，不能称其完全缺少框架代码。

观察结果：主对照都停在 defaultQueryOptions 到 fetch 的交接，认为核心恢复状态断言已覆盖后果。它们没有继续检查同一查询进入挂载和刷新阶段后的公开结果。

算法修改：改进程序分析：从恢复的状态写入追踪到同一 query key 的后续观察者操作。连接恢复、挂载、刷新与最终状态。普通向下调用展开不能完整恢复事件顺序；应在共享状态上补充消费者与回调关系。

程序提取条件 · 人工材料输入

下一版算法应先改什么

  1. 让候选表达条件对结果的影响。用“输入或状态条件—相关操作—最终观察”组织候选。程序应连接提前退出、值转换、复制和后续消费者。不要把“某函数有结果”“某条边存在”直接变成缺口问题。
  2. 把原测试当作具体行为证据。记录当前候选需要的输入状态、共享对象及操作顺序即可。辅助函数调用、回调参数和公开入口都可保留为潜在测试联系。已有一次成功断言不能排除其他条件。
  3. 用程序事实构建候选，不只把事实附在末尾。保留缺失与取值、复制与共享、默认化与原选项、配置校验与后续解析之间的联系。当前语法事实列表仍缺少这些联系。
  4. 让反馈回到条件与原因。T24 说明原补丁失败反馈能帮助定位原因。对通过测试，应继续检查条件是否实际触发。本轮 D 只提供执行结果，没有完整的分支与状态激活记录；下一步应补这一点。

实现上应先修改 候选构造，再修改 测试入口与消费者关系 和 验证历史连接。本轮没有把这些建议写回原方法；已实现的是独立诊断脚本和程序条件提取原型。
