八项任务 pilot：程序分析应如何帮助模型发现组合缺口

2026-10-09。检测实验。请求模型为 DeepSeek-v4-flash。provider 返回的模型名称为 deepseek-flash。

96 次运行已完成。结果不支持把“LLM 提前参与程序分析”本身作为有效方法。开放模型发现在两次运行中分别正确检测 4/8、3/8 项任务。增加局部程序条件对比后，结果为 5/8、4/8。模型先选位置再接收程序反馈时，结果为 3/8、4/8。保留同一模型计划、删除程序反馈时，结果反而为 5/8、4/8。

程序条件对比有局部价值。但本次增益很小，样本也小。更明确的问题是：程序能定位代码，却还不能说明原测试是否区分了关键行为。当前实现不能据此声称形成了完整的学术贡献。

问题和成功标准

我们在 agent 提交 patch 前检查其验证测试。原测试可能分别检查了两个条件，却没有检查它们通过同一程序关系共同影响结果的情况。我们寻找这种遗漏，并提出后续补测目标。

本次只检测缺口。我们没有生成新测试，也没有执行被测项目。本次结果不能表示补测成功率或 resolution rate。

一个合格目标必须同时满足四点：公开需求支持预期结果；原验证没有有效检查该组合；静态语义分析支持原补丁违反该预期；gold patch 满足该预期。gold 和 benchmark 材料只供实验后复核。算法和 DeepSeek 均未读取这些材料。

我们不把覆盖不足直接当作实现错误。原轨迹已经执行并暴露的失败，也不算新组合缺口。已有有效联合测试但未运行的情况，应归为选测问题。

两版实现有时使用不同私有类、缓存文件或错误码。我们按相同逻辑条件和公开可观察结果比较。我们不声称模型文字可以直接变成一份能在两版执行的测试。若比较需要改变逻辑条件或主要预期，我们不计成功。

本次检验的软工假设

原验证可能使几个不同的行为解释看起来都正确。例如，测试总把“存在错误”和“已失效”同时设为真。此时，“保留失效标记”和“有错误就强制失效”都会让断言通过。补测应拆开这两个条件。

同一现象也可能跨越多个操作。闭包复制测试只调用一个闭包，无法检查两个闭包是否仍共享同一个捕获变量。配置测试直接调用运行时构造函数，无法检查配置是否先被准入校验拒绝。组合搜索应追踪这种行为区别。

这个假设将搜索目标从“再覆盖几个函数”改为“找出原验证尚不能区分的行为”。它给出了软件工程依据。但它仍需算法和消融结果支持，不能仅靠一个新名称成立。

六项任务共有八个固定参照目标。我们在调用模型前冻结了这些目标。T20 和 T24 各有两项。它们来自前期原补丁、gold、benchmark 失败和原验证的静态对照。

每组处理同样八项任务，每项重复两次。每次最多保留两个缺口。温度为 0，启用 high reasoning。相同设置仍可能产生不同答复，所以我们分别报告两次结果，不取两次中的最佳结果。

每次包含三轮逻辑调用。每轮输出上限为 65,536 tokens。只有输出截断、JSON 格式或数量结构不合格时，程序才对同一输入重试一次。所有组使用相同恢复规则，不根据语义结果追加调用。

同一任务的各组、各轮使用完全相同的原始材料。材料包括公开需求、全部修改行附近的源码窗口、最多 45 段验证测试，以及按现有规则截取的轨迹命令和反馈。源码窗口保留修改行前后各 24 行。测试材料上限为 51,000 字符。轨迹材料上限为 22,000 字符。模型没有在中途自行查询仓库。

这些材料比前一版方法的局部候选包更广。因此，A 组也不是旧版实验的原样复跑。不能把本次 8 项的结果与旧版 30 项的结果直接相减。

程序实际做了什么

D 组分析 Python、Go 和 TypeScript 的局部布尔表达式。一个表达式包含 2 至 6 个条件。程序枚举真假取值，找出“只改变一个条件就改变结果”的组合，也找出“改变这个条件但结果不变”的组合。它排除同一变量上一些直接矛盾的字面值约束。

E 组先让模型把公开需求对应到最多四个源码位置。程序核对位置和需求原文，收集局部赋值，并返回同一函数附近的条件对比。模型选择分析目标。程序计算局部事实。

本次程序提取了 68 个支持的布尔表达式，向 D 组选入 49 个。E 的两次运行共提出 45 个位置。程序定位了 44 个，其中 11 个位置获得了布尔对比。另一个位置属于 YAML，超出了当前语法分析范围。

“定位成功”不等于“缺口提取正确”。当前测试联系仍来自名称出现位置。程序没有绑定测试输入与函数参数，没有证明对象身份、跨函数数据流、共享捕获变量或后续异步操作。局部赋值收集也不是完整的程序切片。

在八个固定目标中，当前局部算子明确表达了 T28 的关键真假组合。它没有自动表达 T13 的捕获单元共享、T17 的存在性判断、T20 的跨层准入限制或 T24 的默认参数传递。因此，其余成功主要说明模型从材料中找到了关系，不能自动归功于程序算子。

学术判断与下一步算法方向

当前贡献不能写成“先分析、再调用模型、最后判断”。这些调用顺序只是实现选择。本次 E/F 对照也表明，提前规划和程序反馈需要分别证明价值。

局部条件独立影响并不是新覆盖准则。相关基础可见 NASA 的 MC/DC 教程。本次使用这类对比来检查 agent 验证中的条件混淆，其应用目的不同，但尚需证明该表示能稳定指导有效补测。

让 LLM 参与程序分析也已有先例。IRIS 用模型推断污点规格并结合静态分析。SemTaint 用模型补充调用边、来源、汇入点和库内传播信息。这不否定本问题的创新空间。它说明“LLM 不在最后”本身不是充分的新意。这里引用方法用途，不把预印本自动视为 SE 顶会发表结果。

更有依据的研究目标是：从原验证中识别尚未被区分的行为，再搜索最小的区分组合。原 agent 可能让实现和测试共享同一个简化。方法应指出这个简化，并说明哪个输入或操作会使它失效。这样，轨迹、程序关系与测试补强服务于同一个问题抽象。

第一步，让模型从公开需求提出两个需要区分的解释。例如，“键不存在”和“键存在但值为 undefined”不同；“复制后与源实例隔离”和“复制体内部仍共享变量”也不同。模型只提出待核验假设，并标出有关输入、状态和观察位置。

第二步，让程序按这个假设追踪输入到观察结果的关系。它应绑定同一次测试中的对象和参数，展开相关辅助函数，并跟踪值经过调用、默认值补全、复制或序列化后的变化。遇到无法分析的库操作时，模型可以提出一个局部语义摘要。程序应保留该摘要的假设状态，不能把模型文字当作已证明事实。

第三步，用原测试是否能区分两个解释来指导搜索。若原测试在两个解释下结果相同，就寻找使两者结果不同的最小条件改变。先检查单个关系。只有当区别不能传到断言时，才沿调用、状态或后续操作扩展。这个规则按行为传播扩大范围，不按任务不断添加变异规则。

第四步，按候选关系查询完整轨迹。检索同一对象、操作和断言的生成、执行与修改记录。若原 agent 已看到同一失败，就输出失败反馈问题。若测试后来删除了关键条件，就输出测试弱化问题。只有没有有效联合检查时，才进入新测试补强。

最后判断应逐项指出哪条前提成立、哪条前提缺证。它不能用一般编程惯例直接否定显式需求。程序应帮助模型纠正条件和补齐证据，而不是只给模型一个更长的相关函数列表。

本次已实现的是局部对比和早期位置选择。上述输入绑定、跨操作行为对比和按候选检索轨迹，属于后续算法方向，尚未在本次 pilot 中实现或验证。我们不把它们写成已有实验成果。
