30 条任务 pilot：为什么漏检，以及如何改进

2026-10-08 · 已保存候选、模型请求、答复和测试的逐项诊断 · 没有新模型调用或被测程序执行

主要问题是候选的语义范围不准确。程序常找到函数之间的联系，却没有保留使最终结果不同的条件。模型随后用局部测试判定整个方向已验证，或生成没有触发错误条件的测试。原流程也没有用补测反馈修正下一步探索。

“只有 1 个任务成功”的范围

这里的 1 个任务，是命中本轮 23 项参照目标的任务数。23 项分布在 18 条任务。T24 命中 1 项并生成有效补测，另外 22 项漏检；17 条任务没有命中任何参照目标。T24 的另一个 anyOf 目标也漏掉了。

这个数字不表示方法在全部 30 条任务中只发现一个错误。原样生成测试还在 T04、T23 发现其他真实错误；此前 T11 的环境对齐记录另有一项。这些发现不属于本轮参照目标，但不能算误报。

本报告检查全部 18 条参照任务的候选和模型输出，并逐项解释 22 个遗漏目标。其余 12 条任务没有进入该参照集合，不能一律判作漏检或真实负例。目标筛选及静态依据见30 条任务的补丁差异报告。

本轮检查了什么

我们读取原程序提取结果、实际发送的模型请求、答复、生成代码和已有执行记录。8 个原型源码文件与原调用计划的校验值全部一致。诊断对应实际运行版本。

原实验先用程序分析找出可能未被联合验证的调用、状态读写、条件及返回结果。每个候选触发一次模型调用。请求包含公开任务、原补丁、相关源码、测试和历史步骤。模型判断是否存在缺口，并在判断为有缺口时生成测试。程序随后在原补丁上尝试执行测试。gold 与 benchmark 失败信息仅用于事后评价。

原实验请求 DeepSeek-v4-flash。provider 返回的模型标识为 deepseek-flash，其模型目录名称为 DeepSeek-V4.1-Flash。本次只分析原记录，没有重新请求模型。

范围模型调用生成并执行的测试建议说明
全部 30 条任务1005337907 次答复通过输出校验：337 次提出补测，570 次判无缺口；其余为 76 次输出校验失败、22 次未完整返回或调用失败。
18 条参照任务418162T01 提取超时。其余 17 条进入模型阶段。

一份测试建议可以包含多个测试。已保存的执行结果说明建议是否运行成功，不能单独证明检测了真实错误。298 份原建议通过原补丁，也不能据此全部判为误报。

“检测命中 1 项”和“补测命中 1 项”不是两个独立能力分数。原流程先检测，再为自身发现的目标生成测试。它没有逐项获得 23 个正确目标作为输入。因此，当前结果不能证明模型在明确获知其他目标后仍无法生成正确测试。T06、T17 等记录则能直接说明：即使方向接近，生成仍可能漏掉必要条件。

本轮依据记录定位了实际丢失的条件，并检查相应实现。我们没有做输入替换或模块消融。因此，各原因可以同时存在，不能把 22 项强行分配成互斥的因果百分比。分析由 Codex 完成，尚无独立人类复核。

根本问题一：搜索目标仍偏向验证覆盖

原方法寻找缺少的程序关系检查。原模型提示允许“补充一个原补丁能够通过的正确测试”。当前评价则要求测试暴露原补丁已有错误。两者的成功标准不同。

例如，T30 四份补测都围绕 gap 与 span。它们可以补齐验证，但没有检查真正出错的子网格宽度向父网格传播。继续生成同类通过测试，不会自动接近该错误。

应保留覆盖补强的价值，同时为错误检出设单独目标：根据公开要求和原补丁，提出一个可能违反要求的行为，再寻找能够区分该行为的组合。不能以强行制造失败作为目标。

根本问题二：函数关系丢失了关键上下文

当前候选主要表达调用、传递字段的差异、状态读写和返回值观察。函数联系存在，不能说明具体哪组输入、哪个对象、哪次调用会产生不同结果。

遗漏的信息记录中的表现相关目标
一次操作与再次操作的区别状态搜索要求不同函数。相同函数的多次调用、不同层级或不同配置没有充分表达。T06 连续 include；T16 同一 Env 切换模式；T30 父子布局。
控制流对末端观察的影响候选未保留提前退出跳过输出，以及成功前缀之后的异常终止。T10 预热后 JSON；T08 关闭边界。
值、存在性和对象身份的区别已有值相同，仍可能来自不同存在状态；复制后的多个闭包也可能需要共享一个捕获单元。T17 undefined；T13 共享捕获；T12 导入绑定。
声明约束与运行时代码的联系源码加载仅支持 Python、Go、TypeScript。配置约束没有进入程序关系图。T20 小数 TTL、重复配置项。
构造结果与后续执行的区别返回对象字段已被断言，就缺少继续追踪实际解析、挂载或输出的候选。T22 递归执行；T28 挂载；T18 普通 String。

代码中存在两个具体限制。条件筛选要求至少一个测试输入能静态求值；全部未知时不输出该条件。状态组合还跳过相同函数的读写组合。这会削弱配置间接传入、重复调用及阶段切换的表达能力。

查看候选筛选与状态组合实现。这些限制能解释候选表示的不足，但本轮没有删除限制后重跑，尚不能声称每个遗漏都由某一条限制单独造成。

T10 最能说明“数量不等于相关性”。229 个候选中，131 个检查多个缓存状态操作，93 个检查缓存读写，只有 4 个涉及 CLI main。模型的 229 份保存结果均未提出 warm-cache 与 JSON 输出的组合。

根本问题三：模型把局部覆盖判断扩大了

部分候选已经接近正确代码。模型拒绝“函数结果完全无人检查”这个过强假设，本身可能合理。但它没有继续判断原测试是否只覆盖了某一种输入状态。

任务模型用来判定已覆盖的证据证据没有覆盖的条件
T08普通带引号的边界已经送入解码器。引号内部同时含分号。
T13一个闭包在源实例和副本中返回不同值。同一副本中的两个闭包仍共享捕获变量。
T16开启和关闭类型模式分别有测试。两次执行使用同一 Env，旧约束仍然存在。
T18PreserveResets 后经过 Truncate 的输出正确。直接调用普通 String，不再经过 Truncate。
T24 的 anyOf 目标普通 map 的条件更新与 savedAs 已测试。多个分支包含不同规则，只应作用于所选分支。
T28恢复后核心缓存状态已检查。同一快照在框架挂载后仍保持错误状态。

改进应限制“已覆盖”结论的作用范围。一次成功断言只能支持相应输入、状态和观察阶段。无需给每项测试建立复杂规范；保留与当前候选有关的条件即可。

程序没有把所有已有结构证据直接删除。它会把这些候选交给模型核查执行情况。T24 的成功候选就来自这条路径。因此，不能把漏检全部归因于程序提前过滤了已有测试。

根本问题四：补测没有落实决定性的条件

T06 和 T17 已出现接近目标的模型说明，但测试没有构造真正使原补丁出错的输入。检测和生成同时低分，不能据此认定两阶段是同一种失败。

任务生成代码实际做了什么缺少或绕过的条件
T06给不同层路由设置不同默认值。连续两次 include 显式传入不同覆盖值。
T17比较存在的普通值与缺失值，并观察默认值副作用。键或位置存在，但值为 undefined。
T27设置 filter:()=>true 后检查异步光标。默认过滤器再次处理异步结果的错误路径。
T27 的旧选择目标异步结果正常到达后提交。已有选择后输入过短，再提交。

生成后应核查测试是否到达目标分支、使用同一状态对象，并观察目标发生之后的结果。测试通过时，先区分“没有触发候选条件”和“条件已触发但实现正确”。原方法没有进行这个区分。

根本问题五：trajectory 没有成为完整的验证记录

当前历史检索按源码路径和函数名匹配。它把命中的步骤整体加入请求，没有稳定连接测试编写、实际执行、反馈和后续修改。纯 go test ./... 这类不含具体路径的命令可能被漏掉。

例如，T17 最后的 step_id=221 包含 go test ./...，但没有进入任何候选的历史步骤集合。这个事实说明检索存在遗漏，不能单独证明它导致了 undefined 目标漏检。

相反，大量资料已经进入请求。T28 的材料包含部分框架测试，T20 的完整补丁包含配置 schema。问题不是一律少给资料，而是没有围绕具体状态变化组织资料。

应为当前候选收集短的验证过程：原测试如何构造条件、如何观察结果、最后一次运行发生在哪次相关修改之后。程序负责连接记录；模型判断是否仍遗漏条件。不能从测试数量推断 agent 的动机或遗忘。

根本问题六：补测结果没有指导下一轮

原 runner 对每个候选只发起一次独立模型调用。它随后执行生成测试，但没有把执行结果传回模型，也没有根据结果更新其他候选的优先级。原型是一次生成与事后评价流程。

因此，相似候选可以重复生成同一个已正确实现的组合。T30 的四份 gap/span 补测，以及 T10 大量缓存状态补测，都没有推动搜索转向尚未解释的行为。

原生成流程与独立执行流程提供该事实的直接依据。不能把“没有反馈迭代”进一步说成模型无法利用反馈；后者尚未实验。

为什么 T24 能成功

T24 的区别集中在相邻代码：调用方把省略 mode 解释为 put；下游检查却直接读取原 options。模型明确指出了两者不同，并注意到原测试只显式传 put。

随后生成测试省略 mode，让控制字段命中规则，并省略依赖字段。断言检查解析应拒绝该值。已有差分记录证明同一检查在原补丁失败、gold 通过。

该成功说明：当关键区别清楚、相关代码和测试集中、触发条件可直接构造时，当前模型能够完成检测与补测。它不能证明所有多关系问题都需要更强模型。

改进后的核心算法

建议把候选定义为“条件、短操作序列、末端观察”。程序关系用于连接这三个部分。模型只需说明哪项条件仍未验证，以及需求要求观察什么。

  1. 程序定位行为范围。从变更的判定、状态写入或转换出发，向前寻找输入来源，向后寻找公开观察。包含提前退出、异常和返回对象的后续执行。保留同一函数的多次调用与共享对象。先实现短序列，不扩成任意全程序搜索。
  2. 程序提取可能被混淆的状态。利用代码里的默认化、字段存在检查、复制、筛选及边界条件，保留决定结果的输入区别。对已有测试，只记录它实际使用的相关条件。静态未知保留为未知。
  3. 模型判断缺失的行为区别。输入公开需求、局部代码、原测试和相关验证过程。模型可以否定候选，但结论仅覆盖当前条件。输出一条短假设和测试，不要求额外生成复杂规则文档。
  4. 程序核查触发，模型按反馈补测。运行时记录少量关键分支或读写事件，核对输入是否触发目标。若没有触发，只修改该输入条件。若触发且通过，将该假设记为已验证；若触发且失败，再核查预期。反馈可以指导一次后续尝试，不通过改写预期强行制造失败。

单关系目标检查条件变化如何影响一个后续结果。多关系目标从同一对象或值继续扩展操作序列，直到结果可观察。两者使用同一表示。函数数量和测试数量不再决定组合阶数。

程序提供可操作的条件，模型负责解释需求。例如，程序能指出“存在性与取值分开”“省略值经过默认化”“两次操作共享状态”。它不需要为每个项目新增一套手写变异规则。

这是设计假设。学术贡献应围绕“结合程序关系与原验证上下文，构造能够区分潜在错误的测试”，并用对照证明效果。仅增加提示词、模型调用或候选种类，不足以证明该贡献。

建议先做的诊断 pilot

先用 T10、T13、T17、T20、T24、T28 六条任务。它们覆盖控制流、共享身份、存在性、声明约束、已成功案例和跨阶段状态。该组用于定位模块作用，不用于宣称对新任务的泛化。

对照只改变什么回答的问题
原自动流程保留原候选及输入。得到参照结果。
相关材料对照人工选出相关公开代码、原验证与历史步骤；不提供 gold 或 benchmark 测试。自动定位是否是主要瓶颈。
条件表达对照在相关材料上加入从原源码提取的关键状态与操作顺序。模型是否需要更具体的条件指导。
执行反馈对照加入关键条件是否触发及断言结果；给相同预算的后续尝试。反馈能否修正未触发或观察过早的测试。

每组使用相同模型、调用预算和执行环境。分别报告目标检测、条件实际触发、测试可执行、原补丁错误检出及错误断言数。人工选材可以利用本次诊断来定位材料，因此只是能力上限与模块诊断，不能当作自动方法的成绩。

gold 与 benchmark 只用于离线复核。若人工选材仍不能检出，应改进模型的条件推理或预期判断；若人工选材有效而自动流程无效，应优先改程序定位；若目标正确但条件未触发，应改生成与执行反馈。

langchain-request-coalescing

本轮目标：批内重复输入与受限调度（漏检）

原方法结果：0 次调用；有效答复中 0 次提出补测，0 次判无缺口。测试建议的执行情况：运行通过 0 份，运行失败 0 份，无可用结果 0 份。

T06 · 连续路由复制与多次覆盖

fastapi-deprecation-response-headers

本轮目标：多次路由复制与覆盖来源（漏检）

原方法结果：20 次调用；有效答复中 9 次提出补测，8 次判无缺口。测试建议的执行情况：运行通过 9 份，运行失败 0 份，无可用结果 0 份。

T10 · 缓存预热与 JSON 输出
