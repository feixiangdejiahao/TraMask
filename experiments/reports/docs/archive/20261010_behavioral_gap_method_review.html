使用 Supervisor-Skills 审查组合测试补强方法

2026-10-10 · 研究方法审查 · 依据现有实现、冻结的 pilot 和静态语义复核 · 本次没有新增模型实验或测试执行

建议保留测试补强这一问题，替换当前核心搜索机制。当前程序主要提供相关位置和局部条件。它还不能系统说明原验证为何遗漏某个行为区别。下一步应让原测试的具体限制直接约束搜索，并检验这种做法是否优于同材料下的模型自由分析。

本报告使用 idea-evaluator 审查核心主张、反证和最近邻工作。随后使用 tech-paper-template 检查问题、挑战、算法和贡献之间的对应关系。两项 skill 来自 Supervisor-Skills。本报告区分已观察结果、机制推断和待验证方案。

1. 研究判断

初步判断：真实需求明确。现有实验也找到了一些可用缺口。但当前结果不足以支持“程序分析稳定提高组合缺口检测效果”这一主张。

核心反证：让模型先选位置，再接收局部程序反馈的 E 组，两次合计成功 7/16。共享同一计划、只删除程序反馈的 F 组成功 9/16。16 是八项任务的两次重复，不是 16 项独立任务。这个配对对照没有支持当前反馈机制的增益。

对当前机制的决定：按 idea-evaluator 的“机制被对照击败”规则，不再把 E 组的局部反馈作为论文核心贡献。本报告不为这一机制打乐观分数，也不靠增加重试次数维护该主张。

这个决定限定于已经实现和比较的机制。样本很小，且全部是开发案例。因此，不能据此否定所有“LLM 辅助程序分析”的方案。建议改变模型与分析器交换的信息，再检验新的机制。

当前更适合定位为方法论文。待解决的问题属于已有的补丁验证和测试补强。Agent trajectory 提供了新的过程证据，但增加这项输入本身不构成新的算法贡献。“组合缺口”是否形成独立的新问题，还需要更严格的边界和普遍性证据。

2. 现有方法实际做了什么

使用场景如下。Agent 已经生成 patch，并运行过一些验证。方法读取公开需求、提交的实现、原验证测试和 trajectory。方法寻找原验证遗漏的组合，并提出补测目标。实际使用时，方法不能读取 gold patch 或 benchmark 隐藏失败测试。

最新 pilot 只做缺口检测。它没有生成或执行新测试。评估端按你的规则复核：同一个具体组合应在原 patch 上失败，在 gold patch 上通过。评估还检查公开需求依据，以及原验证是否已经有效检查过该组合。

这轮选择 T10、T11、T13、T17、T20、T23、T24、T28，共八项任务。六项任务含八个事先冻结的参照目标。T11 和 T23 用于检查此前误报类型，不能当作整个任务没有缺陷的负样本。每组每项重复两次，共完成 96 次运行。

各组使用相同原始材料。材料包括修改行附近源码、最多 45 段验证测试和截取的轨迹。每次有三轮逻辑调用，最多输出两个目标。F 组共享 E 的第一轮计划。请求模型为 DeepSeek-v4-flash；provider 返回的模型名称为 deepseek-flash。没有独立核验后端版本。

当前程序分析的是含 2 至 6 个条件的局部布尔表达式。它计算条件何时影响结果，何时被其他条件遮蔽。测试联系主要依靠名称匹配。E 组收集的赋值也主要依靠局部名称回溯。源码已明确声明这些限制。见 实际实现 中的 test_occurrences、automatic_guidance 和 guided_analysis。

八个固定目标中，当前算子只明确表达了 T28 的关键真假组合。E 提出 45 个位置，程序定位 44 个，其中只有 11 个获得了布尔对比。定位正确不能替代行为提取正确。

统计依据：完整统计、冻结协议、完整 pilot 报告。复核由 Codex 根据静态语义完成，不是独立人工复核。本轮没有测量 resolution rate。

3. 创新分析：比较问题、用途和机制

下面列出五项最直接影响本次判断的工作。它们包括近年的方法，也包括不能跳过的基础工作。检索截止到 2026-10-10。这是针对当前主张的对照，不是最近一年全部 SE 论文的系统综述。

工作对象、输入和用途与本研究的重合及差别
Qi Xin、Steven P. Reiss，2017，ISSTA。Identifying Test-Suite-Overfitted Patches through Test Case Generation（DiffTGen）。根据修复前后程序的变化生成输入，观察运行差异，再由正确性判断来源确定预期。实验使用正确修复版本。补测揭示错误 patch 的目的已有研究。本场景中 gold 只能用于评估，因此必须从公开需求得到预期，不能把运行差异本身当作错误。
Zeyu Lu、Peng Zhang、Yuge Nie、Yibiao Yang、Yutian Tang、Chun Yong Chong、Yuming Zhou，2026，OOPSLA。Beyond Coverage: Automatic Test Suite Augmentation for Enhanced Effectiveness using Large Language Models。LLM 生成语义变异体。存活变异体指导已有测试集的补强。研究包含有项目依赖的方法。“语义变异＋LLM 补测”已不能单独支撑创新。可研究的差别是：从一次 agent 验证的具体限制推导遗漏关系，并寻找提交 patch 的真实需求违例。
Sergey Mechtaev、Xiang Gao、Shin Hwei Tan、Abhik Roychoudhury，2018，TOSEM。Test-Equivalence Analysis for Automatic Patch Generation。用值和依赖关系把候选 patch 分成测试无法区分的类，从而减少修复搜索中的重复执行。“原测试无法区分两种行为”这一概念已有研究。我们的候选用途相反：寻找能够拆开这类行为的新验证。用途差别仍需对应具体搜索算法和收益。
Ziyang Li、Saikat Dutta、Mayur Naik，2025，ICLR。IRIS: LLM-Assisted Static Analysis for Detecting Security Vulnerabilities。LLM 推断污点源和汇等分析规格。CodeQL 计算跨过程路径。LLM 再结合上下文筛查报告。把 LLM 放在分析前面并不新。可借鉴的是：模型输出要改变分析器能够计算的对象，而不能只增加一段位置说明。
Shihao Xia、Mengting He、Shuai Shao、Tingting Yu、Yiying Zhang、Nobuko Yoshida、Linhai Song，2026，OOPSLA。SymGPT: Auditing Smart Contracts via Combining Symbolic Execution with Large Language Models。模型把 ERC 规则转成受限语言。程序将其绑定到具体合约，生成违例约束并执行符号分析。“LLM 理解规则＋程序求解反例”也已有研究。我们的难点是从不完整需求和原验证中选择所需区别，并找出该区别何时无法被原验证观察到。

CoverUp 还说明，源码检索、覆盖反馈和多轮修正可以组成有效方法。但加入这些功能不能自动成为本研究的新贡献。其主要搜索目标是覆盖不足的代码；我们应证明新增机制能找到覆盖信息不能指出的关系缺口。见 Juan Altmayer Pizzorno、Emery D. Berger，FSE 2025，CoverUp: Effective High Coverage Test Generation for Python。

MuTAP 的一个具体差别也值得保留。它会用被测程序的实际输出修正生成断言。若直接沿用这一步，可能把本研究待发现的错误行为写成预期。这里需要独立的公开需求依据。见 Arghavan Moradi Dakhel 等，IST 2024，Effective Test Generation Using Pre-trained Large Language Models and Mutation Testing，第 3.2.2 节。

对我此前建议的修正：“提出两种解释，再找区分测试”只是方向描述，还不是已经成立的创新。局部布尔独立影响也接近已有的条件覆盖思想。可能形成贡献的是：自动提取原验证使行为区别消失的条件，再用这些条件选择分析范围和补测目标。这个机制尚未实现，也尚未验证其新颖性与效果。

4. 当前探索为何容易陷入局部改动

4.1 搜索对象仍不统一

现有“组合”包括多个输入值、对象共享、参数默认值、跨层校验和异步顺序。这些对象需要不同的语义信息。调用图中的两条边，不等于输入空间中的两个自由维度。把它们统一成关系数量，会把真正的搜索难点隐藏起来。

也不能把任何漏掉的边界值都改称组合缺口。报告应解释：已有验证分别检查了什么；哪个关系仍未被有效区分；新增条件如何让这个关系产生可观察差异。当前历史标签没有统一证明每个例子的最小交互阶数。

4.2 程序交给模型的对象，弱于论文希望讨论的对象

案例原验证保留了什么限制需要表达的行为区别当前分析的不足
T17：解构默认值默认值测试使用缺失项或普通值。键存在但值为 undefined 时，按存在性判断与按值判断不同。关键区别不要求源码中同时出现两个布尔条件。
T24：条件必填相关 Zod parser 验证显式传入 mode。省略 mode 后，局部默认值与传给辅助函数的原始参数不同。需要绑定调用实参、默认值和被调用函数。
T13：闭包复制验证包含同一闭包的重复引用，或不修改的闭包。两个不同闭包在复制后是否仍共享内部捕获单元。需要保留对象身份和“写入后读取”，名称相同不够。
T20：配置时长测试直接构造运行时对象，绕过配置准入。一个时长被运行时接受，不代表它能通过真实输入入口。需要连接配置约束和运行时解析。
T20：策略合并原验证检查合并后的字段。合并后再应用配置，会不会清空高优先级策略。需要把中间结果连到后续使用及最终观察。
T28：恢复状态部分判断默认 error 非空就意味着 invalidation 为 true。公开恢复入口允许提供 error 非空且 invalidation 为 false 的状态。程序可给出局部组合，但最终模型仍可能引入没有依据的输入限制。

这张表说明，下一步缺少的不是更多关系名称，而是测试约束与语义区别之间的绑定。案例依据见 逐类静态复核。这些解释是机制诊断，不是已完成的因果消融。

4.3 当前 trajectory 提取会漏掉决定性反证

现有程序优先保留轨迹尾部，受 22,000 字符上限限制。T11 在 step 66 已执行节点交换的组合，并看到错误结果。T23 在 step 53 已观察初始化结果为 undefined，随后修改测试让初始化器返回实例。这些记录不能当作“还未生成联合测试”。

应按目标关联代码阅读、测试写入、执行失败和随后的修改，并保留这些事件的版本顺序。不能因为某个失败发生得早就丢弃它，也不能把旧版本失败直接认定为最终版本仍有问题。见 原始反证记录。

Trajectory 可以提供遗漏原因的线索，但通常不能证明 agent 的心理原因。我们可以报告“只从内部入口验证”“看到失败后改断言”等行为。没有直接证据时，不应断言 agent 遗忘了逻辑，或只追求 coverage。

4.4 发现失败、判断失败和评估不匹配混在了一起

127 条肯定报告中，69 条符合标准，53 条不符合，5 条待定。这些条目包含跨组和重复运行的重复发现。53 条不合格报告中，39 条属于 gold 也不满足目标，10 条属于原轨迹已经执行过失败，3 条属于源码推断错误，1 条没有构造出声称的行为差异。

因此，不能把 53 条全部归为模型能力不足。T24 的某个 list 处理问题在原 patch 中确实存在，但 gold 也未修复它。它不满足你的本轮成功标准，却不能据此断言源码判断错误。

方法在线不能读取 gold，所以无法直接用“gold 会不会修复”来筛选目标。应继续使用你的成功标准，同时单独记录不合格原因。否则，算法会被推动去模仿已知 gold 的修复范围，而不是提高独立发现能力。

最后一轮模型复核也不是正确性证明。T28 和 T20 都出现“中间已提出有效场景，最终又被否决”的情况。需要记录结论改变时新增了什么证据。不能只比较最终成功数。

5. 建议的新抽象：原验证没有区分哪些行为

核心问题：原验证在什么条件下，使错误实现与需求要求的行为得到相同检查结果？怎样构造一个合法组合，让这一区别传到可检查的结果？

以 T17 为例。公开需求按键或位置是否存在决定是否使用默认值。原 patch 按取出的值是否为 undefined 决定。下面比较的是“是否使用默认值”，而不是完整程序。

输入情况需求：键不存在才用默认值原实现：值为 undefined 就用默认值能否区分
键不存在，读取结果为 undefined。使用。使用。不能。原测试包含此类情况。
键存在，值为普通数值。不使用。不使用。不能。原测试包含此类情况。
键存在，值为 undefined。不使用。使用。可以。两种判断在此分离。

这不是盲目枚举所有值。原测试先指出两个判断为何看起来等价。程序再搜索能使它们不同的合法状态。对应原测试见 冻结输入 中的 TestDestructuringArray 和 TestDestructuringMap。

对每个候选，只保留四项主要信息：原验证的具体范围；需要区分的两种局部行为；能使它们不同的输入或操作；支持正确预期的公开依据。源码位置和轨迹步骤作为附件。无需先为所有测试建立庞大记录。

设 S 表示提交实现的局部行为。设 R 表示根据公开需求提出的对应行为。设 V 表示相关原验证。check(S,t) 表示测试 t 对该行为作出的检查结果。候选搜索要求如下。

原验证没有区分它们：对相关 t ∈ V，check(S,t) = check(R,t)
新组合能区分它们：存在合法 w，使 check(S,w) ≠ check(R,w)
正确性另有依据：公开需求支持 R 在 w 上的预期。

离线评估再检查：同一个 w 在原 patch 失败，在 gold patch 通过。

这里的 R 是待核验的局部需求解释，不是完整正确程序，也不能从 gold 推导给方法使用。如果源码绑定或需求解释仍不确定，方法只能报告候选。受限分析中的结果不能升级成全程序证明。

“组合”的范围也需要保留。一个目标必须说明输入、状态或操作之间的哪个关系没有被原验证有效检查。孤立的未知边界值不自动成为本研究的组合缺口。已有联合测试但未运行，应报告选测问题。已有失败但未处理，应报告反馈处理问题。

6. 将算法收敛为三个步骤

步骤一：找出验证中的具体限制

程序从 patch 涉及的行为和相关测试断言出发。它提取实际输入、调用入口、共享对象和检查时点。它保留同一次测试中的联系，不把不同测试的取值拼成一次执行。只分析当前候选需要的部分。

LLM 在此阶段读取公开需求和关联轨迹，提出少量需要区分的局部行为。例如“存在性与取值”“复制后保持内部共享与完全拆开共享”。模型还指出这些行为对应的变量、参数或操作。它不负责生成通用规则库，也不只输出函数名。

Trajectory 用于解释测试范围，并排除已经观察到的同一失败。提取时以代码、测试和执行事件的联系为索引。仅把近期文本追加到 prompt，不能完成这项任务。

步骤二：让程序计算行为何时能够分离

程序把模型提出的行为绑定到实际源码和测试输入。它先处理存在性、字面值、参数默认值、直接赋值等可计算关系。针对共享状态，它保留必要的对象身份和读写顺序。对模型假设与程序已经建立的联系，分别记录来源。

程序应返回一份可检查的对照：原测试固定了哪些条件；这些条件为何使两种行为相同；放松哪个测试条件后出现差异；差异沿哪些操作影响断言。若条件仍不可计算，返回具体缺口，例如“缺少此调用的输入绑定”。不要把“找到附近代码”记成分析成功。

LLM 可以在分析过程中补充缺失的语义映射。例如识别哪个配置入口会先做准入校验，或哪个操作生成两个共享捕获变量的闭包。程序再查询对应定义并检查绑定。模型帮助选择分析对象和补齐局部解释，程序承担重复的条件计算和连接检查。

原型不必实现通用符号执行器。可以先支持一组固定的表达方式，如存在、相等、赋值、对象同一性和先后顺序。具体任务中的条件由模型提出，程序根据源码绑定。固定的是表达能力，不是“遇到某项目就执行某条变异”的规则集合。

步骤三：搜索最小的可观察组合

搜索保留 API 的合法输入前提，只改变测试偶然固定的条件。它优先改变少量输入或操作，并保留需要检验的关系。如果差异已经能在公开状态上观察，就直接提出该检查。如果差异还停留在中间结果，就沿必要依赖延伸到后续使用。

因此，补强可以是修改一个输入，也可以是补上一个外层入口、一次后续操作或一个断言。T20 的准入问题需要恢复真实入口。T13 需要复制后修改一个闭包，再通过另一个闭包读取。T28 的状态区别可能不需要继续增加框架步骤。

搜索目标是“在选定范围内，用较少改变产生可观察差异”。这不是全局最小性承诺。若使用受限求解器，求解成功只表示所建模型中存在见证；输入构造、源码对应和需求解释仍需核验。

最后的模型不再自由重写全部结论。它检查需求依据和具体见证中的剩余问题。否决一个程序已建立的事实时，应给出冲突证据。没有证据的新假设不能覆盖已给出的源码条件，但也不能因此自动把整个候选判为正确。

对 patch 相关的验证行为：
  提取测试实际固定的条件和观察结果。
  让模型提出需求相关的行为区别，并定位其语义对象。
  用程序绑定条件、对象和操作，解释原验证为何不能区分。
  搜索能够区分行为的合法组合。
  若差异尚不能被观察，只扩展必要的依赖或操作。
  输出具体目标及依据；将已运行失败、选测问题、未知情况分开。

当前 pilot 到此结束。生成可执行测试属于后续阶段。

7. 单关系与多关系应使用同一搜索原则

已有 211 条记录的关系重编码纳入 264 个验证缺口条目。其中 200 项用单关系表示，64 项用多关系表示。它们来自 90 个任务，且只包含失败尝试。这些数字支持从局部关系开始分析，但不能证明有 75.8% 的修复相关缺陷属于二维搜索。见 原统计及定义。

单关系情况下，程序在已知上下文中求行为区别。例如 T17 的“键存在”和“值为 undefined”。这里不必增加调用链长度。

多关系情况下，程序保留使区别到达观察结果的中间状态。例如“生成共享闭包→复制→通过一个闭包写→通过另一个闭包读”。两个局部测试都通过，并不能替代这个序列。各阶段必须对应同一组对象和正确版本。

扩展的依据应是“当前区别缺少哪一段传播或观察”，而不是预先枚举所有两边、三边关系，也不是先失败若干次再机械增加深度。方法必须允许从一开始就分析需求明确要求的跨阶段关系。

潜在贡献在于用行为区别决定分析需要保留的状态和搜索范围。单关系和多关系共享这条原则。增加图搜索或限制路径长度本身不构成该贡献。

8. 下一步 pilot 应验证机制，而不是先扩大流程

下一轮仍只做提取和检测。先回答一个问题：程序能否自动输出比“相关代码片段”更有用的行为对照？暂不加入测试生成、执行后的修复和完整 agent 循环，避免同时改变多个环节。

先用当前八项开发案例检查表示能力。人工复核程序是否绑定了正确输入、对象、阶段和断言。这不是新的检测成绩。尤其要检查 T13、T17、T20、T24 的区别是否真正由程序表达，而不是只在模型解释中出现。

随后建议选约 12 个此前未用于方法迭代的任务。按任务和仓库去重，预先冻结选择规则。当前 30 条都已参与探索，不能把其中其余 22 条称为独立留出集。若新样本仍来自 211 条失败记录，结论也只适用于该样本范围。

组别输入和处理回答的问题
开放分析基线同一模型读取公开需求、实现、原验证及修正后的轨迹材料，自由提出缺口。新增机制是否优于模型直接分析？
语义计划对照模型提出局部行为区别。返回相关源码和普通分析事实，由模型继续构造见证。收益是否仅来自更好的提问和材料？
完整候选方法共享上一组的同一行为计划和源码材料，另用测试约束绑定与差异搜索产生对照和见证。程序计算是否对有效发现产生独立作用？

后两组复用完全相同的第一轮行为计划。保留相同源码片段和统一调用预算。若程序查到了新定义，应把同一原始定义提供给对照。这样才能区分“获得更多材料”和“程序真正计算了有用关系”。

所有组使用相同的轨迹提取修正。Gold、benchmark 失败和历史目标留在评估端。为完整方法人工提供的正确关系只能作为单独的能力诊断，不能混入自动方法成绩。

应报告四项主要结果：正确建立行为对照的任务数；正确检测任务数；不合格肯定报告数；固定参照漏检数。再记录模型提出的有效场景有多少在最后被保留。不合格报告继续区分源码判断错误、已经运行过的失败和 gold 也不满足目标。

有些任务没有已确认正目标。这不等于它们是负样本。可以使用已有有效联合验证的具体机会检查误报，但不能据此计算全任务误报率。两次重复应分别报告，不能取最好的一次。

如果程序仍只定位到相关函数，说明表示设计没有实现。若行为对照正确却不比共享计划对照更有效，应放弃该计算机制作为主要贡献。若成功仍只集中在开发案例，不能主张泛化。这里检验的是新机制，不是继续为已失败的 E 方案寻找解释。

这条链在概念上对应了三个实际困难。但它还没有通过“方法交付了贡献”的最后检查。当前可以推进原型验证，不能直接把上述三项写成已经实现的论文贡献。

建议的优先顺序：先实现测试输入与局部行为的真实绑定。再实现基于原验证约束的区别搜索。轨迹事件提取和最终判断中的证据检查应作为配套修正。暂时不要扩大规则库，也不要靠增加 agent 轮次替代核心计算。
