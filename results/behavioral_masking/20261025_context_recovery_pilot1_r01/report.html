只改变测试上下文，能否揭露已知错误？

在固定顺序筛选出的 10 个 Validation Miss 中，Clack 的原测试通过增加两行 setup 揭露了已知错误：让前一次请求先完成，再执行原来的新请求与取消断言。轨迹里已有相近的执行条件，但没有把它用于这项断言。

这轮回答的是四个 Observation。结果支持一个具体的上下文迁移操作：改变前一次异步操作的完成状态。跨任务的重复规律尚未建立。

O1 · Context-only Repair 是否存在？

存在，确认 1 个。Clack 的要求是：启动新请求时，取消前一次请求的 signal。Agent 测试与 Verifier 都调用同一功能、检查同一取消行为，区别在于新请求开始前，旧请求是否已经完成。

事后的机制检查表明，原测试确实执行了 pending 请求的取消；它未覆盖被断言请求的“完成后再取消”路径。该例属于有效的 Context-recoverable Validation Miss。它遗漏了完成后的执行路径；整体取消机制已经运行。按 PDF 的严格定义，原测试中被跟踪的 a-signal 在两实现上均为 true，尚未建立局部效应不同的 Masking witness，因此本轮确认的严格 Behavioral Masking 为 0，细分类型保留为“完成路径未覆盖”。

O2 · Repair 是否简单？

这个成功修改只改变 1 个语义条件，新增 2 行可执行代码。它把前一次请求从 pending 变为 resolved，无需重构测试，也没有修改目标操作或断言。

 signals.push(lastCall[1].signal);
+resolveA([{ value: 'stale' }]);
+await flush();
 instance.emit('userInput', 'ab');
 await vi.advanceTimersByTimeAsync(10);
 expect(signals[0].aborted).toBe(true);

该修改揭露的是“旧 signal 必须被取消”这一任务语义。原复合测试末尾再次调用 resolveA 时，Promise 已经完成，因此那一部分不再构成迟到结果的竞态检查。这个成功结果具体支持取消行为的上下文修复。

O3 · Context Factor 是否有规律？

发现了“前次操作的生命周期状态”这一因素，尚未观察到跨案例重复。本例给出的可执行变换是：在同一后续操作之前，让先前异步操作完成。它可以作为后续候选生成规则，但本轮只有一个成功案例，无法据此归纳出多类稳定的 Context Transformation。

其余所选测试未建立合法的 setup 修复。对齐中发现的阻碍包括遗漏目标输入、原断言错误和参考对照不成立。

O4 · Trajectory 中是否存在相关线索？

事后回查找到 1 条可追溯的执行线索。Clack 轨迹第 62 步曾运行一个 smoke test：启动异步 resolver，等待 50 ms 使初始请求完成，再输入字符 x 发起后续请求。执行记录显示它观察了 loading、选项和调用次数；它没有保存旧 signal，也没有检查取消状态。

后来通过的目标测试把被检查的请求 a 保持为 pending。成功修改所需的“前次已完成”条件，已经在更早的执行历史中出现，却没有用于这一取消断言。这里可复用的是完成时序条件；历史脚本尚未检出该错误。第 62 步原命令 · 原执行记录

由此得到一个值得检验的简单算法：

提取历史中的完成／等待条件 → 迁移到相关测试的目标操作前 → 执行 P/R 对照

成功修改所需的条件可以在既有历史中找到。下一步应检验：同类历史条件能否在更多任务中被提取和复用，以及它能否提高候选修改的成功率。
