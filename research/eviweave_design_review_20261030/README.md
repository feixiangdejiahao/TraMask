我建议保留 EviWeave 的证据图、对象绑定和整体可组合性检查，同时把“这次要核实哪条要求、需要观察什么”提前放进检索与规划。现有方案已经较清楚地解释了怎样把片段接成可运行测试；实现时最需要补齐的是：怎样选择值得组合的片段，以及怎样判断组合后检查的是任务要求。

**1．我对 PDF 中完整方案的理解**

[PDF](../../eviweave-report.pdf) 的输入是 issue、最终 Patch、Agent 历史、当前测试和测试预算。输出是生成的测试及其执行结果。它的主线如下：

```text
历史记录 → 建立轻量索引
当前测试 + Patch → 选择目标 API / 字段 / 操作
                 → 检索相关历史位置
                 → 提取局部证据片段、建立证据图
                 → 匹配对象和输入输出端口
                 → 检查类型、别名、状态、顺序和观察可达性
                 → 排序，必要时再补一个历史片段
                 → 生成测试，从 issue 推导断言
                 → 执行；未落实组合意图时，根据反馈重新规划
```

这里有三个不同的工作。Typed Path Fingerprinting 帮助判断两个片段在目标及依赖结构上是否对应；Typed Port Matching 决定哪个输出接到哪个输入、哪些操作使用同一对象；Joinability Validation 检查接好的整体有没有冲突。这些职责应继续分开：结构相似可以帮助找候选，对象与顺序约束决定候选怎样连接。

PDF 已经考虑了搜索规模。附录给出了先索引后局部分析、两个检索通道、保留不同历史版本、三值可组合性判断，以及示例上限：3 个目标、24 个分析位置、路径深度 3、128 个特征、每对片段最多 2 个映射、扩展 3 个计划、返回 5 个计划、最多两个历史片段。因此，接下来的重点是补全这些上限之前的选择规则，以及上限之后的补救机制。

另一个容易混淆的词是 coverage。第 31 页的 R_FP 是“候选图包含多少当前测试的结构特征”，分子分母都是图路径特征。此前覆盖率实验测量的是程序执行中的分支和函数内路径。二者应在实现和实验报告里分别命名。

**3．从输入到输出，一次完整实现需要做什么**

**步骤 A：先确定当前测试及其运行环境。对应 Algorithm 1 的输入。**

需要明确 `current tests` 是哪些测试。建议默认使用最终提交时保留、且能关联到历史执行的验证测试作为组合起点。已删除的临时脚本、旧版测试和已有项目测试进入历史索引；完整旧 witness 另有恢复入口。如果任务要求涉及的操作没有任何当前测试承载，可以从历史测试恢复一个起点，或记录需要新建调用。

每个起点至少记录测试函数或参数化实例、fixture、运行命令、工作目录、构建方式、最终实现版本。初次执行原测试可以确定基线是否通过以及目标是否真正运行。全套测试通过但无法定位单个函数是否执行时，执行状态保留为未确认。

这里不需要重新开发 replay。现有 [replay runtime](../../src/context_recovery_pilot1_runtime.py) 已可作为执行层；需要在它上面提供“取指定版本代码、运行选定测试、返回结构化结果”的接口。生成测试始终针对最终 Patch，历史结果保留其原版本。

**步骤 B：把历史变成可查找的记录。对应 `IndexHistory`。**

PDF 的四种证据来源应有不同的解析方式和用途。

|历史载体|怎样提取|能支持什么|
|---|---|---|
|Agent 写入测试文件、执行内联脚本|恢复代码版本，解析定义和调用，连接执行记录|对象构造、输入、操作、断言、实际到达情况|
|Agent 运行已有项目测试|从对应仓库版本取测试及 fixture，核对测试选择、skip 和执行结果|历史确实执行过的项目用法；不要求源码曾完整出现在对话中|
|stdout、生成的 JSON、配置文件|关联产生它的命令和读取它的后续操作|实际数值、数据形状、状态变化；输出值本身不自动成为正确 expected|
|读过的源码和文档|保留原文位置、符号和适用版本|API 契约、效果摘要、规则依据；阅读不等于执行|
|模型 reasoning / 计划文字|单列为可检索的假设，连接其引用的代码或需求|提供搜索词和解释线索；不能单独证明代码执行过或规则正确|

一个最小记录可写成：

```text
来源：历史步骤 54，测试文件中的 streaming_consumes_and_closes
代码版本：该步骤写入的文件版本
执行：步骤 118 的测试运行包含此函数，通过
目标：Response.iter_multipart
准备：IteratorByteStream 包装生成器，Response 使用 stream 参数
观察：同一个 response 的 is_closed
历史断言：正常迭代后 is_closed 为 True
适用范围：这次历史执行使用合法 multipart
原文位置：代码、命令、执行输出分别可取回
```

应保存“写代码→后续执行”的关系，不能只用相同的 step id 关联二者。S030 的测试在 s54 定义，在 s118 的通过记录中再次执行。S065 的可用旧测试来自恢复出的项目文件；如果索引只扫描 Agent 命令里的代码，就会漏掉它。

对于长历史，先扫描全部记录并建立轻量索引，只为命中的位置提取详细图。代码、依赖及实现版本都相同时可共享解析结果，多个执行结果仍分别保留。断言变弱、加入等待、改动输入、删除测试的版本不能合并掉：这些变化可能正是恢复 witness 的线索。

**步骤 C：把任务要求整理成具体待检查事项。建议加入，放在目标选择与检索之前。**

PDF 在测试生成之后才调用 `DeriveAssertions`。我建议增加一个较轻的前置步骤，先说清楚准备检查什么，不必立即写出最终断言代码。

每条事项包含五项：依据原文、适用条件、目标操作、应该观察的结果、观察时刻。例如：

```text
依据 1：framing malformed 时抛出 DecodingError。
依据 2：streaming multipart iteration 消耗流并关闭响应。
待核实的组合：对一个开始时打开的 live response，解析坏 framing；
              捕获 DecodingError 后，该 response 应已关闭。
需要确认：关闭要求是否适用于此异常退出；错误是否来自 framing 解析。
```

两个需求都存在并不自动证明任意组合成立。要检查它们的前提是否可以同时满足，是否有例外，以及检查对象是否相同。需求没有说清楚时，检索已读文档和项目接口契约，保留尚未解决的解释。

这一步可以由 LLM 提出，但输出必须包含原文、条件和推导。模型自评的“置信度高”不足以替代这些信息。第一次只提出与当前目标直接相关的少量事项；后续找到互补历史证据时可以补充。这样既有方向，也允许历史带来新的检查想法。

规则来源还要区分权威性。先看任务是否明确规定行为，再看该任务采用的 API 文档和接口契约；有明确任务特例时记录特例。被测 Patch 的当前实现描述实际行为，不能单独证明应该如此。已有测试的 expected 和模型 reasoning 都可能有误，需要核对依据；版本不一致或规则互相冲突时，保留具体争议，暂停据此报告缺陷。

**步骤 D：选择目标。对应 `TargetElements(t, patch)`。**

建议从三处合并候选：当前测试调用的 API 或观察的字段；Patch 修改函数及其直接入口；任务要求点名的 API 或效果。先按需求分组，再在每组中优先选少量目标。

只使用测试与 Patch 的交集可能漏掉任务要求新增、而 Agent 没测试到的调用。S088 的历史测试没有调用 `DirEntry.Info()`；它需要从文件系统接口要求和已读源码找到这一操作。`3 个目标`适合作为首轮并行处理数量，余下目标进入队列，避免永久丢弃。

目标名还需要解析到类型和模块。例如两个类型都有 `close()`，不能仅因为方法名相同而认定可互换；无法解析时保留构造器和局部用法，让后续绑定处理不确定性。

**步骤 E：先粗检索，再花时间建图。对应 `RetrieveCandidates`。**

PDF 的目标通道和接口通道都应保留。建议再加入一个需求/观察通道：按待检查状态、观察字段、历史断言修订、规则依据查找。这能召回“能提供有用检查，但和当前代码结构不太像”的材料。

粗检索阶段还没有完整图，只使用廉价信息：解析出的符号、构造器、字段、输入形状、读写文件、执行命令、历史 diff、需求中的词。动态语言的词法命中可作为候选，不提前宣称类型匹配。

如果首轮沿用 24 个局部分析位置，可以各给三个通道 8 个名额；重复候选合并后补足，空通道的名额借给其他通道。这是待校准的初始配置，其目的在于防止大量同 API 的近似测试挤掉少量观察或契约证据。只按最后出现的时间或全文相似度取前 24 条，会失去这种保障。

`CheapRankAndDiversify` 的第一版可以使用可检查的排序项。目标通道先排解析到同一符号的记录，再排包装调用与未解析同名调用；接口通道先排明确输出/输入类型及资源来源对应的记录；需求/观察通道先排待观察字段、需求相关设置及其断言修订命中。每个通道内部再按相关状态词、来源可恢复程度和版本适配成本排序，时间新旧只作末级区分。一个候选具体能补什么，在局部片段恢复后确认，不应由粗检索凭空判定。

**步骤 F：提取能解释行为的局部片段。对应 `LoadOrBuildSliceGraph`。**

从目标调用向前找 receiver、输入、fixture、配置和数据文件，向后找返回值使用、状态读取、输出和断言。局部分析遇到 helper 时，保留 helper 的效果摘要和可取回位置；只在当前连接需要其内部信息时展开。

“向后取几行”不适合表示观察：HTTPX 的观察发生在异常捕获之后，异步任务的观察可能发生在 await 或事件回调之后。应沿数据使用及正常/异常控制流找观察，并记录消费 iterator、等待任务完成等必要动作。

片段达到分析预算时，应把缺少的依赖留下，记录它是什么、到哪里继续查。局部预算需要独立于指纹深度：例如首轮只展开两层 helper、最多分析 200 个语句节点；超过后使用摘要，遇到具体未满足依赖才申请额外展开。这两个数同样属于待校准配置。生成器函数被定义并不表示它执行过；`iter_multipart()` 返回 iterator 与 `list(...)` 实际消费，需要在图中区分。

对于文档、源码阅读和生成数据，采用适合各自内容的表示。文档提供约束，JSON 提供值及来源，执行代码提供可调用操作。它们可以共同进入一个计划，不必都伪装成可执行语句图。

**步骤 G：建立图，并计算结构指纹。对应 `BuildEvidenceGraph`、`CorePaths`、`R_FP`。**

PDF 已给出节点和边类型。实现还要规定以下内容：

|需要补充的规则|建议|
|---|---|
|一个对象在不同时间是否是同一状态|对象身份保持一致，状态标注时点；读取前、消费后、异常后不能混成一个 State|
|`WRITES` 表示什么|区分代码可能写、某次执行观察到、规范要求建立的状态；并记录正常/异常条件|
|图边从何而来|标注 AST/数据流、运行观察、文档摘要或模型推断；模型推断不直接升级为确定事实|
|别名怎样表示|保留必须相同和必须不同的对象约束；克隆还需要副本内共享、副本间隔离|
|常量怎样处理|结构匹配可抽象普通数值；语义条件保留 absent/undefined、空/非空、阈值两侧等区别|
|方向、重复和截断|特征编码包含边方向；明确重复计数上限，优先保留 receiver、输入和观察相关特征|

第 16 页把 `iter_multipart → WRITES → is_closed` 画成一条边。在实现中，这条边需要附带条件：正常流执行曾关闭，并不代表异常分支也关闭。也不能把待检查的“异常后应关闭”当作当前 Patch 已经满足的事实。

建议把用于结构对齐的核心限制为计划准备保留的锚点，例如目标操作、receiver 的角色和资源身份。准备替换的输入/状态单独比较。否则，当前测试使用 buffered body，历史片段使用 live stream 时，原来的状态越被完整编码，真正有价值的替换反而可能越不相似。

R_FP 继续用于同通道内排序即可。同时计算候选增加了什么：新的执行条件、观察字段、观察时刻或检查依据。相同目标、相同结构、同样只检查异常的另一条 buffered 测试，即使 R_FP 很高，也可能没有新的检验价值。

**步骤 H：先写组合计划，再生成代码。对应 `MatchPorts`、`Extend`、`PortDelta`。**

除 PDF 已有的来源、绑定、顺序和改动外，计划应记录：待检查要求、必须满足的条件、保留的操作、采用或修订的断言、观察时点、尚未解决的事项。

HTTPX 的计划可以写得很具体：

```text
保留：原坏 framing 的 bytes、Content-Type、iter_multipart、DecodingError 检查。
替换：Response(content=body) → Response(stream=历史 stream helper(body))。
绑定：解析与 is_closed 访问使用同一个 r。
顺序：新建打开的 r → 消费 iterator → 捕获预期异常 → 读取 r.is_closed。
新增检查：r.is_closed 为 True；依据是该输入下适用的生命周期要求。
禁止的干扰：观察前由测试主动 close；另建 Response 读取状态。
```

端口应区分两种“缺少”。一种是代码尚不能运行，例如没有构造 receiver；另一种是测试虽然能运行，但缺少这次想建立的条件，例如已有输入是 buffered，希望替换成 live stream。后者也必须产生检索与扩展需求。

第 35 页用“open observation: closure state”驱动第二个片段检索，但原来的错误测试在语法上没有缺失变量。这个 open port 应由待检查要求创建，或由同对象的历史观察发现。否则实现者无法判断为什么要找 `is_closed`，而不是该对象的其他几十个字段。

匹配时先固定资源身份和已知相等/不等关系，再尝试输入和观察连接。最多输出 2 个映射并不限制搜索这些映射的工作量；还需要限制尝试过的部分绑定数。确定冲突立即剪枝，未解析的类型进入 UNKNOWN。两个保留映射尽量代表不同的对象连接假设，避免只在变量改名上不同。

**步骤 I：整体检查，并允许多条件共同满足。对应 `Joinability` 和第二次扩展。**

保留 PDF 的 Type、Alias、State、Order、Guard 五类检查，并补上“适用条件是否满足、观察是否能测到所需效果”。建议让每一项返回状态及理由，整体只在存在明确冲突时返回 NO。没有建模到的必要条件应为 UNKNOWN，不能因约束集合为空而得到 YES。

尤其要分开两类条件：

```text
测试前提：response 开始时打开，输入会触发预期解析分支。
被测义务：该解析分支退出后 response 应关闭。
```

前者用于构造和验证测试，后者用于发现错误。若把“错误 Patch 没有关闭”解释成计划不可组合并丢弃，测试就失去了揭错机会。类似地，任务要求的 API 缺失、合法调用异常，也可能是产品错误，应先与规范对照，不能一律当作坏测试修复掉。

组合允许一次补齐多个相互依赖的条件。PDF 的“最多两个历史片段”并不等于“只能修改两个字段”，一个片段可以提供一组数据和设置。建议首轮仍限制两个 donor；若已有计划只差一个有明确来源的必要条件，允许一次受预算约束的第三片段扩展。

旧记录中，S012、S059、S061 的构造统计报告过 3 个转移片段；其中 S012 的多个片段可以来自同一个源码单元，S061 也有更短的替代提案。因此不能把该计数直接当作对“两个证据图”的反例。它说明实现需要定义片段计数单位，并测量截断造成的损失。S059 的真实数据库、WAL 故障注入、错误传播与 waiter 连接，是很好的扩展深度压力案例。

**步骤 J：排序并分配全局预算。对应 `RankAndDiversify`、Algorithm 1 的循环。**

第 38 页优先 YES、明确改动、目标对应、低编辑成本。建议把检查意义放到更前面：先看计划是否有依据、是否补上一个尚未验证的条件与观察关系，再比较可运行把握和成本。

对于首轮返回的 5 个计划，可以先按“待检查要求＋改变的条件＋观察字段/时点”去重，保留不同输入、状态、观察方向；在存在有依据的 UNKNOWN 计划时给它留一个位置。这样不会因某个候选容易确认类型，就让五个近似但无增益的 YES 全部占满队列。

这里的“增益”是可以说明的新检查。例如“开始用流承载坏数据并观察错误后的关闭”，比“另一个也能抛同样异常的 buffered 输入”更有针对性。第一版可以用明确分组和顺序规则，不必先训练复杂排序模型，也不宜把模型随口给出的置信分数当作校准概率。

Algorithm 1 对每个测试处理完整个 Q，再进入下一个测试。若 b 是全局预算，前几个测试可能耗尽它。建议按需求组轮转：每组先尝试一个计划，再回头分配额外尝试。同一测试的众多参数实例共享检索和图缓存；参数化的不同语义条件仍分别保留。

**步骤 K：生成测试及 oracle。对应 `ComposeTest`、`DeriveAssertions`、`RequirementApplies`。**

给 LLM 的输入应是选定的基准代码、有限 donor 原文、绑定与顺序计划、要求依据、尚未解决的条件，以及允许修改的位置。输出是测试改动和“每条改动实现计划哪一项”的对应关系。生成后重新解析，检查关键调用、输入、对象绑定和观察是否兑现。

原断言按适用性处理。S030 可以保留异常断言并增加关闭断言；S065 原测试对 `Invalid.lash` 的预期本身有问题，需要依据接口契约修改。不能统一要求保留全部历史 expected，也不能允许模型为了通过测试随意改 expected。

建议支持三种 oracle：直接任务要求、带适用条件迁移的历史断言、两次相关执行之间的 MR。优先使用最直接且有依据的表达。HTTPX 已知应关闭时，直接 `assert is_closed` 比仅比较两路关闭状态更明确；两路都未关闭时，单纯相等会通过。

MR 计划还要描述两次执行共享什么、分别新建什么，以及比较结果的哪些部分。例如 S088 两路必须指向同一个文件；S042 两次查询必须处于对应的事件观察窗口；S078 比较逐字符样式时不能先删除 ANSI 信息。运行两次不自动得到有效 oracle。

**步骤 L：执行、分类反馈、结束或继续。对应 `Execute`、`ExercisesPlan`、`ReplanWithFeedback`。**

`ExercisesPlan` 需要返回多项结果，而不是一个布尔值：目标调用是否运行、前置状态是否成立、对象绑定是否正确、观察是否到达，以及断言在哪一项失败。依据这些信息区分下面的情况。

|执行情况|后续动作|
|---|---|
|缺 import、fixture 或构建失败|修复已定位的接线问题；不解释为行为错误|
|只创建 iterator，没有消费|添加消费动作，保留原来要检查的语义|
|测试选择或准备未使目标执行|修订准备、命令或绑定；若是合法调用被产品错误阻断，转为缺陷候选|
|需求前提未满足|修改 setup 或选择别的计划；报告哪些条件未到达|
|前提成立，支持充分的断言失败|保存缺陷候选和失败观察，重复确认；不朝“让当前 Patch 通过”修改 oracle|
|前提成立，断言通过|记录该具体组合已检查；有不同条件或观察方向时继续探索|
|oracle 或事件状态解释未解决|保留未决结果，补充契约或观察证据|

失败时，后续普通断言可能没有机会执行。应区分“组合前提已落实，但第一个义务失败”和“测试没有运行到目标”。需要多个观察时可收集诊断结果或拆成共享准备的测试，避免最先失败的检查遮蔽其余信息。

每次修订只解决已定位的问题。建议每个计划最多两次修订作为初始配置；对语义相同的计划去重，记录已尝试过的绑定和反馈，阻止循环。在实践中，编译、生成、执行、总用时各有预算；PDF 的 b 只约束生成/修订次数，不能单独限制索引、建图和匹配的总开销。

执行环境也属于计划的一部分。每次运行重置可变 fixture、文件和进程状态；异步操作用明确的事件或完成条件同步，避免靠任意增加 sleep 改变被测交互。需要先观察、后清理的资源，把清理放在记录结果之后。重复执行可以发现部分不稳定性，不能替代对对象共享、事件窗口和时序要求的检查。

**4．三个具体案例怎样走完整条流水线**

**S030：怎样从两个通过的 HTTPX 测试得到失败测试。**

历史 s54 同时写入了正常流测试和 malformed framing 测试，s118 的 87 个通过测试包含它们。前者使用 `IteratorByteStream(stream())`，消费后检查关闭；后者通过 `content=body` 提供已缓冲的坏数据，检查异常。来源见 [原轨迹](../../results/failure_analysis/deepswe_failed_trials_n211_20261006/trials/httpx-multipart-response-parsing__pAv36Bv/trajectory.json) 和 [逐例记录](../../results/behavioral_masking/20261026_fragment_reuse_n88_r01/observation/adjudicated/S030.json)。

下面是人工推演的候选选择，不是自动检索输出：

|阶段|具体中间结果|
|---|---|
|选择起点|现有 malformed framing 测试，保留坏 body 和异常检查|
|提出检查事项|streaming 状态下，错误退出也应履行适用的关闭要求|
|检索|同 `iter_multipart` 找到正常流测试；`is_closed` 也能通过观察通道命中|
|选择 donor|正常流测试提供传输方式和状态观察；另一条 buffered 错误样本没有补齐所需条件|
|建立图|bytes→生成器→IteratorByteStream→Response；Response→解析消费与关闭状态读取|
|绑定|流的输入接原坏 body；解析和状态读取共用 r|
|裁剪|不迁移 donor 的 `len(parts)==1`，它只适用于正常输入；不迁移与本次目标无关的第二次迭代检查|
|验证|r 初始打开；合法 Content-Type；消费解析器；异常捕获后能读取状态；观察前无测试主动清理|
|生成|`content=body` 换为 live stream，并在异常后检查 `r.is_closed`|
|执行解释|原异常正确出现、关闭失败，就报告生命周期义务违反|

这一推演还暴露了切片中的一个细节：正常测试同时含“解析一条数据”“关闭”“禁止第二次消费”等检查。将全部 forward slice 原样复制进错误测试会引入不适用断言。切片要保留可用观察和来源，采用哪些断言由本次条件决定。

此前 [MR 执行记录](../../results/behavioral_masking/20261028_metamorphic_history_n88_r01/runtime_analysis_001/relations.md) 已确认 S030 正常退出关闭、错误退出在 P 上未关闭而 R 关闭；这是具体关系可揭错的证据。这里的自动检索、映射与排序仍是待实现设计。对于“报错前底层尚未耗尽”这样的更细条件，若测试确实依赖它，还应记录实际读取进度，不能只根据多放了一块数据来推定。

**S085：为什么必须允许一次修改多个值。**

分片测试原来有四个文件，duration 为 400、300、200、100，阈值 150，两个 shard。缺少的条件是“只有一个 slow 文件，同时还有剩余 shard”。历史输出提供了可迁移的较短耗时记录。

|候选准备|slow 文件数|错误 Patch|正确实现|
|---|---:|---|---|
|原值 400、300、200、100|3|PASS|PASS|
|只将第二项换成历史耗时记录（102、103）|2|PASS|PASS|
|只将第三项改为 54|2|PASS|PASS|
|同时改第二、三项|1|FAIL|PASS|

这些是已有 [执行矩阵](../../results/behavioral_masking/20261026_fragment_reuse_n88_r01/observation/execution/S085/attempt_001/matrix_summary.json) 的结果，每种实现重复两次，原操作和断言保留。

算法应先表达目标条件 `0 < slow_count < shard_count`；对当前四文件和两 shard 的计划，具体落实为一个 slow 文件。两次数据替换共同满足它，不能要求每一次单独修改都先产生失败才继续组合。

这里没有缺失变量：四个 duration、threshold、shard_count 都已有值。只查询未连接的代码端口，无法发现这个需求。因此，计划要把“将已有值调整到满足某个关系”也表示为待解决事项。对该例，可以枚举历史提供的有限数据替换，计算 slow_count，而无需一开始就实现通用约束求解器。

旧执行还验证了将阈值改为 350 也能揭错。这是根据已有关系新推导的数值，不能标为历史直接复制。两种构造都应保留，用来比较纯迁移和有依据的有限参数生成。

S006 提供了另一种组合理由：去掉并发上限但保留三个任务时，继续断言峰值为 2 会拒绝正确实现；再将任务数调整为 2，原断言才适用。联合修改既可能建立错误触发条件，也可能使保留的 oracle 在新条件下成立。[S006 记录](../../results/behavioral_masking/20261026_fragment_reuse_n88_r01/observation/adjudicated/S006.json)

**S088：怎样处理历史从未执行过的观察操作。**

历史执行过嵌入文件的读取和目录枚举，也读过标准库中 `Size()` 返回文件内容长度的实现；没有执行过 `DirEntry.Info()` 的测试。来源见 [S088 记录](../../results/behavioral_masking/20261026_fragment_reuse_n88_r01/observation/adjudicated/S088.json)。

推演过程是：从文件系统要求获得 metadata/content 对应关系；从现有测试恢复非空文件 fixture 和 ReadDir；通过已读接口材料补充 `entry.Info().Size()` 调用；把它与同一文件的 ReadFile 字节数连接。完整关系是：

```text
前提：同一文件系统中的同一路径；普通文件；内容不变；使用非空字节样本。
执行 A：ReadDir → 选中该文件的 entry → Info → Size。
执行 B：ReadFile(同一路径) → 字节长度。
检查：A 与 B 相等。
```

此前执行中，ASCII `abc` 在 P 上得到 metadata 0、读取长度 3；UTF-8 内容得到 0 与 6；R 两组一致。空文件的 0=0 在 P/R 上都成立，适合作为控制，却无法揭露这个错误。[执行关系](../../results/behavioral_masking/20261028_metamorphic_history_n88_r01/runtime_analysis_001/relations.md)

PDF 已把源码和文档阅读列为证据，建议明确实现出口：它们可以支持有依据的新调用和检查。该类结果应记录为“历史 fixture＋契约指导的新操作”，保留其来源差别。

**5．怎样具体限制搜索空间，同时保留长历史中的有用信息**

建议把搜索分成廉价广查与有限深入两层：全部历史都进入索引，只有命中的少量位置进入图分析。以下是可直接实现的起始规则，数值需要在开发集上校准。

|位置|具体规则|解决的问题|
|---|---|---|
|历史索引|按符号、类型/构造器、字段、文件、测试版本、断言修订和状态关键词建立查询入口；原文按需取回|无需将整条轨迹放进每次模型输入|
|去重|相同代码与依赖版本共享图；不同输入、观察、断言或实现版本保留；失败/通过结果分别关联|减少重复工作，同时留下测试弱化和早期发现|
|粗召回|三个通道分配 24 个位置；同一模板的重复样本限额，按状态与观察方向补足|防止相似代码挤占全部候选|
|局部图|沿目标依赖展开，使用 helper 摘要和缓存；触及边界保留未解决依赖|避免完整跨过程分析成为前置成本|
|图特征|先沿用 h=3、最多 128 个特征；保留被截断标记；路径只用于局部排序|控制图展开规模，便于测量截断损失|
|端口匹配|先绑定资源和对象身份，再匹配值与状态；每对输出 2 个不同映射，并限制部分映射扩展数|防止仅限制输出数量却仍枚举全部映射|
|第二片段|仅对排名前 3 的不同意图计划扩展；围绕每个计划的待补事项合计取最多 6 个相关位置，优先复用已有图|把“查第二个片段”的候选数也显式限制|
|第三片段|仅用于仍有一个明确且可补的必要条件的计划，取少量候选，计入同一预算|为少数复杂组合留下出口|
|测试调度|按需求组轮转，每组先一个；相同准备/目标共享构建和分析；运行状态相互隔离|避免前几个测试耗尽全局预算|
|反馈|同一计划限制修订次数；语义相同的改动不重复执行；通过后仅探索新的条件或观察|避免无限修正和重复生成|

在没有缓存命中和冲突剪枝时，24 个首轮候选、每个 2 个映射，最多产生 48 个一片段扩展；扩展 3 个计划、每个取 6 个候选、各 2 个映射，最多再产生 36 个二片段扩展。这只是该配置的候选数量上界；图分析和每次映射求解的开销仍需单独计量。

第二片段的图缓存只按来源和版本存储；可组合性结果还要包含当前绑定、顺序及条件。一个 donor 能接到计划 A，不代表能直接接到计划 B。

预算至少记录四本账：分析了多少位置/节点，生成或修订了多少测试，实际运行了多少次程序，以及总用时和模型消耗。一个 MR 候选可能运行两路程序，重复确认又增加执行；不能只按“生成一个测试”与单次直接断言比较成本。达到上限时输出尚未尝试的需求和截断位置，后续扩大预算可以从队列继续。

模型调用也按阶段分开：先从任务提出少量具体检查；再对已召回的小集合解释对应关系；最后按固定计划生成代码。确定性的代码解析、来源记录、状态计算和执行结果采集交给程序。模型遇到缺失信息时请求局部补取，避免每轮重读完整历史。

以下信息适合降低优先级，通常不适合作为直接删除理由：历史很早、测试当时失败、没有新增执行 coverage、类型暂未解析、需要两个修改、结构指纹分数不高。它们都可能出现在有用候选中。

S078 的结论来自单测试路径复核，详见 [覆盖率分析](../verifier_coverage_20261027/why_no_new_paths.md)。该分析也修正过一部分 Verifier 的 oracle，因而不能用原始“31 条无新增覆盖”概括真实缺陷数量。这里采用已具体确认的 S078 来约束方法设计。

MR 可以成为 oracle 分支，但不宜强制用于全部候选。已有分析中 8 条更适合直接契约，2 条尚未找到有区分力的关系，4 条 focal oracle 存在争议。S080 的一个等价关系在错误 Patch 两路都丢失样式时仍然成立；S078 仅比较可见文字也会漏错。构造不同运行、选择正确观察和避免退化样本，仍是方法必须完成的工作。

**7．建议的算法改写**

下面保留 PDF 的主要模块，补上上述接口。`Obligation` 就是一条带前提、出处和观察方式的待检查要求；`Need` 是实现它还缺的构造、条件或观察。

```text
I = IndexHistory(history, recoverable_repository_versions)
O = ProposeCheckableRequirements(issue, relevant_read_contracts)
Groups = SelectTargetsAndBases(current_tests, patch, O, I)
Results = []

每个 Group 第一次被调度时，在分析预算内惰性建立初始计划：
    加入适用的历史 witness 恢复计划
    加入当前测试的 oracle / 观察修订计划（可以没有 donor）
    提取当前图，按目标、接口、需求/观察三个通道检索
    对有限候选建图，进行端口匹配与整体验证
    以未满足 Need 定向扩展第二片段
    保留必要时才使用的有限扩展入口

while 全局预算仍允许 and 存在未尝试计划：
    按需求组轮转，选择有依据、有不同检查意义的计划
    验证前提与 oracle 依据；必要信息不足则局部补取
    生成测试，并核对代码是否实现了绑定、顺序、条件和观察
    执行，分别记录 reach / preconditions / observations / assertions
    保存本次结果，包括通过、行为失败、接线错误和未决
    若接线或到达存在具体问题：有限次数修订
    若得到有依据的行为失败：重复确认，最小化并保留必要条件
    若通过：仅为尚未检查的条件/观察方向继续扩展

输出全部尝试、缺陷候选、尚未解决事项和各阶段成本
```

最小化发生在有意义的测试构造出来之后。删除一项修改后除了重跑断言，还要检查待测条件是否仍成立。否则删除关键 setup 后得到的“更短测试”可能已经换了要检查的事情。

**8．实现顺序与验证方式**

第一步先打通一个可解释的完整闭环：历史记录及版本恢复、简单检索、明确的组合计划、直接契约或 MR oracle、已有 replay 执行、分项反馈。证据图首先服务于对象、数据和顺序检查。结构指纹作为独立可替换的排序模块加入，便于判断它实际减少了多少无效候选。

原型不能只围绕 HTTPX 调整。建议至少包含以下不同难点作为开发检查：S030 的资源状态与异常后观察；S085 的联合数值条件；S066 的两个 donor 与已有项目测试；S037 的旧 witness 恢复；S088 的契约指导新调用；S042 的观察窗口未决；S080 的 MR 两路共享错误。各例使用情况和已知答案应记录为开发信息。

所有 88 条及其人工分析已经用于此次方法设计，适合做回顾性开发和诊断；最终泛化结论需要新任务或未参与设计的材料。同一任务的不同轨迹按 58 个任务分组，不能跨开发与评估集合。将来生成测试的一侧只读 issue、Patch、当前测试和本轨迹可恢复的历史/仓库，Verifier 与参考实现留在评估侧。

最有价值的对照是：相同执行与模型预算下，直接恢复旧测试、简单历史检索后生成、加入绑定/整体验证、再加入指纹排序；另比较提前给出检查事项与最后才生成断言。对组合深度和检索数量做小规模变化，分别观察召回损失及成本。

测量应覆盖整个过程：人工有用证据是否被召回；组合是否成功建立条件；oracle 是否适用；是否真正揭错；错误报告数；模型、分析与执行成本。将失败归入“证据没找到、条件没建立、观察不合适、oracle 有问题、执行环境失败”等具体阶段，才能判断下一步应该改检索、组合还是检查。

当前证据最充分地支持三项实现工作：保留并检索完整历史中的不同版本；围绕对象、状态、顺序和观察位置组合；让有依据的检查要求参与组合决策。Typed Path Fingerprinting、具体排序规则和搜索上限的效果，应通过这些对照来决定。
