## 1. 为什么从 trajectory 得到这个方向

不少测试的通过存在一个偶然原因：测试选的状态，让较弱的实现与所要求的行为表现相同。

- P2：shortcut 测试没有 associated text，`None` 与 `text or None` 正好相同。
- P6：分别复制共享 cell 与保持共享的 clone，初始值都相等。只读看不出，先经一个 closure 写、再经另一个读才看得出。
- N04：验证与不验证 invariant，在不影响 COUNT 的 UPDATE 上相同。
- N09：记录级“选参数或默认值”与逐字段合并，在全给/全不给时相同。

这引出一个更精确的搜索问题：**怎样构造最短的输入—操作—观察程序，使这两种行为不再相同？** 需要的 combination 是这个搜索问题的解，而不是先贴上的 feature 标签。

重新读轨迹还排除了两个简单叙述。N02/N05 的 agent 已想到不关闭/不恢复样式却接受它；N06 的目标组合曾实际通过，后来失效。因此，发现可区分行为不等于已经确定缺陷，恢复旧验证也不等于生成新测试。

## 2. 核心抽象：带孔的可执行上下文

把仓库候选记为 `P`。选择一处局部实现选择 `ℓ`，用两个可执行片段 `h0,h1` 填入，得到 `P[h0]` 和 `P[h1]`。它们是两个竞争解释，**不预设哪一个正确**。它们也不必构成两个完整、正确的候选补丁；只需能在考虑的上下文中执行。

上下文是测试程序：

```text
K[-] = build inputs and state;
       call P[-];
       perform further legal actions;
       observe a public value / exception / resource state
```

`K` 区分两解释，当且仅当在相同输入和环境安排下，其稳定观察不同：

```text
Obs(K[P[h0]]) != Obs(K[P[h1]])
```

可以将它理解为“针对一个具体疑问设计实验”。例如 N08 的疑问是 `< high` 与 `<= high`，P2 是 shortcut 下 `None` 与 `text or None`。P6 的疑问是共享图保持还是每条边独立复制，此时差异暂时藏在对象图里。

这一表示比 `(q,ρ)` 多出的算法能力，不是公式本身，而是下面的**构造运算与反向传播**：上下文可拆成前缀和后缀；后缀的区分条件可以向前计算，前缀产生的对象和状态可以满足该条件，两者因此可以在中间状态处连接。类型决定能调用什么，效果决定需要写/读哪里，成对执行决定是否真能分开。

### 2.1 同一算法维护什么

搜索节点只需要测试 AST、共同变量绑定、成对程序状态，以及待满足的区分条件。对象差异包含三种可计算内容：

1. 对齐访问路径上的标量值不同。
2. 正常/异常出口或资源阶段不同。
3. 同一运行内部的两个访问路径是否别名，在两解释中不同。

第三项不能省略：P6 的初始标量全相同，但别名分区不同。两次运行中的裸地址本来就不同，不能拿地址不等当缺陷或区分信号。根由共同输入、对应调用结果和访问路径对齐；比较的是根内部的值与别名关系。

这些状态是分析数据，不是让 LLM 填写的自然语言 schema。内部 heap/capture 信息可作为搜索信号，最终测试的断言优先落到公开 API、返回值和可合法读取的状态。外部 fixture 也属于状态：N03/N04 的两次运行需要从等价且隔离的文件系统/数据库快照开始，不能让第一次 move/UPDATE 改变第二次的输入；临时路径按对应 fixture 根比较。

## 3. 竞争解释从哪里来：明确保留这项前置难题

不能把 `obtain_hypotheses()` 写成黑盒。第一版将来源限定为以下可复现的范围，并分别报告成功率：

**实际编辑。** 从 trajectory 恢复同一函数的相邻可执行版本；只替换一个可独立编译的编辑单元，其他代码保持相同。若 API 变化导致无法局部替换，使用完整快照或记为不可恢复。N06 已有旧行为及成功脚本，应先直接重放，通常无需合成。

**有限表达式替代。** 在 issue 改动的表达式位置，以同类型、作用域内的变量/成员、源常量及语言运算符构造深度有界的表达式；包含比较运算替换、布尔连接、可空值/default 表达式。类型检查和原验证的实际观察向量用于控制规模。例如 N08 的 `<`/`<=`，P2 的 `text or None`/`None` 可由该范围产生。这属于已有变异/修复技术，不作为新颖性声明。表达式文法、节点数上限和候选排序必须在运行前固定，不能按 case 加分支。

**少量局部语义提案。** 上述范围不能产生 N03 的规范化去重、N04 的 SQL 写表验证或 P6 的共享 cell 映射。可以让 LLM 根据 issue、局部代码和 trajectory 提出一个小的可执行替代片段；必须保存具体 AST diff，而不是“共享关系正确”这样的描述。编译通过、源测试相容不证明它正确，也不证明它有价值。此来源单列为模型依赖，并与“同预算让 LLM 直接写测试”比较。

**主算法不要求正确参考实现位于假设集内，但检测目标若未体现在任何竞争解释的差异中，就可能漏检。** 多数投票、所有解释一致或全部通过，不是正确性证明。不能为了留下“全是 passing hypotheses”而删除不符合错误 agent 断言、却可能符合 issue 的解释；已有断言冲突应先作为 oracle 分歧处理。

因此这条路线的第一项可否定假设是：**不用目标标签、参考补丁或手工修复，能否经济地得到足够多有用的局部分歧？** 若不能，应放弃将它作为完整 combination 检测方法，而不是悄悄加入 case 专用修复器。

## 4. 测试构造文法：只列三类程序运算

从实际 validation 的 AST、作用域和 def-use 提取构造器、调用、参数表达式、断言观察及异常捕获。保留必要的 fixture 和有副作用 setup，不能只取赋给局部变量的语句。反向切片用于确定候选根；大脚本中的多个 observation 分开索引，但保留各自完整前缀以便重放。

允许访问的方法还可从仓库签名中补充，使用返回类型继续展开，类似 STARS；未解析调用保留 unknown。下面三个运算产生真实代码：

| 运算 | 输入与生成的代码 | 机械合法性条件 |
|---|---|---|
| 实参绑定/替换 | 将调用的一个参数接到已有变量、源表达式或可构造的新对象；可省略声明为 optional 的实参 | 类型、作用域、生命周期、必需参数；同一资源绑定复用同一根，不按变量名字合并 |
| 调用/访问扩展 | 已有 `x:T`，增加 `y = x.m(args)`、字段/下标访问或已有状态操作 | 接收者和参数可构造；必要前置状态由前缀提供；保留真实副作用 |
| 出口连接 | 将观察放到正常返回后，或已知异常捕获后的 continuation | 观察根在该出口已定义；不能在抛异常后读取未赋值的 result |

“可构造的新对象”有有限边界：第一版只允许签名可枚举的构造器调用、源代码/测试中已有 literal，以及对源 record 已出现字段的有限保留/省略/替换；不凭一个 `Object` 类型任意发明对象图。递归构造深度、容器长度、字段集合、字符串/整数域都有预先固定的界。新 closure 的函数体不在这些基础运算中，若需 LLM 提案须单列，不能计成机械构造。

每次扩展至多加一个绑定/调用/访问或一个捕获结构，长度与数据域有界。候选按新增 AST 节点数、执行成本估计、源位置字典序确定顺序；没有根据 pilot 命中率调出来的打分器。

嵌入字符串里的 Tengo、SQL、协议输入不会因 host AST 有类型就自动变成可组合结构。它们需要对应 parser/encoder 或有限局部构造提案。要记录前端是否提供这种结构；原型不支持时算生成失败，不能声称上述三运算天然覆盖了它们。

## 5. 核心算法：反向区分需求与前向构造相遇

普通“先生成输入，再补断言”会反复得到观察不到差异的测试。这里从一个可能的公开观察反推：要使它在两解释上不同，中间状态需要满足什么？再让前缀构造该状态。这个反向需求进入前缀参数和操作选择，才是联合合成。

### 5.1 反向传播的精确定义

对支持的有限语句片段，把两份解释中的变量重命名为互不混淆的两组，执行相同的测试操作。每边执行先表示为带 `Normal(value,state)` / `Raise(type,state)` 标签的结果；捕获异常后可继续执行相应 continuation。若末端观察是 `z`，初始区分需求为 `D ≡ z0 != z1`，也可比较规定的出口标签。对后缀语句 `s` 计算：

```text
Pre_s(D) = wp(Product(totalize(s0), totalize(s1)), D)
```

这里是两份独立状态上的 weakest precondition，不把一个运行的副作用施加到另一个运行，也不把两份可能抛异常的源语句直接串联，否则第一份异常会阻止第二份执行。总化指显式保存正常/异常结果；非终止、超过展开界、超时仍为 unknown，不能伪装成正常结果。两份变量虽然重命名，测试输入仍由显式耦合约束绑定：每个参数孔只有一个共同赋值，初始输入 heap 按构造对应且保持相同别名图，受控环境/调度也对应。否则求解器可以给两个相同程序选不同输入，制造伪分歧。仅耦合共同输入和安排，不强制两个实现执行后的内部状态相等。循环和递归有展开界；任意外部调用不假装有精确 WP。

明确的局部规则如下：

```text
纯表达式赋值 z=f(x): 将 D 中 zi 替换为 fi(xi)；副作用/可抛错调用用转换关系。
字段写 x.f=a:      使用 store/select 更新对应 heap，保留别名条件。
顺序 s;t:         Pre_s(Pre_t(D))。
条件 if b:s else t:
                  对两次运行的可行分支组合分别加入 b0/b1 条件再反推。
异常/正常出口:     使用不同出口关系；在 catch 后仅引入确定已定义的变量。
```

只对可精确建模的标量、有限对象访问和受限表达式做求解。对复杂调用使用有界直接调用展开；仍不支持时采用具体成对执行验证候选，不把 unknown 判为不可满足。这里不承诺建立整个 Python/Go/TS 仓库的通用符号执行器。

### 5.2 最重要的一条构造规则：把别名差异变成可见差异

若两解释的状态中：

```text
alias0(x,y) XOR alias1(x,y)
```

从效果摘要找可经 `x` 写入单元的操作 `w`，以及可经 `y` 读取该单元的操作 `r`。生成：

```text
w(x, a)
z = r(y)
```

然后由 `z0 != z1` **反推写入参数 a**。若单元初始值为 `v`，最简单的写读摘要会导出 `a != v`。这同时选出了操作顺序、对象绑定、数据值和观察；不是先随便改数据，再检查是否碰巧有效。

效果摘要由 AST 字段/下标读写、闭包自由变量绑定以及有界直接调用组合得到。动态分派解析不了就保留未知，不能伪造“不读、不写”的摘要。相同规则也适用于复制后的容器、共享 view、缓存快照，不含 Tengo/clone 专用分支。

这条规则是本提案目前最具体的算法支点。它的前提是能构造出相关对象形状、拿到两种有别名差异的解释；它没有解决这两项前置问题。

### 5.3 前向搜索与连接

前向从恢复的验证 setup 和类型可构造值出发，应用第 4 节的操作。每个部分上下文保留成对状态与绑定。支持建模的片段使用共同符号参数得到路径和状态约束 `F0,F1`；仅支持执行的片段只得到具体成对状态，不从它们假装反解所有参数。后向从已有观察、公开标量 getter、异常类型或资源状态出发，沿调用摘要生成需求。

当前缀的可达状态约束 `F0,F1` 和后缀需求 `D` 有兼容绑定，求解 `F0 ∧ F1 ∧ Couple(inputs, environment) ∧ D`，下文简写为 `F ∧ D`。可满足时把解写回一组共同前缀参数，连接后缀，并执行**完整仓库入口**核实观察分歧。对仅有具体状态的前缀，则在有限参数域内枚举并执行；一个具体赋值不满足需求，不能用于剪掉其他参数变体。若只在私有 helper/手写组件模型上成立，只算组件层结果。

```text
for each executable local alternative h to candidate P:
    replay relevant historical validations on P and P[h]
    if an existing validation already exposes different public observations:
        judge its contract independently
        classify as replay finding, oracle conflict, or irrelevant difference
        continue  # already distinguished; do not claim new synthesis

    forward = restored prefixes and their common typed bindings
    backward = public observations with paired-output-inequality demand

    while budget remains:
        choose the least-cost unresolved forward/backward item
        expand one binding, call/access, or exit continuation
        propagate paired state forward or observation demand backward
        match compatible roots and solve supported conjunctions
        materialize and execute each completed test on both interpretations
        if stable public observations differ:
            retain the distinguishing context and request a contract judgment
```

选择较短代表是搜索策略，不是声称预算内必定找到全局最短测试。若文法有限、状态模型精确、按成本穷举完毕，才有该文法内的最小性；实际仓库的 unknown、环境和截断都限制这个结论。

### 5.4 可以据什么剪枝

- 类型、作用域、definite-assignment 不满足，可以删除相应构造。
- 精确支持片段中的 `F ∧ D` 已证不可满足，可以删除该配对；求解超时不是不可满足。
- 两个访问/操作已证明会正常终止，具有封闭且互不相交的状态/IO effects，也不创造后续 receiver 时，可以作相应的局部交换顺序消重。只有字段读写不相交仍不够：异常可能使另一操作不执行。未解析 effects 只影响排序。
- 对相同绑定、相同完整相关状态和剩余预算，保留成本更小的代表。**当前输出一样不能当作状态等价**，尤其不能丢掉别名拓扑不同的节点。
- 动态前缀没有出现差异，不足以删除它：后续调用可能才触发不同代码，或写操作才激活共享差异。剪枝须考虑两解释的后续代码及可达 effects，不能只沿 buggy candidate 已发生的数据流。

## 6. 三个推导演示

### 6.1 P2：同一个观察决定应该改哪个输入

在 modified shortcut 分支，候选输出 `text or None`，有限表达式文法可提供 `None` 这一替代。原 shortcut 测试 `text=''`，两者相同。

对 `.character` 的区分需求反推得到：

```text
到达 non-shift modified printable 分支
并且 text 非空
```

因此保留原 shortcut 的 key code/modifier，只把已有 associated-text 构造接进 payload；code-zero 的 text-only 测试整体替换不满足这个路径条件。`.key` 在两解释下相同，不能完成区分；`.character` 可以。

issue 对 shortcut 的 `character=None` 给出独立裁决，生成断言仍是 `character is None`。这里的组合、源测试 A 和观察选择都由这处数据流及区分需求约束，而不是关键词得分。

这是人工说明文法应能导出的结果；本轮未实现上述推导。旧 batch7 的 P2 检出来自完整源断言恢复，不能拿来证明新算法有效。

### 6.2 P6：观察需求反过来选择写操作和参数

假设已经取得“保留共享”与“每条边独立复制”两种可执行解释，并已构造两个 closure 共享一个 cell 的前缀。clone 后初始值都为 0，直接读 getter 无法区分。

后向选择 getter 的返回值为观察，读摘要指向其 capture cell。成对 heap 显示 setter/getter 的 cell 在一边相同、另一边不同。第 5.2 节直接产生：

```text
setter_in_clone(a)
observed = getter_in_clone()
```

反向求解给出 `a != 0`，例如 1。一边读到 1，另一边仍为 0。最终依据 clone 应保留内部共享的契约写 `observed == 1`；另观察源对象仍为 0，验证外部隔离。

这里不需要一个名为“clone combination”的规则。但**本例所需的双 closure 前缀和保留 cell identity 的竞争解释，目前都不是简单 Go 类型搜索就能自动产生**。应分别计入输入文法和假设生成指标；不能用这幅人工示意掩盖它们。

### 6.3 N04：为什么已经组合仍不值得作为判别测试

假设两个局部解释分别是 bulk 跳过 validation、bulk 在目标表检查 validation。在 UPDATE 本身成功且检查可达的路径上，要让公开 exit code 或回滚状态不同，反向需求通常会要求 `I(state_after_update)=false`。要检验“本次写入破坏了原本合法的状态”，还需从测试 setup/契约加入 `I(state_before)=true`；后者不是仅靠区分条件就能自动推出的。因此完整约束是：

```text
I(state_before) = true
I(state_after_update) = false
```

已有 `COUNT(*)=1` 加 `UPDATE name=...` 无法满足该需求：更新 name 不改变行数。于是算法不会把“同表出现 bulk 和 invariant”误计为完成区分。

若源构件中有字段谓词 `age>=18` 和 UPDATE age 的表达式，SQL 前端能求出跨阈值的值，再用已有 safe-mode 的失败/快照观察。若没有可组合的 SQL 构件，或无法生成目标表验证的竞争解释，本例保持未解决；不能写一句 `make_invariant_sensitive()` 代替缺失实现。

该例同时说明研究风险：构造一个正确的 bulk-validation 替代可能接近局部修复本身。必须与直接让模型写测试/修复的等预算基线比较，判断间接路线是否值得。

## 7. 断言何时保留、何时加强

区分搜索回答“看哪里、怎样看才能分开”，不决定“哪边对”。三种情况分别处理：

1. **既有断言在新上下文的契约范围内仍成立。** 保留原断言，例如 P2 的 shortcut 前提仍满足。不能仅凭类型兼容推断范围不变。
2. **原断言看不见两解释差异。** 继续搜索观察/状态操作，如 P6 的初始读或 P2 的 key。能区分一对解释，只证明相对这对解释更有判别力，不证明这个断言普遍充分。
3. **没有可靠期望。** 输出可执行的判别测试及两种结果作为待裁决项；不能自动报 bug。N05 尤其需要 issue 语义裁决，重复看到候选原输出不会增加正确性。

LLM 可以在这里根据 issue/接口说明和具体上下文提出小的断言表达式，或选择有依据的结果；它不能因候选失败而把 expected 修到 actual。保存实际提案便于重放，但缓存只能保证本次构件可重放，不能证明模型跨运行稳定或 oracle 正确。

## 8. 对全部 17 条的适用性审查

这是已见案例上的**设计可行性判断**，不是成功率。每行都列前置缺口，避免把有解释能力写成有生成能力。

| Case | 可利用的分歧/搜索目标 | 同一上下文算法可做的事 | 尚需解决的前置条件 |
|---|---|---|---|
| P1 | phase 只在 `u` 路径还是在其他合法语法也生效 | 绑定合法编码到事件观察 | 协议 grammar 和可执行语法替代；候选正则不是合法输入规范 |
| P2 | `text or None` / `None` | 反推非空 text，保留 shortcut 路径，选择 character | parser payload 的字段化构造 |
| P3 | 保留全部 modifier / 消去被 shifted alternate 吸收的 shift | 求使 alias 分开的 modifier 值 | 规范化替代不是当前有限表达式文法保证能找到的 |
| P4 | 保留 quote / 解码 command quoting | 沿 magic 到真实文件/path 观察，构造非平凡字符串 | 合法编码器和 tokenizer 语义；不存在现成 B |
| P5 | 外部 frame 初始化的两种行为 | 合成 Call→member→Call 的观察后缀 | guest factory 复合返回文法、frame 替代及运行时摘要 |
| P6 | 保留 alias / 独立复制 | alias-demand 导出 write→read 与参数 | 双 closure 前缀、正确绑定映射的竞争解释 |
| P7 | recursive 改写保留 / 丢失 pipeline 执行 | 要求 runtime parse、选择值变化观察 | schema 程序构造和有效替代；type-only 不够 |
| N01 | 耗尽前解析抛错，关闭放在正常尾部 / 必要出口 | exception continuation 上读同 response | 清理义务范围、可执行 cleanup 替代、流摘要 |
| N02 | 同上，且轨迹明确有语义争议 | 区分消费前拒绝与消费中失败 | 竞争 cleanup 结构与独立 oracle |
| N03 | 配额前后的身份重复处理 | 反推至少两个 identity、重复前缀、有限 k | canonical identity/dedup 替代及 CLI/文件构造 |
| N04 | bulk 验证 / 不验证 | invariant 敏感性约束与 exit/rollback 观察 | SQL 前端、目标表验证替代；困难较大 |
| N05 | fitting 时 quick return / 仍处理 resets | 对具体 Output 调用保留样式观察 | oracle 是主要难点，输入并非主要缺失 |
| N06 | 旧/新 conflict 分类 | 先恢复现有临时脚本 | 属回归重放，单列收益；不必合成 |
| N07 | 当前扫描 / 真正处理不同起点的重叠 | 用具体端点推演约束真实输入 | 替代扫描算法和可控的 text→hunk 构造 |
| N08 | `<` / `<=` | 求 target=high，并观察未就绪 | 从真实 batch 取得 high/count，确定性异步安排 |
| N09 | record 二选一 / 字段合并 | 使一个字段显式、另一个缺省；flush 前读缺省字段 | 多字段 schema 和 merge 替代；不能仅靠移动 effect |
| N10 | raw mode / 规范化 mode | 同一 requiredIf 前缀省略 optional mode，保留错误观察 | 默认表达式及公开 parser 契约 |

最适合先检验机械部分的是 P2/N08/N10：局部分歧较小。最能检验新搜索是否超越简单参数变异的是 P6/P5，但它们也有最明显的前置生成难点。N06 则是防止夸大组合生成效果的负向控制。

## 9. 从论文借什么，以及不声称什么

| 工作 | 已有贡献/可借鉴之处 | 本提案不能据此声称的新颖性 |
|---|---|---|
| [STARS，ISSTA 2026](https://www.software-lab.org/publications/issta2026_STARS.pdf) | 给定前缀，按变量/类型构造 observer 调用链 | 类型引导调用链已存在；这里待研究的是观察需求反馈到输入与状态操作 |
| [AdverTest，ISSTA 2026](https://arxiv.org/html/2602.08146v3) | 测试与 mutant 共同演化；生成阶段把原程序作为参考 | “模型造 mutant，再补测试”不是新核心；我们的候选不预设正确 |
| [Beyond Coverage，OOPSLA 2026](https://2026.splashcon.org/details/oopsla-2026/51/Beyond-Coverage-Automatic-Test-Suite-Augmentation-for-Enhanced-Effectiveness-Using-L) | 利用存活 mutants 增广真实项目测试 | 只换成 trajectory 提示词不足以成立贡献 |
| [Testora，ICSE 2026](https://www.software-lab.org/publications/icse2026_Testora.pdf) | 结合真实行为差异与自然语言变更意图区分回归 | 用 issue/意图裁决差异也已存在；不能把 oracle 组件包装成首次提出 |
| [Fix2Fit，ISSTA 2019](https://mechtaev.com/files/issta19.pdf) | 用能区分候选 patch 分区的测试减少过拟合 | 候选等价类、区分目标和信息收益并非我们的创新 |
| [Shadow，ICSE 2016 项目及论文入口](https://srg.doc.ic.ac.uk/projects/shadow/) | 在成对版本中寻找真正产生分歧的输入 | 成对执行与条件 XOR 都是借用的基础 |
| [SYNTRA，NeurIPS 2025](https://arxiv.org/abs/2509.17393) | 在有限程序假设空间上选查询、用模型预测裁决 | 对称假设加少量模型 oracle 也不能单独声称新颖 |

可以争取的研究贡献只能收窄为：**从 validation 暴露的局部分歧出发，把值/出口/别名上的可区分性作为可反向传播的需求，联合合成测试的构造前缀和观察后缀，减少无区分力的组合搜索。** 其中“别名差异经写读转为公开差异”是具体机制之一；它不是关于所有 combination 的完备理论。

是否足以构成新颖贡献尚未确立。必须正面比较联合合成、标准差分输入生成和状态序列搜索；若同预算常规工具达到相同效果，应接受该方向的贡献不足，而不是继续加关系名称。

## 10. 最小验证方案与指标

现有 17 条全部为发现集。先做无需参考补丁/目标标签的构件提取和推导审计，再冻结算法，在新的仓库/任务上评价；不能将人工填写本表当作自动提取结果。

只回答四个递进问题：

1. **有用分歧获得率**：17 个目标中，有多少能由事前固定的历史/表达式/模型来源给出涉及目标机制的可执行替代？三来源分别计数，未获得者仍留在总分母。由评价者事后判断“涉及目标”，不把标签送给生成器。
2. **区分合成率和成本**：给定同一组分歧、文法和预算，多少得到稳定、公开可观察的区分测试？报告全部给定分歧数、成功数、执行次数/时间；不能只保留本来已知可区分的分歧。精确 WP/摘要支持与具体成对枚举 fallback 的成功数、成本分别报告，防止枚举收益被误写成反向分析收益。
3. **真实缺陷检出与误报**：完整 trial 检出率、已独立确认的报警 precision、未确认项数量、未解原因。分歧不是 bug；17 个筛选正例不足以估计总体误报率。
4. **修复收益**：相同 agent/预算下，有无新增有效测试的配对 issue resolution rate。生成失败测试不自动等于修复成功。

必须分开记：历史脚本重放、新上下文生成、已有场景的 oracle 修正，避免 N06/N05 被混入新增组合成功数。

最关键消融使用**相同假设与文法**：固定输入只找观察；固定观察只改输入；无反向需求的类型引导搜索；去掉 alias 信息的联合搜索。另设同预算模型直接生成测试，以及旧 4/17 原型。这样才能看出收益来自新搜索、假设来源还是更多计算。

本轮交付到方法设计与原证据校正为止；没有新的实验成绩。若下一步无法给出自动产生的完整推导树，或 LLM 局部替代比直接测试更贵却没有额外收益，就不能把这份提案升级为成熟方法。
