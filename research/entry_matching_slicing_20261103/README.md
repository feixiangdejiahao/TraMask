# 入口、匹配与切片的联合实验

在全部 **88 条 trajectory、58 个任务**上，较好的方案是：**用调用位置和源码输入位置找历史代码，把同一验证测试的多个相关命中合在一起切片，再通过命令和文件来源连接其他材料。** 字段、变量、初始化和断言可以由依赖关系补进来，无须分别作为入口。

本轮比较了 12 种匹配点特征、14 组入口与切片设置，并用两种切片器比较主要设置；另外比较了 6 种命令与数据材料的匹配方式。全程使用确定性规则，没有新增 LLM 调用。

88 条全部参与规模统计。128 段人工引用分布在其中 79 条轨迹；另外 9 条没有现成的历史引用，逐任务表中记为 0。

**入口数量和切片数量分别减少了多少？**

下面各行使用相同的历史版本和当前切片器。代码引用的分母是原来能按代码定位的 98 段人工引用。

|处理方式|入口组|不同的切片结果|覆盖代码引用|
|---|---:|---:|---:|
|每个匹配语句单独切片|111,423|48,488|95/98|
|匹配点只保留调用和源码输入|94,386|41,142|95/98|
|再合并依赖连通的匹配|38,295|36,105|95/98|
|同一验证测试共用多个依赖末端，并保留注释和源码结构|**30,282**|**28,882**|**98/98**|

相对第一行，入口组减少 **72.8%**，不同切片结果减少 **40.4%**。切片中累计携带的源码由 **70.85 MB 降至 53.48 MB，减少 24.5%**；累计语句引用减少 29.9%。需要构建依赖图的源码版本只减少了 5.0%，所以这些比例不能直接解释为运行时间的降幅。

匹配表达式的位置由 179,666 个减少到 123,420 个，减少 31.3%；多个表达式可以属于同一语句，因此归并后的语句数更少。此前 D 报告中的 70,382 按函数或代码单元计数；这里的“入口组”按共同进行一次切片的语句集合计数。

**具体如何匹配和切片？**

以 `query.execute()` 为入口时，D 用其调用名及已有的来源约束，在历史源码中定位调用位置。每次命中都保留历史版本和源码偏移，再回到对应材料做切片。同一文件在改写前后的版本分别处理。此次调整主要改变命中后的归组和依赖扩展，而不是要求每段历史证据都直接包含 `execute`。

1. 沿用 D 从 issue、Patch 和历史编写来源得到的任务查询，在每个历史源码版本中找调用位置和源码输入位置。源码输入包括交给解析器、解释器等操作的程序字符串。这条规则同时处理 API 和语言特性，不要求调用属于仓库自己的 API。
2. 同一语句上的多个命中先共用一个入口。原始命中位置和来源继续保留。
3. 从这些语句沿数据、控制和对象状态依赖向后续操作扩展，找到其影响到的末端。末端可能是断言、打印、状态操作或返回值。分支有多个末端时全部保留；循环按相互依赖的节点组处理，不枚举执行路径。
4. 同一验证测试内的末端共用一次依赖遍历，从这些末端向前补齐初始化、输入、控制条件和相关状态，同时连接 helper、调用者和测试 setup。不同测试保留独立入口组。无法识别测试边界的代码使用其词法作用域，并记录识别问题。
5. 保留选中语句附带的注释、定义文档和必要语法符号。它们不产生新的执行语句。

例如，一段历史测试可能分别命中 `createQuery()`、`query.filter(...)` 和 `query.execute()`。这三个位置影响同一次检查；共用一份切片即可带出 Query 的创建、配置、执行和断言。若随后有两个不同的检查，两条依赖都保留。

还需要处理另一种情况：一个测试先调用 `resetContext(...)`，再创建 `kea(...)`。两次调用的关系藏在库的全局状态中，单份历史测试源码未必能证明这条关系。S038 就出现了这种情况。把同一测试内已匹配的两个入口放进同一视图，恢复了此前被拆开的两段条件。

全部 94,386 个保留的匹配语句都能在所属组的切片中找到。30,282 组的共同遍历结果，与分别遍历各末端再合并的结果一致。

**哪些尝试效果不好？**

- **只用调用点，删除源码输入位置：**代码引用覆盖降到 78/98。语言特性测试经常把目标程序放在字符串中，仅检索调用名称会漏掉这些输入。
- **只围绕观察语句切片：**覆盖为 81/98。历史中有用的条件不一定已经连接到一个有效观察。
- **仅合并依赖连通片段：**保持了原有覆盖，但仍有 3 段代码引用未覆盖。S006、S038 说明，同一测试中的互补条件可能暂时没有被静态依赖连起来；S041 还要求保留与代码相邻的注释。
- **只依赖单文件的局部切片：**采用相同的测试分组和注释保留后，覆盖为 95/98。加入上下文连接后为 98/98，补齐 S019 的回调与类型检查、S059 的 helper 调用者与错误检查，以及 S082 的测试 setup。

实验也修复了切片器中暴露的遗漏：Rust 属性与函数定义的连接、TypeScript 类型引用与回调读取的局部变量、Go 局部函数值的调用者、下标状态更新和 `defer`。另修复了依赖缓存被修改导致查询顺序影响结果的问题。这些修复应用于本轮所有比较条件。

**其余历史引用如何取得？**

128 段引用中，98 段属于原来可定位的代码，另外 30 段涉及追加代码、源码输入、输出、snapshot 等材料。本轮程序切片覆盖 **104 段**，其中包含上述 30 段中的 6 段。剩余 24 段通过材料入口取得。

|材料匹配方式|涉及的历史动作|与程序切片合计覆盖|
|---|---:|---:|
|只取源码入口所在的原始命令及输出|4,307|108/128|
|再取明确提及入口文件路径的动作|5,921|120/128|
|再取验证、程序执行和测试编写动作|7,468|126/128|
|再取包含任务查询名称的源码读取动作|10,603|128/128|
|改为补充含 JSON/XML 形式数据的读取动作|**8,721**|**128/128**|
|保留全部相关源码与数据读取动作|10,874|128/128|

只沿源码入口及文件路径扩展，仍会漏掉材料。比如 S056 的配置字面量和 S057 的 XML 输出出现在源码读取结果中。将读操作关联的命令或输出中的 JSON 键值、XML 结构作为材料特征，可以找到这两段引用，并比保留全部读取动作少处理 19.8% 的动作。

因此推荐把这些输入、输出和数据作为**材料入口**保留，按需读取；程序源码才进入程序切片。原始 B 材料仍保留。本批数据中，推荐的首轮材料范围包含 18,944 条记录，尚不能把它们全部直接转换成 typed graph。

**本轮结论与仍需解决的规模问题**

入口选择、匹配和切片应当联合设计。当前值得采用的改变，是减少重复命中，为同一验证测试保留多个互补入口，并让一次共同切片恢复它们的上下文。

每条 trajectory 的不同切片结果中位数为 **272**，95% 分位为 681，最大为 1,186。每份切片的语句数中位数为 **12**，95% 分位为 92，最大仍有 **1,487**。下一步的开销重点在大型 helper 和调用者上下文展开，以及材料入口的后续关联；单纯继续减少查询名称不能解决这些问题。

本轮使用原 trajectory 中的字面源码和归档源码版本，逐版本进行静态切片，没有重新运行 88 个 Docker 环境。128/128 表示引用内容在原始来源中被取得：104 段进入一份程序视图，24 段由关联材料补齐。候选先按公开输入保存，再用人工引用计分；这批数据同时用于发现问题和修订算法。

当前正式 D 的选择规则保持原样；联合策略已实现为可复跑的实验算法。通用切片器的依赖修复已生效，201 项 EviWeave 回归测试通过。
