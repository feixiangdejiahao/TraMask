2. 直接观察
O1. 这组 issue 主要是跨模块功能扩展。很多需求显式包含共享状态、优先级、缺省值、别名、对象隔离、时序、不同入口的一致性。原测试并非只测单一功能：T13 已测嵌套容器传递、克隆、共享闭包；T17 已测缺省、嵌套、参数与 rest；T28 已测数据/错误独立新鲜度。不能把研究动机写成“agent 不会写组合测试”。

O2. T17 需求只允许在位置或键不存在时使用 default。原测试区分空 map 与正常值，但未区分“键存在且值为 undefined”。compileDefaultBinding 以取出的值等于 undefined 决定 default。原始补测日志显示 {x: undefined} 被绑定为 50，断言预期为 Undefined。这是需求区别在内部表示和测试输入中被合并的具体例子。该日志支持原补丁行为；此阶段尚未核验 gold。

O3. T13 原传递测试刻意以同一 src 编译两侧；源码直接把原函数 bytecode 与目标 globals 数组配对。原始 A_final 补测通过增加目标前导 global 得到 0 而预期 100。另一原测试在 array/map 内复用同一个闭包对象；新 probe 改为两个不同闭包共享同一捕获变量，记录 inc=3、get=2。代码的 seen 表跟踪 Object，没有对应的捕获 ObjectPtr 共享复制证据。两个问题都与“测试中的对象/位置关系是否真能区分所声称语义”有关，但还需分别判定期望与 gold 兼容性。

O4. T24 原 JSON Schema 测试仅断言序列化文本含 if 和 then；这不证明条件语义正确。原 update 测试已经包含嵌套 savedAs，不能再把“未测 savedAs”当事实。生成模型曾提出 $set 缺失依赖的解释；实际 probe 先报类型错误，且还把 Go 的 t.Logf 写进 TypeScript。这不能证明目标业务分支到达。模型对“$set 提供了值但仍须原存储存在”的期望也需要独立需求依据，不能由失败反推。

O5. T28 原 trajectory 第 80 步把订阅 observer 后读取结果改为 getOptimisticResult，理由是避开挂载 refetch；最终测试确有这种选择。第 75 步把两个新建 Error 对象的 toBe 改为比较 message，这是合理的测试修正。第 81 步加 as any 绕开类型不兼容。可见同一历史里的测试修改有不同含义，不能把所有修改都解释为测试迎合实现。

O6. 原始诊断执行的 pass 可以只表示日志程序完成。T13 probe 没有比较 inc/get 的语义断言，日志明确 inc=3 get=2，但 D_probe 后续把 PASSED 当作撤回缺陷的理由。C_history 对同一场景生成断言后失败；E_observations 对同一日志也保留断言。这说明“执行完成”和“符合需求”必须是不同命题。T17 probe 反而直接调用带断言的 expectRun，表明同一个 probe 机制在案例间并不保证相同观测语义。

O7. T06 多个模型怀疑在真实执行后被正确撤回：内层 router 默认值、异常路径 tracking、大小写 header 均观察到所需行为。也有日期星期写错造成的假失败。局部未覆盖不等于缺陷，也不等于必须增加测试。

O8. T08 完整 patch 的 _parse_part 到输入末尾后仍返回 part；原 malformed-framing 参数集没有缺少结束 boundary 的输入。这是可疑的 framing 行为，但可能只是单条件缺陷，不能硬归入组合机制。未运行新测试，也未核验 gold；此项是静态候选，不能算已发现 bug。

O9. 实际运行以原镜像 base commit 校验开头，git apply submitted patch，然后复制生成测试并运行 native harness。历史 edits 作为文本恢复，不逐条执行。正确表述是“恢复提交补丁状态后补测，并利用历史记录作为可选证据”，不是“完整重放 trajectory”。它不保证保留原会话临时文件、动态进程、依赖变更或环境状态。

3. 候选解释，不是已证实因果
H1. 有研究价值的核心可能是“恢复需求要求的可区分性”：原自测在具体输入、状态构造或断言下，把两种需求上不同的行为视作同一情况。补测应提出一对合法且有明确语义关系的情境，证实区别确实被建立，并在公共可观察结果上验证关系。T17、T13、T24 给出不同链节的例子。
H2. 程序分析可提供对象关系、值流、调用路径、分支、断言依赖与执行证据；它不能自行决定需求是否要求两种情境等价或不同。LLM 可提出语义关系、构造候选和补全语义，但会错认路径、合法性和执行状态。应让双方通过可检查的中间对象循环配合，而不是固定“分析先做所有事，LLM 最后判断”。
H3. 历史的主要价值可能是暴露当前测试为何局限于某种构造，而不是提供新的语义事实。T13 是线索；T28 的合理修改则提醒不要泛化。需要与同预算 final-source baseline 做独立消融。
H4. 另一可能方向是“自测与实现共享错误假设”。目前没有独立人类/另一个 agent 编写测试的对照，不能声称这类相关错误是 agent 独有，或比普通开发者更多。

4. 主要未知与下一步核查
尚不知道：固定目标集合是否充分；旧标签是否把合法输入/正确 oracle/原补丁失败/gold 通过混合在一起；同一缺陷的多条输出数量；probe 表现是否跨任务一致；原测试有多少确实运行并通过；补测是否改善后续 repair/resolution。
需要先看旧数值的评价单位和分母，再把它们放回具体输出核查。不因旧标签判错而改变本文件。后续问题抽象必须声明范围，保留不适用和不确定类。最小可行 pilot 应先证明“合适的语义区别 + 可执行见证 + 独立期望”能稳定提高有效发现率，再讨论修复增益。
