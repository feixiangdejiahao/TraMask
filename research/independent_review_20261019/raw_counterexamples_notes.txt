memory 测试通过与这一候选不冲突。它们在已选后端上确实验证了许多行为。原测试不是总体薄弱，而是适用范围有限。

观察：一个测试的名字强于实际区分力。
step 80 的 C180–194 标为 dead_letter_max_hops discard，设置上限 1。第一次到 dlq 后，又从没有 DLX 的 dlq 调 dead_letter。最终断言仅是原 x-death count 仍为 1。最终补丁 420–425 行在跳数检查 437–442 行之前就因没有 DLX 返回。因此该用例的第二次调用不能确认跳数上限导致了丢弃。去掉跳数上限逻辑，这个用例仍可能通过。
这是可直接解释的验证不足，不是“上限代码有 bug”的证据。源码的累计上限检查本身看起来合理。适当补强应给第二个队列配置有效 DLX、避免同时触发回路保护，并观察应丢弃的下一跳。不能只增加 hops 数字而保留那个提前返回条件。

推断：不宜把本例强行做成组合覆盖正例。
该任务的主要空间是字符串语法、分类优先级、数值精度与比较关系。可以组合符号、指数和单位生成输入，也可以用变形关系检查排序；但这不等于已证明 t-wise 因子覆盖是正确抽象。传统语法边界测试和性质测试在这里就是强对照。
原自测已经跨类型且包含多种等价表示。只增加若干类别对，可能大部分重复现有能力。若后续方法有效，应说明它找到了哪一个此前不可区分的分类或比较边界。

推断与边界
公开描述“may return a replacement”有可能意味着无替代返回时保留原实例，但给定 API 示例又显式 return instance。仅凭这两句，我不把无返回 callback 情况确认为缺陷；这是需要先明确契约的候选。不能仅见 step 54 改测试，就断定它错误，也不能仅因测试变绿，就认定需求得到证明。

另一个有具体路径的静态候选是依赖图中的非初始化中间节点。
最终补丁 1184–1207 行先只留下带 initializer 的注册项，再把每项直接依赖过滤到该集合。若 A 有 initializer，依赖无 initializer 的 B，而 B 依赖有 initializer 的 C，则 A→B→C 的约束不会在该图中成为 A→C。按登记顺序让 A 先于 C，则 A resolve B 时可能遇到尚未初始化的 C；若 C 已开始但尚未完成，A 也可能过早见到它。issue 要求依赖感知启动次序，因而这个候选比任意组合配置更贴近图结构。现有测试只展示直接 initializer 依赖链。
本次未运行该候选，也未检查 gold。实际 parser 能发现哪些依赖、需求是否包含这种间接路径，还需后续验证，不能当成已确认原补丁失败。

另一个需语义裁决的观察是 1103–1112 行在 await initializer 前标记 initialized，892–897 行 resolve 只检查这个标记。原测试对 resolve 的禁止主要发生在 initialize 之前，没有在初始化 pending 时外部 resolve。本次不把“uninitialized 必然涵盖 pending”当成已经确认的 oracle，也不据此声称异步并发有缺陷。

反例价值
本例足以说明“错误处理、scope、并发、初始化顺序都没交叉测”的说法不成立。方法若只按这些词挑场景，会重复既有测试或生成语义未定义的断言。应先确定具体状态/图形态和公开可观察结果，再判断是否值得补强。

与此相反，step 97 发现 Or(Added(p()), Added(q())) 每次都新建身份导致每次都是首轮结果，遂把 query 保存一次并复用，同时保留第二次应为空和后续 b 转移的断言。这项测试修改有合理语义依据，而且增强了对持久状态的检查。不能把全套测试概括成“每次重置所以完全不测状态”。

观察：延迟求值用例的观察时点不足。
1495–1510 行只有一个实体，callback 只写入数据，断言在 updateEach 返回后检查 callback 看见过该实体、另一个新 query 已不匹配。即时求值与末尾求值都可能给出这两个结果；该用例没有直接观察 predicate 执行相对于迭代的时点。提交源码 query-result.ts 68–123 行包含 snapshot、callback、写回与最终 flush，源码与要求表面一致。本次没有确认错误，只确认当前断言不足以证明延迟策略。
应考虑观察调用顺序或跨 callback 可见状态，而不只是把实体数量从一加到二。测试要明确其能排除哪一种提前求值行为。

观察：删除/修改测试的原因不能只看失败标签。
step 95–96 删除 entity.set 发生在 updateEach callback 内的变体。该 callback 的 Health snapshot 后续会写回，可能覆盖 entity.set 的直接 store 写入。提交源码 query-result.ts 72–73、103–109 行支持这种执行顺序。因此该历史失败并不自动证明谓词延迟失效；应先隔离写回语义。

静态候选与未知
1034–1055 行把 per-entity 上次谓词状态更新放在各组的遍历中，并在某个 AND 组未匹配时立即返回；后面的 tracking 组可能没更新状态。runQuery 613–621 行只在查询时计算谓词转移。这提示可调查多个 tracking 组、两次查询之间的多次真值变化、关系筛选与状态记录的相遇。但“Changed 是否要记住两次查询间已往返的瞬态”和组合组语义需要公开 oracle 支持；本次未执行，不计作缺陷。
同样，fresh query 的断言弱，并不等于复用 query 一定失败。将新鲜/复用实例作为配对测试很有价值，但通过也应作为反证保留。

可迁移特征与方法边界

本组最可靠的共同点是：修改涉及的不只是输入取值，还涉及解释输入的程序路径、状态持有者和观察时点。测试可以有许多条件，却仍无法确认想验证的那个因果环节；测试也可以很少，却对该环节有很强的区分力。

适合程序分析做的事情较具体：定位被测 API 的实际 dispatch 和后端 override；识别 factory 在断言前重新创建身份；从控制流发现更早的丢弃条件；连接 mutation、snapshot 写回、flush、断言的先后；提取图构造在哪一步过滤节点。程序分析给出路径和依赖，不负责凭空决定需求语义。

LLM 可以把 issue 的行为要求映射到具体可观察结果，判断路径变化是否合法，审查候选 oracle，设计能区分当前自测与替代错误行为的最小场景。它也必须允许输出“现有验证已覆盖”“需求不明确”“只是测试质量机会，未证实缺陷”。不能用“生成了更多组合”代替这一判断。

本组不支持以下结论：四项都存在同一种组合缺陷；没有旧目标的任务是无缺陷负例；原自测全部是浅层 happy path；测试修改普遍降低正确性；只要发现缺一个组合就能提升真实修复率。没有运行修复后的 resolution 实验，也没有独立金标准。

建议父线程保留三种不同的后续结果：公开契约支持且动态区分的缺陷；补强了原测试证明力但两版都通过；语义不明确或候选在实际路径上不成立。T15 可作为必须允许“不适合当前组合抽象”的反例，T23 可作为必须尊重已有强验证的反例。仅凭四项指定样本不能估计这些现象的总体发生率。
