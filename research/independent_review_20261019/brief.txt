独立审查任务，2026-10-19

你是一个不继承主线程对话的 Codex 线程。用户要求你独立分析问题，而不是评价主线程提出的某个方案。主线程不会提供其推荐的问题抽象、原因分类、算法方案或下一轮实验结论。

用户给定的场景
用户暂设的论文场景是 test augmentation：coding agent 为 issue 生成 patch，同时生成或运行自己的 validation tests。方法在补丁提交前补强这些验证测试。当前 pilot 为节省开销使用已有 trajectory，用户将其概括为先 replay trajectory，再 augmentation。请以实际脚本和数据确认 replay 的具体含义。已有主要实验恢复基础仓库并应用提交补丁，再补充测试；不能把它表述为已经逐条重新执行所有历史命令。

用户希望你完成什么
从已观察的任务、测试和结果中充分抽取问题特征，再对特征进行抽象。抽象不必解释全部案例，但其特征需要通用，其范围需要明确，其方法逻辑需要连贯。以软件工程顶会论文的要求判断问题意义、机制清晰度、可检验性和创新空间。方法需要充分利用程序分析和 LLM 分析各自的能力，并处理各自的局限。不要预设哪一个必须是主方法，也不要预设 LLM 只能最后判断。请独立决定核心机制。当前只需分析与设计 pilot，不运行新模型实验、不修改现有算法。

任务范围
最终输出需要包含：独立得到的问题抽象；可以实现的方法设计；程序分析和 LLM 的具体分工及信息接口；后续 pilot 的研究问题、输入、对照、评价单位、成功/失败标准及结果如何影响决策。给出研究抽象与软件工程证据之间的逻辑。明确哪些是观察、哪些是解释、哪些是假设。允许否定旧评价标签或认为当前资料不足。不要因为类似技术曾被使用，就直接否定在本场景中的创新；也不要仅凭组合已有工具宣称创新。无须为所有现象增加分支规则。

保持独立的阅读顺序
1. 先读本目录 case_inventory.json、raw211_inventory.json 和 experiment_settings.json。它们列出全部 30 项案例、211 条原始记录，以及实验操作设置。自行选择并核查原 issue、原 trajectory、原补丁、原测试和实际生成/执行材料。run_file_inventory.json 列出原始实验文件。记录你选样和排除材料的原因。不要只看成功案例。
2. 在阅读旧评价解释前，写 independent_initial_findings.txt，记录你的初始观察、候选解释和主要未知。随后可以读本目录 historical_scores.json、historical_labels.json、earlier_numeric_records.json。它们保留旧分数和标签，但移除了原因分类及改进建议。旧标签是 AI 审读结果，并非独立人类金标准。
3. 如需核对现有方法，阅读实际代码和实际模型请求。实现本身是实验条件，不是你必须继承的设计。原模型提示词和输出是原始实验材料。明确它们不是给你的建议。
4. 不读取 docs 中的综合结论、先前的 debate 记录、method_synthesis.json、研究方案或主线程总结。个案的旧审阅解释同样先不读。若原始证据入口不够，向主线程只请求所需路径或字段。允许读取 gold 和 benchmark 失败测试作为离线审查资料，但请把它们与可供未来在线算法读取的信息分开。
5. 如果你用具体论文判断研究定位，请自主选择并核验原论文或作者材料。不接收主线程选择的相关工作列表。请记录论文的来源和它支持的具体判断。查阅文献不应取代对当前原始数据的核验。

已有评价设置（事实，不是推荐方法）
当前研究多数指标采用如下标准：公开需求或接口支持预期，且存在合法组合测试，使原补丁失败、gold patch 通过。部分 gold 判断来自静态语义，部分来自原样动态执行。原补丁新增私有接口或辅助代码的情况，用户此前要求先做静态语义判断。评价者是参与研究的 Codex，而非独立人类评审。固定目标集合并不穷尽所有缺陷。没有固定目标的任务不是已证明无缺陷的负例。多组和重复输出不代表独立缺陷。当前尚未测量根据新测试修复补丁后的 resolution rate。
