独立研究审查：补强 coding agent 的验证测试

2026-10-19 · 原始材料优先 · 初始观察先于旧评分冻结 · 未运行新 provider 实验


1. 主要判断
────────────────────────────────────

值得继续做一个有退出标准的机制 pilot；现有证据还不足以确认一篇技术论文的核心贡献。 我建议把问题收敛为：从 agent 已有的验证中，找出需求所要求、但当前测试尚不能区分的行为情境，并生成有明确预期和执行见证的对照测试。研究对象是“验证的区分能力”，而不是笼统的组合数量。

这里的“区分”指：测试能够排除一个具体、违反公开需求的替代行为。例如，缺失字段才用默认值，与字段值为 undefined 就用默认值，是不同语义；重新创建查询后得到正确结果，与已有查询能随状态变化正确更新，也不是同一项保证。已有测试可以很长、调用很多 API，却仍没有区分这两种行为。反过来，一个短测试也可能已经充分检查某个具体义务。

原始材料支持这一问题有现实实例，但不支持“agent 普遍只写正常路径测试”“测试编辑普遍迁就错误实现”或“组合覆盖不足是统一原因”。T15 的排序测试和 T23 的初始化测试已经很强；T02、T29 的原验证还真实发现了交互错误。没有人写测试的对照组，因此也不能把现象宣称为 agent 独有。[E6]

可探索的方法贡献应是一个可计算的连接：把需求关系、原测试的实际执行条件、对照场景以及最终观察绑定起来，让程序分析改变测试选择和修复决策。LLM 负责解释语义和构造场景；程序分析负责定位真实路径、身份、数据依赖和可检查的执行条件；执行器按冻结的关系判断结果。各自的输出都应留下可反驳的证据。仅把现有提示词改成结构化表格，不构成足够的技术贡献。

新颖性门槛较高。PROBE 已用存活程序变体引导补测，TestJack 已按需求与候选补丁生成反例；PANTA 已把静态路径、动态覆盖和 LLM 迭代结合；Otter 已在生成时不读取 gold。线上没有参考实现是重要约束，却不是单独的新意。下一轮必须证明：某个具体诊断信息在相同上下文和预算下，提高了新增有效缺陷的发现，而不只是测试数量、覆盖率或格式正确率。

3. 从原始证据得到的问题特征
────────────────────────────────────


3.1 最强正例：测试覆盖两种值，却漏掉“存在性 × 值”的语义区别

观察，T17：需求说默认值仅在键或位置缺失时生效。最终提交的原测试检查空对象得到 50，以及对象中的 x=10 得到 10。实现 compileDefaultBinding 在取值后与 Null/undefined 比较，于是“没有键”和“键存在但值是 undefined”进入相同处理。补测使用 {x: undefined} 并期待保留 undefined，候选补丁却给出 50。[E1]

本审查核对了已保存的同一补测 artifact、候选/参考执行结果和 Go 日志：candidate 失败，gold 通过。测试文件哈希与 artifact 标识一致。这是本审查直接核实的动态反例。该命名测试还包含数组场景，但候选在对象断言处先失败，不能说本次日志已经逐项动态确认数组分支。

解释：原测试并非没有默认值测试，而是没有把“字段存在”与“字段值”分开。补测的关键不是多加一个任意取值，而是从需求选择一个能区分两种语义的具体见证。这也是程序结构与需求解释需要互补的地方：代码比较的是值，需求限定的是存在性。


3.2 对象图关系比组合词更有解释力

观察，T13：原自测已经涉及 clone、函数转移、嵌套容器和捕获变量。跨实例测试使用相同源码布局；嵌套测试重复放入同一个 inc 闭包。另一个 inc/get 共享捕获变量的测试只在原实例里执行。最终实现对同一个函数对象做了 memoization，却为不同闭包的自由变量分别建立新指针。两种闭包共享一个变量这一对象图关系，不能由“测过嵌套数组和 map”替代。[E2]

原始 probe 将共享 n 的 inc/get 一起转移。日志得到 inc=3、get=2；probe 只有日志，没有检查两者应一致的断言，所以测试框架给出 pass。同一草稿加 probe 状态的 D 组撤回缺口，去掉框架成功标签、保留观测值的 E 组又保留缺口。这是具体反馈误读的证据，不是“所有运行反馈有害”的证据。gold 的静态实现显式 memoize 捕获指针，为共享关系提供支持；本审查没有把它升级为新的动态 gold 对照。

另一个跨不同全局布局的候选虽在 agent patch 上失败，但参考实现是否支持按名称重定位也成问题。它不能和上述共享捕获反例混在一起。原轨迹还出现过临时放宽嵌套测试预期，最终补丁又恢复更强断言并修复了部分共享情况；只截取中间步骤会错误描述最终行为。


3.3 程序执行成功、前提成立和需求成立是不同事实

观察，T24：原更新测试已经覆盖嵌套 savedAs 路径和 requiredIf 条件；不能说这些交互完全没有测试。另一方面，已核查的最终 JSON Schema 测试只检查生成文本含 if/then，没有检查它实际接受或拒绝哪些对象，说明该测试的输出结构检查不等于行为检查；本审查没有穷尽所有临时验证。[E3]

某补测用 $set 包装 string 字段，probe 在进入目标业务路径前就报“应为 string”；代码甚至混入了 Go 风格的 t.Logf。该目标的 candidate 与 gold 都失败。随后模型仍从源码“不对称”推断缺陷。它说明：没有建立合法场景，就不能把异常当作目标语义的反证；删除 pass/fail 字样也不能自动解决这一问题。

观察，T28：轨迹中把 Error 实例身份比较改为消息比较，有合理依据。把订阅改为 optimistic result 避免 refetch 则改变了观察环境，可作为下一步核查线索，但本身不是缺陷证据。旧补测还要求保留最大失败计数、对某些 error-only snapshot 恢复错误状态；这些预期或输入前提不能仅从实现差异推出。对 invalidation 合并的语义也应保留不确定性。[E4]

3.5 观察、解释与假设的界线

• 已观察：原测试存在具体的条件遮蔽、身份重建、观测粒度不足以及语义预期不确定；也存在强验证、合理 oracle 修正和原自测发现错误的案例。

• 解释：有些自测把需求允许的多个情境压缩为同一种可观察结果，因此通过不能支持更宽的需求结论。该解释能连起上述若干案例，但不是所有失败的统一原因。

• 待检验假设：分析这些压缩发生在哪一条路径、哪个状态持有者和哪个观察点，再按公开契约生成小幅对照，比同预算的普通补测更有效。

• 尚无证据：agent 比人更容易产生这种问题；历史推理必定增加有效信息；该机制能提高最终 issue resolution rate；所有无固定目标的任务都没有缺陷。

实际 local_slice 主要找最小语法单元、标识符、同一函数前面的赋值和包围 guard；它没有完整处理别名、可达性、调用分派或需求语义。旧计算组未占优，不等于程序分析普遍无用；但也不能继续只提供同类片段，再期待换个概念名称就得到新机制。[E9]

“被旧评价拒绝”不应直接等同于“公开需求证明这是误报”。例如 candidate/gold 都失败，可能是非法测试，也可能是 gold 没实现某项需求；私有辅助 API 的不匹配又是另一个问题。后续应分别记录需求成立性、候选行为、参考兼容性与失败原因。本次确实核实了 T24 的前提问题；并未复审全部 104 个拒绝标签。

当前数据没有测量用新测试继续修补后的 resolution rate；固定缺陷集合也不完备。因而既不能报告总体召回率，也不能把“未命中固定目标”直接判为没有价值。前缀 1 和前缀 3 是同一批输出的嵌套统计，不能当成额外独立试验。


5. 建议的问题抽象：需求约束下的行为区分补测
────────────────────────────────────

给定公开 issue R、最终候选补丁 P、可恢复的原验证 S，以及可选的历史 H，目标是在有限预算内增加测试 ΔS，使其检出 P 对 R 的残余违反。生成与在线决策不能读取 gold 或隐藏测试。输入单位是一个 issue 与一个最终 patch；新增测试必须在这个最终状态上建立证据。

核心对象称为区分义务：它说明需求要求哪些合法情境保持相同、产生不同结果或满足一个明确状态关系，以及原验证为何尚不能检查这个关系。一个义务至少包含以下六项；缺少语义来源或合法构造时，应保持未决。

字段 | 含义 | 谁提供或检查

r：需求依据与范围 | issue/公开文档的具体位置；对象、生命周期、允许输入与例外。 | LLM 解释并提出；离线评审核对。实现本身不能给自己定义正确性。

s：原验证锚点 | 最终补丁上可运行的种子测试、命令或明确可恢复的临时代码。 | 程序定位与执行确认；缺失或不可恢复要记账。

c₀、c₁：合法对照 | 一个原情境和一个最小改变的情境；改变可以是值、实例共享、调用历史或公开后端。 | LLM 设计；分析绑定符号、检查构造，运行见证实际变化。

φ：应满足的观察关系 | 明确等式、不等式、顺序、保留/隔离或条件行为；不允许“可能不同”之类不可证伪说法。 | LLM 从需求提出，在看目标执行值前冻结；执行器计算。

w：执行见证 | 公共前提成立、目标状态确实形成、相关调用确实发生、观察值确实取得。 | 静态事实与动态事实分开；未知不能自动填成真。

g：原验证的具体不足 | 例如被提前返回遮蔽、每次新建状态持有者、观察不到所要求的区别。 | 分析给出可查的源码/轨迹位置；这是补测机会，不是缺陷判决。

O = (r, s, c₀, c₁, φ, w, g)
有意义的反例候选 = 输入前提成立 ∧ 对照确实实现 ∧ 观测到位 ∧ ¬φ
“原测试通过”不推出 φ；“进程成功退出”也不推出 φ。
φ 的需求有效性是独立的语义条件，不由上述执行公式证明。

T17 的义务把缺失与显式 undefined 分开；T13 的义务在转移后保留容器内部共享关系，同时隔离原实例；T29 的义务在复用状态持有者时验证更新，而不是每次重建；T02 的跳数义务先排除更早的丢弃条件。这些不是一份闭合缺陷分类表，而是同一过程的不同实例：先确定应有关系，再建立能观察该关系的合法情境。

“组合”可以作为某些对照的构造手段，但不作为充分性标准。两个功能名、多个布尔因子或较高 t-wise 覆盖都不能说明 oracle 正确，也不能说明目标路径被执行。对一个单值解析错误、纯环境故障或没有可恢复种子的任务，本抽象可能不占优，应允许交给普通测试生成或报告不适用。

这一抽象与传统测试充分性、蜕变测试和故障传播理论相通，不是新的故障理论。它在本场景中的研究价值，取决于能否从 agent 已有验证中计算出有用而且可靠的选择信号。如果只将“测试不足”换成“区分不足”，或让 LLM 自己填写全部字段而无程序核验，就没有完成这个要求。


6. 可以实现的方法与信息接口
────────────────────────────────────

建议先实现一个受限系统，暂不做任意语言的全程序证明，也不先枚举庞大因子空间。第一版使用现有 Go 和 TypeScript 测试 harness；只支持局部调用、显式对象身份、顺序事件和可公开观察的字段/返回值。需要反射、复杂并发调度或不可见内部状态的目标保留未知。

流程：需求 + 原验证 → 区分义务 → 程序绑定与见证 → 对照测试 → 分项反馈


6.1 恢复最终状态，建立有边界的种子集

验证 base commit，应用最终 agent patch，恢复能够从文件或轨迹命令无歧义抽出的自测。记录文件哈希、依赖、执行命令与测试名单。对历史临时测试，先核对它是否还适用于最终 API；任何语义改写都产生新版本，不能沿用历史 pass。若原验证在恢复状态已经失败，该失败属于原可发现问题，不计入新增缺陷。无法恢复则记为不可用，不能默默退化后仍称自测增强。

现有 runner 实际进行的是基础镜像/提交核对、git apply 和测试注入执行；没有逐条重放历史 trajectory。它节省重新求解 issue 的费用，但无法保证重建历史安装、临时文件、服务状态或每次中间代码版本。新 pilot 应继续采用最终状态恢复，并准确命名这一过程。[E7]


6.2 从需求和原验证提出有限义务

第一次 LLM 调用最多提出 3 个义务。每项必须绑定公开要求、原测试锚点和一个具体替代行为；同时写明为何原断言不能区分它。优先使用 issue 中明确的 only、preserve、independent、after、equivalent 等约束，但不把词表当作正确性规则。对“期望依惯例如此”的候选，应找文档或弃权。trajectory 可用于发现测试重置、预期变动与环境收窄；它不是 oracle，也不是第一版必需输入。

φ 和目标输入前提在看到对照执行输出前保存版本。模型可以在独立语义复核后提出新的 φ，但必须作为新候选计费和评价；不能看到 2 就把 3 改为 2 后宣称确认了原要求。合理的测试修正仍被允许，只是不能混淆其证据角色。


6.3 计算“原验证实际做了什么”，并用它约束下一步

用语言前端解析修改范围、种子代码和直接依赖。建立函数/字段符号索引、局部 def-use 与控制依赖、测试 setup—调用—观察之间的关系；对 factory、容器缓存或 clone 路径保留实例标识和创建位置。Go 可先用 go/ast 与类型信息，必要时扩展局部 SSA；TypeScript 使用 compiler API。库调用无法解析时显式标 unknown，不伪装成完整别名或全程序分析。

按义务选择少量运行观察点：公共包装器的调用/返回、显式对象或查询标识、目标 guard、事件顺序和断言输入。首先在种子上采样，形成附来源的事实表。若要插桩产品代码，只记录不改值的局部事件，并用原测试确认未改变结果；复杂插桩不成立就退回测试层观察。观测只说明这次执行，不外推所有路径。

分析产物 | 可执行的计算 | 对生成决策的具体影响

遮蔽条件 | 从目标操作向上找控制依赖和先行 return；与种子轨迹对照，识别先发生的退出。纯局部 guard 用小域枚举求可满足组合。 | 修复 setup 以先通过已有 guard；T02 的上限测试必须建立有效下一跳，不能只改变 hops 值。

状态持有者与身份 | 连接构造调用、变量定义使用、cache key 和后续操作；运行时比较标识或用公开行为见证共享。 | 决定应复用还是新建实例；T29 需把已有查询跨 set 保留，T13 需区分同函数重复与不同闭包共享捕获。

语义输入到实现判据的绑定 | 将候选前提中的字段存在性、取值或事件绑定到实际 lookup、比较和分支。程序不自行发明所需语义。 | 寻找能区分需求谓词与实现谓词的输入；T17 选择“存在且 undefined”，而非再加一个普通非空值。

观察依赖与时点 | 检查断言使用的表达式、事件发生顺序和可达观察点；无法证明依赖时标记为待动态见证。 | 决定要增加哪个公开观察或在哪个时点观察；T24 从文本含关键字转为 schema 对合法/非法对象的行为。

这里的计算目标不是返回更多源代码。输出必须能改变一个具体决定：排除不可达候选、改变最小输入、选择要保留的实例、添加必要观察，或者认定当前证据不足。如果程序只做文件检索，论文应如实称检索增强。


6.4 生成小幅对照，并检查“对照确实发生”

第二次 LLM 调用接收义务与事实表，输出基于种子的最小变换和可运行测试。先支持一个小的关系表达式集合：相等/不等、数值比较、序列顺序、集合包含、字段保留与条件分支。复杂自定义谓词保留完整代码和来源，单列可信程度；不假装由类型检查证明了语义。

程序检查实际符号、类型/导入、fixture 构造与关系表达式所引用的观测槽位；再执行控制情境和改变情境。见证 w 检查测试没有在前置解析处失败、确实复用了指定对象、触发了相关调用，或实际形成目标状态。无法机械检查的 API 合法性仍由公开规范支持和离线评审决定，不能把 runtime 不报错等同于合法。

多个候选的优先级先按语义依据明确、绑定可完成、具体对照尚未被当前种子见证、预计成本较低排序。对于这份有限义务集可以做贪心去重，不宣称完成全空间覆盖。“已有覆盖”仅指同一义务及其具体前提已被检查，不能由一个样例推断该性质普遍成立。


6.5 将反馈分为事实，避免框架状态替代语义

execution_record = {
  build_ok, process_exit, setup_ok,
  witness: {required_call, context_change, observation_available},
  values: {before, after, control},
  relation_id, relation_value, relation_source,
  unresolved_bindings, environment_errors
}
if not setup_ok or not all(required_witnesses):
    outcome = "场景未建立"       # 修复 setup；不能报目标缺陷
elif relation_value is None:
    outcome = "尚无语义判定"     # 日志完成不等于性质成立
elif relation_value is True:
    outcome = "本次义务通过"     # 不推出整项 issue 正确
else:
    outcome = "需求违反候选"     # 带语义来源；仍需评估 oracle 正确率

第三次调用只能基于明确失败环节修复一次测试构造，或者撤回候选；第四次用于审查最终证据、去重和输出。关系执行由机器完成，避免让 LLM 从测试框架的 PASS 重新猜一次语义。T13 的纯日志 probe 应显示“执行完成、观测 inc=3/get=2、已冻结关系不成立”；T24 应先显示“场景未建立”。这些都是第一轮必须检查的机制单元，不是新缺陷计数。

在线端输出测试、需求依据、见证与限度。它不读取 gold，不宣称以一般形式认证自然语言需求。对语义歧义保持弃权，比制造一个看似确定的断言更符合目标。对于明确反例，最小化时必须保留输入合法性、见证和关系违反；最后在两个干净进程中确认可复现，成本计入预算。


6.6 三方接口与局限

参与方 | 必须交付 | 不能代替的工作

LLM | 带位置的需求解释、最小对照、可证伪关系、代码构造与对未知的说明。 | 不能因为实现这样做就决定应当这样做；不能把编译成功、打印值或旧历史推理视为语义证明。

程序分析 | 带符号/行号的静态近似、真实轨迹见证、可计算条件和未解析边。 | 不能凭局部切片判定需求正确性；不能把保守近似或单次动态轨迹当完整路径证明。

执行器与评价者 | 机器分别检查运行、前提、观察和冻结关系；离线评审独立判断契约、根因与参考兼容性。 | gold 通过不能独自证明 oracle 合法；LLM 复核不能冒充独立人类金标准。

和现有试验相比，必须新增的能力是：原测试执行与义务的符号级绑定、对照实现的机械见证，以及只修复失败环节的反馈。原来的 source 检索、有限模型、历史提示和 probe 输出可以保留为基线。上述新增能力是否值得成本，完全交给下一节的对照回答。


7. 相关工作与真正需要证明的新意
────────────────────────────────────

文献子线程在不读取项目方案的情况下自主检索。以下比较只使用原论文与作者/出版社资料；不声称完整覆盖领域。近期论文截至 2026-10-19；PROBE 使用 v2 名称，TestJack 按预印本处理。每篇的核验章节和版本另存独立文献笔记。

工作与原文 | 已经解决的相关部分 | 对本研究的约束

DCI · Danglot 等，2019/2020（https://arxiv.org/pdf/1902.08482） | 按变更选择原测试，再增强输入和断言；以变更前后执行差异显现行为变化。 | 复用测试、聚焦 diff 和对比执行不新；行为差异仍需需求判断。

TestGen-LLM · Alshahwan 等，2024（https://arxiv.org/html/2402.09171v1） | 对既有测试做 LLM 增强，经构建、稳定通过和覆盖增益筛选。为避免错误 oracle，排除首次失败的候选。 | 目标是可靠扩充回归测试；本任务希望揭露当前 patch 错误，不能直接采用必须在 candidate 通过的接纳规则。

PANTA · Gu 等，ICSE 2026（https://arxiv.org/html/2503.13580v2） | 静态 CFG 路径近似、动态覆盖、目标选择、LLM 生成和修复已经迭代结合。 | “分析 + LLM + 执行”不是贡献。其 fixed-version 覆盖/变异实验不能直接回答残余需求缺陷发现。

SWT-Bench · Mündler 等，v3 2025（https://arxiv.org/html/2406.12952v3） | 从 issue 与旧仓库生成测试，以隐藏参考修复评测，还用于筛选 agent patch。 | issue 测试化和补丁过滤已有先例；最终候选的增量缺陷应与原 issue 复现区分，过滤 precision 也不是修复率。

Otter · Ahmed 等，ICML 2025（https://arxiv.org/html/2502.05368v2） | 生成时只看 issue 和旧代码；结合 LLM 规划与规则检查/import 修复，并用于 SWE patch 筛选。 | 没有 gold 与规则/LLM 混合均非独有。需要证明使用现成自测带来的增量价值。

Rethinking the Value of Agent-Generated Tests · Chen 等，2026（https://arxiv.org/html/2602.07900v2） | 在 mini-SWE-agent 设置中研究自测行为与提示干预；创建频率变化没有产生统计显著的最终结果变化。 | 不能用多写测试代替有效性；结论限于该 scaffold 和干预，不能推广为自测增强无效。

PROBE · Li 等，ASE 2026 作者稿（https://arxiv.org/html/2604.01518v2） | 从参考补丁生成变体，诊断存活变体，再生成参考通过/变体失败的增强测试，审计既有 agent patch。 | “区分不足驱动补测”是极近先例。其参考实现承担语义锚点；把它换成待审补丁改变了正确性前提。

TestJack · Yao 等，2026-10-07 预印本（https://arxiv.org/html/2610.10619v1） | 原子需求、覆盖与 mutation 线索、逐补丁反例、reviewer 复核和 reference-world 验证。 | 逐候选需求审计已有直接先例。新方法须具体替代 gold 的哪一部分作用，并测错误预期与误拒绝，不能只换输入可见性。

Metamorphic Testing · Chen、Cheung、Yiu，1998 技术报告（https://arxiv.org/abs/2002.12543） | 从成功测试衍生下一组测试，使用输入/输出关系补充传统 oracle。 | 对照、关系与种子增强有明确传统；本文不是重新提出蜕变测试。原报告 PDF 文本抽取有乱码，本次仅据作者摘要核验这项基本定位。

Can ChatGPT advance software testing intelligence? · Luu 等，2023（https://arxiv.org/html/2310.19204v2） | 用 ChatGPT 提出蜕变关系，由领域专家判定；不少关系模糊或错误。 | 让 LLM 生成关系也不是新机制；关系来源、前提和错误关系的评价不可省略。

Ripples of a Mutation · Du、Palepu、Jones，ICSE 2024（https://superhangdu.com/publications/icse-24/conference-paper.pdf） | 分析到达、感染、传播、揭露的不同阶段，展示传播到测试也未必触发断言失败。 | “执行成功不等于有效检查”有理论基础。把反馈分项是必要工程，不应独自包装成新理论。

我认为仍可能成立的贡献：在无参考实现的提交前场景，从已生成自测中自动恢复一个有范围的行为区分摘要；将自然语言义务绑定到具体路径、身份和观察；据可执行见证约束对照构造及反馈，从而把相同预算用于更多合法、有效且增量的反例。这里是一个待证机制主张，不是已经完成的新颖性结论。

最关键的对照不是“有工具”和“没有工具”，而是：给普通 LLM 相同源码、测试、需求、运行事实和预算，仅移除所提出的绑定/见证计算，收益是否仍然存在。若差异来自额外上下文、额外调用或额外人工筛选，就不能归因于该机制。若普通需求清单加运行审查已同样有效，应停止把它作为独立技术主方法。


8. 后续 pilot：先检验机制，再扩大效果评估
────────────────────────────────────

以下为可执行的下一轮设计，不是已经运行的实验。预算数字是建议上限，须在运行前冻结；不得根据结果调门槛。当前工作只完成设计，没有调用新 provider、运行新测试或修改既有算法。


8.1 研究问题

问题 | 需要的证据 | 不够的替代指标

RQ1：能否可靠构造区分义务及执行见证？ | 独立评审接受的需求关系、正确符号绑定、合法前提和确实实现的对照。分别报告未决与不适用。 | 模型自己打高分；JSON 完整；多写一份计划。

RQ2：计算信息是否改变了有效决策？ | 同一候选草稿共享后分叉；有/无绑定与见证反馈导致的选目标、改 setup、增加观察、正确弃权差异。记录每次改变对应的事实。 | 仅发现更多代码；用 token 较多的一组胜出。

RQ3：是否新增有效缺陷并控制错误预期？ | 在同最终 patch、同预算下，按 issue 和根因去重的增量反例；需求成立率、误报、弃权、成本一并报告。 | 测试数量、覆盖增量、旧目标命中率或最终挑出的展示案例。

RQ4：是否改善实际修复？ | 另行用固定 solver 和追加预算，把测试交回后重新修补，并在隐藏评测上测 resolution 与回归。 | 本轮发现反例或拒绝错误补丁。RQ4 不属于当前最小 pilot。


8.2 第一阶段：8 项开发任务上的机制可行性

使用已读的 Go 四项 T11/T13/T15/T17 与 TypeScript 四项 T23/T24/T28/T29。它们包含确认反例、强原测试、合法性失败、语义歧义及未确认缺口；都属于开发集。先复用已有工件验证恢复与反馈解析，再对每项最多 2 个义务做一个共享草稿的两分支比较。两个分支分别获得原始执行事实，或相同事实加程序绑定/见证结果。8×2×1=16 次完整流程，最多 64 次模型调用；共享前缀可减少实际调用，不改变条件比较的解释。

预先抽查 T13 的日志 PASS、T24 的前置失败、T17 的存在性区分、T29 的实例身份；这些是正确性检查题，不作为新发现计数。开发阶段允许修复 harness 和分析器，但每次修复保留版本。若连已知证据的角色都无法稳定解释，应先修实现，不进入效果试验。

• 可行性门槛：至少 6/8 项恢复可用种子；最多 16 个义务中，至少 8 个被独立语义审查接受并实际构造出对照，分布于至少 3 个仓库。

• 事实可靠性门槛：抽查所有被系统标为“已验证”的程序事实，至少 90% 与源码/执行吻合；不允许把“setup 未建立”或“纯日志完成”作为语义通过。若没有足够事实，报告分母，不给稳定率结论。

• 机制门槛：至少 4 个义务出现可归因于诊断信息的正确改变，例如补齐 guard、复用对象、纠正观察时点或撤回非法目标；两位评审需能指出对应证据。

• 失败决策：若问题主要在种子恢复，先缩小到可恢复测试；若主要在需求关系，先研究 oracle 筛选；若分析事实错误多，降低自动化范围。不能同时增加多个补丁式模块后继续宣称原机制成立。


8.3 第二阶段：固定预算的配对扩展 pilot

从原 90 个去重 issue 中，排除本次语义审读的 30+6 组后，最多还有 54 组可供扩展。先按仓库与 issue 分组，排除重复尝试、近似 issue 和开发仓库泄漏，再冻结 24 个可运行任务；若 Go/TypeScript 范围内不足 24 个，则报告实际数或另取新数据，不把重复尝试充数。这个池可能已被项目早期人工/AI 审阅触及，至多称为“本次未用于设计的扩展集”，不能自动称为从未接触的最终测试集。正式论文还需新任务或独立封存数据。

先仅按任务身份和运行条件选样，不看新缺陷目标。保留无可恢复自测、超时与环境失败的 flow count；不能只报告成功运行子集。所有组使用同一最终 patch、同一恢复种子、同一公开文档范围和同一模型版本。gold/隐藏测试进入独立评价目录，在线进程不得读取。历史内容只作单独开关，第一轮主比较不依赖完整历史。

组别 | 输入与执行 | 检验什么

B0 · 原验证 | 直接恢复并运行原自测；无新模型。 | 确认增量基线，排除原测试已经能发现的失败。

B1 · 强普通 LLM 补测 | 需求清单、相同源码与种子、相同原始运行反馈；可生成和修复对照测试，无特定绑定/见证算法。 | 排除收益只是更认真提示、更多上下文或普通审阅。明确称 TestJack 思路的同信息改造，不冒称复现其完整系统。

B2 · 路径/覆盖引导 | 相同输入与预算，用可实现的局部路径和动态覆盖选目标；LLM 生成与修复。 | 比较结构目标与所提需求区分目标；称 PANTA 类基线，不冒称跨语言复现 PANTA。

M · 区分义务与执行见证 | 本报告第 6 节；原始事实、分析产物及使用情况完整保存。 | 测最终新增有效缺陷及成本，并结合阶段一解释作用机制。

主模型组 B1/B2/M 各做 2 次独立重复，24×3×2=144 次流程，最多 576 次调用。每次上限：4 次调用、累计 64k 输入 token、16k 输出 token、12 次测试进程、20 分钟墙钟；同一可变预算用于分析与重试。实际用量逐项报告，不能用相同“调用次数”掩盖 token、上下文或执行次数差异。若环境使上限不合理，应在看结果前统一修订。两个干净复验也计入执行预算。

按 task 配对，运行次序随机化；测试间清理状态。同一 issue 的重复和同一仓库的任务不当作独立样本。每轮最多 3 个义务、每个最多 1 个最终命名测试；主指标报告第一目标和全预算两个结果，明确二者嵌套。超时、无结果与弃权进入分母。

第二阶段优先保留 B1 作为最强对照。只有主效果有信号后，再在共享草稿上检查“移除计算但保留同片段/同观测”“移除见证检查”“历史开/关”。不宜一开始分裂出十余个小组，导致每组都无法解释。若方法后来使用 mutants，则必须加普通存活 mutant 引导基线；目前没有必要为贴近文献强行加入 mutation。


8.4 评价单位、有效性与去重

单位/指标 | 具体定义

主要单位 | issue–最终 patch。报告两次重复各自的成功，以及固定两次预算下是否至少新增一个有效缺陷；不要混淆二者。

增量有效缺陷 | 原可恢复验证在最终 patch 未揭露；新增测试有公开契约支持、输入合法、观察指向相关行为；候选可复现失败。按同一根因与修复范围去重。

证据等级 | A：同一未改语义的公共测试 candidate fail/gold pass，且语义审查成立。B：候选动态失败、契约成立，但 gold 接口/环境不可比或 gold 自身有问题。C：仅静态支持。主动态结果单列 A；同时报告经审查的 B，不把 C 混入动态成功。

四个独立判断轴 | 需求/输入是否成立；候选实际行为；参考兼容与行为；失败是否来自 setup/环境/测试本身。gold 通过不能越过第一轴。

生成与筛选分别评价 | 所有提议义务数、语义接受数、合法且可执行数、见证成立数、最终保留数、有效缺陷数；最终错误主张率和弃权率。不能只评挑中的成功样本。

误报与误拒绝 | 误报是最终提出但语义或归因不成立的缺陷主张。现有全失败池无法给出补丁级真实 false-positive rate；需额外符合契约的样本。

成本 | 输入/输出 token、调用、分析 CPU/墙钟、测试进程与总时长、恢复失败成本；报告每个有效缺陷及每个有发现 issue 的成本。

用两名未参与生成的评审，在隐藏方法组名的条件下独立审查全部最终主张及弃权/拒绝候选的固定随机样本。先仅给公开需求、测试与候选执行，判断语义和合法性；再揭示 gold 结果，避免用 reference pass 倒推需求。分歧保留原始标签并由第三人裁决。若只能由 LLM 评价，必须继续称为模型评价，并将独立人类结论作为未完成条件。

补充至少 12 个来自成功 cohort 的最终 patch，或独立审查明确满足所测契约的样本，专门检查错误拒绝。按 12 项、3 个模型组、每组 1 次运行，另需 36 次流程、最多 144 次调用；加上上述两阶段，模型调用总上限为 784，实际共享前缀会减少用量。benchmark pass 仍不是整体正确证明；报告“在这些经审查契约上的误拒绝”，不报告无条件全局 FPR。若新数据暂时不可用，本轮只报告候选主张 precision 与已知失败池的发现能力，不能把这项缺口藏在局限脚注。


8.5 预先约定的继续、转向与停止标准

以下门槛是研发决策规则，不是显著性结论，也不是根据现有结果算出的最优点。24 项 pilot 的统计精度有限；报告逐任务胜负、仓库分组的不确定区间与重复一致性，不以多个相关目标制造小 p 值。

• 继续扩展技术路线：M 相比表现最好的同预算基线，在固定两次运行预算下净增至少 3 个有有效动态缺陷的 issue，且新增独有缺陷跨至少 2 个仓库；两次重复中均有收益迹象。最终主张的独立语义/归因正确率不低于 80%，且不劣于最佳基线。最终主张少于 20 个时，precision 证据视为不足，不能单靠比例过门槛。

• 保留方法、缩小主张：若只提高合法执行率或减少错误 oracle，而新增缺陷没有改善，论文只能主张验证可靠性或成本收益；需要相应独立指标与更大样本。

• 转向 oracle 研究：若找到了更多候选差异，但错误预期仍很多，应先加强需求关系的构造/审查；不能增加组合数掩盖语义问题。

• 否定当前核心机制：若 B1 在同预算达到相同结果，或去掉计算但保留上下文后效果不变，说明诊断计算未提供可识别增益。停止把它作为技术核心，保留经验观察或换研究问题。

• 不外推修复率：只有上述信号成立后才做固定 solver 的反馈修复对照；同时评价原 issue 成功、隐藏回归与成本。在此之前不写“提升 resolution rate”。


9. 可写入论文的主张与当前不能写的主张
────────────────────────────────────

目前能写的是一组可追溯的开发观察：自测可能验证了受限情境，却未支持需求的全部相关区分；身份、路径与观察时点能解释部分这种缺口；运行状态、语义关系与输入合法性必须分开；历史修改既有有用线索，也有合理测试修正。它们足以形成一个明确的机制假设。

目前不能写：这是 agent 特有失败模式；大多数错误来自组合不足；现方法稳定优于一般 LLM；静态分析已经带来因果增益；16 个输出代表 16 个独立缺陷；没有旧目标的任务是负例；恢复提交状态等于完整 trajectory replay；补测已经提高最终修复率。

论文最可能成立为一篇技术论文，前提是先证明上述计算对象与生成/判断之间的有效作用。若机制证据不足，而独立标注揭示了有代表性的验证不足与 oracle 失效，则可以考虑范围严格的经验研究。当前样本是开发集且按失败结果筛选，还不能直接转换成普遍性经验结论。

我的最终建议是冻结这次抽象，先做第八节的机制 pilot。它应允许结果否定“需要复杂分析”的假设，也应允许原测试已足够、公开契约不明确、对照合法但两边都通过。把这些结果记下来，才有可能判断下一步应该扩大方法、缩小范围，还是停止这条路线。
