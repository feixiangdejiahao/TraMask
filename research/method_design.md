# 当前方法：程序分析辅助的组合测试推理

2026-09-30 根据已落盘实验补充核验。本文区分已经运行的算法、正在验证的研究改进和实验结果。旧方案移到[历史版本](archive/method_design_action_observation_20260929.md)，其中的 0/7 等结果不能作为当前配置成绩。

实验定位已根据用户澄清固定为[提交前validation插件](pre_submission_plugin_protocol.md)：用原trajectory恢复候选patch与完整可见历史，增强测试，再让agent基于反馈修改patch，最终用hidden tests评价。原trajectory是允许使用的输入。“冷启动”仅指插件不复用本项目此前额外生成的模型回答，不表示禁止读取原历史；下文既有检出成绩尚未包含patch续修与hidden-test闭环。

根据最新讨论，**程序分析的主要职责是替模型梳理复杂程序信息，降低模型进行组合推理的难度**：把分散在测试、辅助函数和实现中的输入绑定、操作、状态变化及断言依赖连接起来，并保留可核对的源码证据。模型利用这些信息和 issue 契约推理缺少什么交互、组合是否合法、观察和期望怎样变化。限制输出为某种格式只是代码回填接口，不能代替这项分析任务，也不是核心学术贡献。

目前可以自动提取验证测试、生成组合、执行，并有限地调用模型修订预期；**还没有得到冷启动、统一预算下可靠覆盖全部 17 个 trial 的方法**。17 个 trial 对应 14 个任务，全部参与过开发。累计获得各例的正确测试，不等于一次自动运行全部成功，也不证明泛化。

## 核心问题与研究方向

两个操作都执行过，甚至已经出现在同一个测试中，仍可能没有检验它们的相互影响。一种原因是组合没有改变最后断言能够看到的状态；另一种原因是状态改变了，旧期望却不再适用。

因此，围绕一条具体对象上的具体观察，分别解决两问：怎样组合输入和操作，改变产生观察值的执行过程；新场景下应该观察到什么结果。程序分析提供绑定、调用、读写和路径证据，并构造可运行的候选；语义上是否值得组合、哪些断言应一起变化，需要模型利用契约进行推理。当前实现主要支持程序枚举候选后判断期望，还没有完整实现用准确依赖路径帮助模型提出组合的机制。

研究中程序分析的基本工作单位是**一次组合编辑与其关联观察之间的依赖子图**：目标是先从编辑涉及的输入、调用和绑定出发，找可能受影响的断言，再补齐相关调用、参数传递和状态写入。它替模型回答“需要一起看哪些代码，以及它们为什么相关”。模型再结合 issue 回答“这条路径中的交互是否值得测试，组合后应得到什么结果”。当前原型只完成其中有限的原源码关系整理，没有得到完整子图。依赖子图本身是已有技术，不能仅换个名字就声称创新；组合生成收益仍需实验验证。

本轮获得局部检出收益的机制是：**寻找能够改变原断言所读状态的写入来源的组合。** 对象绑定、定义与使用、异常路径给出静态排序；执行检查写入来源是否真的改变。这些都是可计算对象，无需模型填写自然语言关系标签。但写入来源本身是已有程序分析概念，目前仅获得局部收益，不能将其包装成覆盖所有组合缺口的统一创新。

当前最值得继续检验的学术联系，是**用原断言的状态产生路径约束组合搜索**：从“断言读什么”回溯到“哪些操作产生它”，再优先尝试能够改变这条路径、仍让断言执行的组合。它已经导出一个有限的异常路径排序规则，但尚未导出统一的组合扩展算法。程序切片、对象绑定、最后写入和调用图本身都是经典技术；上下文整理、端口和schema也不是学术贡献。目前只能提出一个候选研究方向，不能声称已经获得独特的新统一方法。[STARS对照](stars_abstraction_review.md)说明差异：其类型链直接决定可合成的调用扩展；本方法多数依赖分析仍在给既有候选排序或整理证据。已有16/17检出不能代替这一增量贡献的消融证据。

N01 的测试最后检查 `response.is_closed`。构造时写 False，关闭时写 True。加入错误输入并捕获异常后：

```text
普通 JSON：读完 → 关闭并写 True → 解析失败 → 捕获 → 检查关闭状态
流式 JSON：部分解析就失败 → 捕获 → 检查关闭状态
```

两者都有消费、异常和检查，但第二种跳过了关闭。区别在于断言读到的最后写入从关闭操作变成了构造操作。分析不需要知道 `response` 或 `is_closed` 的业务含义。静态路径只说明可能跳过写入，真实输入需执行验证；期望仍应为 True 则须由关闭契约支持。

## 已实现的全流程

### 1. 恢复测试与观察上下文

从仓库和 trajectory 恢复测试、断言、源码位置、输入、调用与局部绑定。保留完整执行前缀及所需 fixture/import，不把 assert 脱离产生其变量的上下文。已有验证在最终候选补丁上重放，区分有效种子与失效历史片段。

前端能识别直接断言和有限的断言 API。自定义 helper、动态 fixture 和跨语言 guest 代码并非都支持；无法提取属于前端覆盖损失，不能算作无需组合。

### 2. 程序构造候选，并分配预算

构造器依据 AST、调用槽位、接收者、局部绑定和输入结构，产生参数替换、操作组合、共享对象、字段存在性等有限编辑。修改保留源码对应。按构造族、源测试和结构轮换，避免单个测试的大量常量变体耗尽预算。结构归并用于调度，不证明行为等价。

可选 `--writer-priority` 为 Python 候选增加一个布尔优先条件：原断言保留；新异常捕获包围与断言同一对象上的操作；操作到字段写入的源码路径存在可能提前退出；捕获后仍执行原断言。修改后的接收者必须重新确认绑定到原对象，不能仅靠变量名相同。

满足条件的候选优先进入原调度器，其余保留。不支持的语言和绑定方式回退原顺序。排序不读取目标 ID、人工命中标签或语义缓存。[实现](../experimental/exception_write_priority.py)和[语义预算调度](../relation_search/semantic_selection.py)均可复查。

本轮另实现了[未配对观察影响排序](../relation_search/impact_selection.py)。对一个候选编辑，程序分别回溯断言实际值与预期表达式的依赖。如果编辑命中的原图节点能影响实际值，却没有进入预期值的依赖集，就把该观察记为需要审查的义务。它只表示旧预期可能需要重新判断，不表示一定改变，也不表示该候选有缺陷。排序贪心覆盖尚未审查的观察及编辑端口；每四个位置保留一次原结构轮换。

这项排序尚未有效：在相同 4,502 个程序候选上，五个需要修订预期的历史目标，前16覆盖从原结构排序的3/5降为2/5。已固定全部规则后才进行目标匹配，不能为提高这五个排名而增加案例规则。修改后调用上下文与排序收益分开评价。

另两项静态探索没有接入主线。受限常量传播尝试判断参数编辑是否跨过条件分支，但两版在同一4,502候选池中都没有获得已知分区，不能用于排序。[同上下文候选分组](context_candidate_groups_v1.md)允许一次呈现最多4个局部替代项，第一轮16组覆盖的五个语义目标仍只有3/5；模型是否选择并正确解释目标尚未验证。16组可能含64个候选，不能与16个单候选视为同等成本。

后续[修改后图原型](modified_observation_impact_v1.md)在实际编辑后重新绑定调用和对象，修复新增调用以及位置变化造成的遗漏；同池同预算对照仍未改善五个语义目标的排名。[精确材料去重](exact_oracle_material_v1.md)也没有释放预算：完整程序文本有重复，但保留编辑、导入、断言和源前提后，4502候选及首轮271次实际请求都没有可合并的完整材料。二者作为已验证的分析修复或负结果保存，不称为检出收益。

2026-09-30已实现有限参数化oracle模板，独立于主搜索。骨架与每个既有联合替换向量能够逐字节还原原候选，不新增笛卡尔积，也不把成员视为行为等价。4,502候选全部通过还原检查，得到2,924个family。配对研究在调用前按稳定哈希选定17组、每组最多4个成员，共50成员/臂；两臂都是一次联合请求、相同成员及完整断言，仅共享骨架与完整展开的程序表示不同。34次实际请求全部完成，后置完整语义复核得到template **20/50**、expanded **24/50**，正确且接口接收分别12/50、21/50。输入token减少4.35%，总token增加1.13%；这不支持更准确或总成本更低的主张。没有新增subject执行或目标检出。这是代码因子化的负结果，不是新的程序分析核心贡献。[原型与审查](finite_oracle_template_critical_review_20260930.md)记录边界，完整结果保存在`results/relation_search_20260930_finite_templates/evaluation/paired_semantic_final_v2/scored/summary.json`。

构造器在这些案例上开发过；没有按案例 ID 分支，不足以证明没有过拟合。

最新的[补丁到观察路径原型](patch_observation_priority_design.md)把预算单位细化到**一个输入编辑、一个具体调用位置、一条实际观察**。它先重放编辑，再重新解析测试，检查编辑影响的调用是否连接到提交补丁的修改代码，以及同一次调用是否处在断言实际值的依赖中。这样不会把第一次调用的输入变化与第二次调用的观察拼成一条路径。`strict` 要求有限的返回参数依赖链；`may` 允许可靠 callee 到修改函数体的保守可达链。两种模式都只增加一个优先桶，桶内保留原轮换顺序，未支持的候选继续留在队列。

这里的可计算增量是**区分共享同一源测试、但修改不同输入的候选**。旧检索已经连接断言切片与补丁相关函数，不能把这条连接本身称为新增能力。有限返回依赖投影可区分修改使用参数与修改未使用参数；保守模式只取得更弱的候选编辑与调用绑定。切片、调用绑定和返回摘要仍是经典分析；该原型尚不从路径直接合成新的组合，也不证明期望或路径可执行。因此它目前是可检验的排序假设，不能称为已经建立的学术创新。固定 17 例、4,502 候选的三臂对照见[预先冻结的评价协议](patch_observation_priority_protocol.md)，排序曝光与真实检出分开记账。

两种模式已接入主命令的 `--semantic-policy patch-strict` 和 `--semantic-policy patch-may`，沿用已有语义接口和待办队列；提交补丁 SHA 在运行及恢复时固定。主流程先沿完整未服务排序扫描现有 `prepare_requests` 接口能形成请求的候选，再截取候选预算、按原请求粒度分组。无孔或过大候选仍留在 catalogue，避免反复占据预算却没有请求。这个实际请求资格不同于排名实验的 raw@16 和旧 singleton eligible@16，三者不能混用。它们是可选研究模式，没有替换已确认 16/17 的冻结主配置。

### 3. 运行后检查组合改变了什么

主搜索已连接 Python 探针和跨轮前沿。此前关系 profile 与轮换的完整对照没有提高检出，不能将该反馈称为已验证有效。

新写入跟踪原型记录同一实例上的成功字段写入，以及原断言前直接读取的内建标量。生成断言、构造和 writer 映射回原源码，避免新函数名或行号制造虚假新状态。不额外执行用户 getter，只记录插桩范围内的直接写入。

它已经完成真实 trace 和离线前沿复放，**尚未集成为用新 writer 反馈驱动下一轮的在线搜索**。同一 writer 也可能产生不同错误，不能仅按 writer 去重，更不能声称完备。

### 4. 为局部模型推理提供上下文

本轮原型先固定一个候选的输入、动作、绑定与观察。请求一起展示相关断言和完整修改后测试，避免只改尾断言，却保留前面失效的检查。这是目前的实验单位，并不代表任意长度的完整测试都是最佳粒度；按真实依赖整理更小但足够的推理上下文，仍是后续分析工作。

预期槽位接口用于运输模型结论：保留、修改期望表达式、依据不足。程序重建原断言，保留实际观察、动作和诊断代码。Python 仅允许受支持的比较形式调整；Go原生比较和TypeScript matcher固定。后续源码为Go标准一元断言补上 `NoError/Error`、`Nil/NotNil`、`Empty/NotEmpty`、`True/False` 的极性调整，实际参数与诊断保持原样，同时修正把诊断参数错当expected的前端问题。这是表达能力修复，不是学术抽象，也不证明修改后的预期正确；冻结主臂没有回填。

旧接口还曾挡住 `actual is None` 改为 `actual == 300`，也曾将模型正确推断的字符填成 `is 'a'`；main 已修复为联合选择比较符和期望，拒绝新增非单例字面值的身份比较。结构不支持、无可编辑槽位或上下文超预算都显式记录，不能默认为原断言正确。

prompt 提供 issue 契约、固定编辑、完整相关测试和机械解析的定义/辅助函数上下文。候选实现可能有缺陷，只作绑定和调用证据，不能照录其输出作为正确答案。当前上下文解析仍是有限声明解析，尚非完整程序切片：改变 callee 后不能直接沿用原调用图，动态状态与未解析调用也仍有缺口。自然语言理由不参与排序或正确性判定。

本轮主臂使用[修改后调用证据](../relation_search/oracle_evidence.py)：先去掉运行探针，再重新解析修改后的测试、导入和调用，连接实参到形参、局部对象字段写入及可能受影响的观察。请求附上真实函数和来源测试的完整源码，未知连接显式保留。完整结构在本地保存，模型收到去重后的代码与依赖路径。独立核验了固定136个候选的源码跨度和映射；这证明信息出处正确，不证明模型修订一定正确。每个请求处理一个完整候选的相关预期，目前每case每轮最多16个候选。

后续源码进一步将图中的观察位置与模型编辑接口 `A0/A1` 按原始、修改后的byte span对应。同一断言文本在不同调用阶段出现时，不再要求模型仅靠文本猜测对应关系。这项修改已通过重复断言与UTF-8偏移测试，未用于已完成的冻结主臂。

不能依据有缺陷的候选实现中“没有找到依赖”认定旧预期仍然成立：缺陷本身可能就是遗漏了应有依赖。已有测试可提供预期来源，但相同函数名或某个实参不足以搬运其结果，仍要对齐对象历史和观察阶段。相关通用反例见[源预期复用边界](source_oracle_reuse_feasibility_20260929.md)。

此前的两个独立输入整理原型如下；它们与本轮重新分析修改后代码的实现及实测结果分开记录：

- [调用依赖证据](call_dependency_evidence_20260929.md)：从编辑的源码位置、值使用和绑定寻找原调用，再连接相关断言，展示唯一可解析目标、实参→形参、接收者定义与源码。编辑改变 callee 或接收者定义时，不复用原绑定为新事实。
- [断言到写入路径](assertion_path_context_prototype_20260929.md)：从断言读字段回溯对象构造、别名、property 和 writer，再展示已有测试操作经 helper 到 writer 的路径及完整函数。八个 Python 池的 4,625 个观察中，243 个可渲染，48 个有既有操作到 writer 的路径。未支持的观察保留在分母中。

这些证据旨在减少模型自己查找跨函数信息的工作。固定17例34对的新消融中，带上下文与删除上下文分别得到14和13个完整正确判断，尚无稳定收益证据。每例首条请求的三臂对照为完整上下文9/17、无上下文7/17、同一组源码声明9/17；声明臂减少24.1%总token，但出现错误削弱断言，不能称更可靠。原程序的 may 依赖也不等于修改后程序的真实执行依赖。[独立反例审查](call_dependency_evidence_review_20260929.md)已确认，字段赋值后经方法读取、callable alias等结构仍可能关联不到断言。完整修改后测试和契约仍须保留，不能用不完整切片替代它们。

2026-09-30的[局部helper证据原型](local_helper_evidence_20260930.md)进一步从完整修改后测试解析Python局部def、Go函数字面量和TypeScript局部arrow/function，为每次调用分别绑定实参与形参。只读取上述预选50成员的源码，恢复8处旧证据中缺失的调用绑定，得到75条实例化断言，但新增可编辑期望参数为0。P5/P6的`require`来自仓库自定义实现，不能套用testify的断言角色。原型没有接入主搜索，没有新模型或subject执行，也没有生成正确期望。这是分析覆盖修复，尚无语义或检出收益。

后续[失败源码证据原型](source_failure_evidence_20260930.md)从真实`*testing.T`的失败调用出发，用两个有限固定点恢复同包静态调用可达性和失败分支的形参依赖；诊断消息参数不当作失败判据。导入路径与唯一声明确认跨包调用，再把条件与实参分别绑定到具体helper实例。固定50成员中，4成员的8个自定义调用位置取得源码、判据和失败路径证据，对应72次局部helper实例；去重后仅为`NoError`、`Equal`两个API，不能称为72个新缺陷或全库断言召回率。所有期望端口仍未知，接口没有自动升级。Go局部声明遮蔽和短变量作用域错误已修复，未知及完整源码随证据运输。该原型未接入主搜索、未新增模型或subject调用，尚不改变16/17检出或误报结论。

另一个独立[helper字面值接口](helper_expected_slots_20260930.md)从修改后源码确认比较形参和每次调用的期望实参，只替换已有字面值。全量4502候选发现30个新端口，均来自N05一个helper；同时它的普通端口限制会使555个原可表达Go候选失去资格，因此没有替换主接口。固定新端口队列的8次新请求，4个交付了独立确认正确的完整修订，4个length空输出未知。离线native中8个旧期望组合均失败，4个修订均通过，源控制全部通过；本组4个失效旧期望报警得到消除。它是表达能力修复，未新增N05目标检出，不能算整体误报率或漏报改善。[独立配对评价](helper_expected_slots_evaluation_20260930.md)保存完整结果和边界。

这是独立实验接口。冻结的全语料运行仍使用此前完整断言修订接口，成绩分开报告。合法表达式不等于正确期望，正确期望也不证明观察足够强；方法尚不能自动证明任意原断言是否覆盖全部新影响。

### 5. 执行与独立确认

原测试控制和生成测试分别执行。编译/环境错误、未到达断言、真实断言失败及可确认的目标缺陷分别记录。冻结主臂的Go独立测试进程仍共享包编译，其他候选的编译错误可能阻止有效测试运行。后续可选 `--isolate-go-compilation` 为每个Go候选单独编译；真实Go toy确认可避免无效候选阻塞有效候选，但会增加replay及编译成本，当前主臂没有回填这项修复。详见[编译隔离实验](go_compilation_isolation_v1.md)。

评价核对完整测试的期望和前提，不能只看最后一句。当前人工独立复核属于实验评价，不是算法实现的自动语义保证。尚无配对修复实验，不能声称提高 issue resolution rate。

## 怎样检验 general

规则使用语言层面的程序结构，参数在评价前冻结。改名控制检查是否依赖名字；不同对象、写入后才异常、finally 保证写入等结构反例检查分析边界。它们都不能代替未参与设计的新任务。

比较搜索须固定构造器、语义预算和执行预算，再替换排序或反馈。模型对照也固定父候选；不支持的请求计入覆盖损失，拒收、空输出和未知分别记录。真正的泛化评价需事先封存的新任务，这 17 个已见 trial 只能支持开发集结论。

## 指标与入口

核心指标是固定配置和预算下，有正确完整组合测试、通过的原控制且实际检出目标问题的 trial 数。同时报告候选是否进入预算、可执行率、模型可解析率、完整 oracle 正确性、模型调用数和 token。未复核报警存在时不报告整体误报率；未完成与完成但未检出分开。

主入口为 [run_relation_campaign.py](../scripts/run_relation_campaign.py)。以下是八例的零模型静态排序配置，使用新输出目录：

```bash
.venv/bin/python scripts/run_relation_campaign.py \
  --source results/relational_gap_20260928/batch7 \
  --output results/my_writer_search \
  --cases N01 N02 N03 N04 P1 P2 P3 P4 \
  --rounds 1 --limit 8 --pool 512 --include-baseline \
  --group-size 8 --workers 1 --timeout 180 \
  --oracle-mode none --writer-priority
```

研究原理详见[断言写入来源搜索](assertion_writer_search_20260929.md)。旧关系形状假说、STARS 等论文启发和验证标准保留在[关系搜索设计](relation_search_method.md)，未验证推演不算已实现能力。

新排序的零模型复现入口如下。它只生成固定候选池的完整排名和共同接口资格，不执行仓库，不衡量期望正确性或缺陷检出：

```bash
.venv/bin/python scripts/census_patch_observation_priority.py \
  --paired results/relation_search_20260930_finite_templates/paired_inputs_v3 \
  --output results/my_patch_observation_census
```
