# 新增 oracle 回答的实际贡献与16候选预算

本文先只读审计既有请求、响应、发射测试和执行记录：对象是 `semantic_cache_v3.json` 及 `uniform_warm_v2` 的17个独立确认代表见证。后续统一新请求实验的证据另列，缓存不等于正确答案库。

## 哪些正确测试实际使用了新增回答

17个代表中，P1、P6、P7、N04、N05这5个包含插件后续生成的 `semantic_expected` 修订，另外12个保留源断言。P3虽然命中过多条缓存，最终采用的正确代表是程序生成的constructor，不能把它归功于oracle修订。这里统计的是本次代表见证的构成，不是证明所有可能测试中只有这5例需要LLM，也不否认原trajectory本身由模型产生。

| 案例 | 构造出的组合 | 正确预期修订 | 有帮助的具体探索 |
| --- | --- | --- | --- |
| P1 | End键编码与press/repeat/release阶段组合 | key从a改为end，阶段检查不变 | 取回另一个原测试中CSI 8~对应End的直接证据，附在单候选请求中 |
| P6 | 同一闭包放入数组两次，整体迁移到另一个实例后依次调用 | 最后一次结果103改为5004 | 给模型完整操作序列，去掉issue附带的runner工作指令，聚焦局部预期判断 |
| P7 | 递归schema与字符串长度transform组合 | 原输入字符串树改为所有层均转换后的数字树 | 解析新增导入别名，补充实际调用的pipe函数体 |
| N04 | 数据不变量约束name，同时bulk更新同一字段 | 更新成功改为拒绝；name从X改为回滚后的one | 明确列出输入before/after、导入绑定，开启thinking，联合修订两个观察 |
| N05 | width从5改为100，仍使用默认样式reset处理 | 旧截短ba改为完整bar，并要求重开样式及末尾reset | 将已构造候选单独送给模型，推理新宽度与样式状态的共同效果 |

这5次成功请求均使用deepseek-v4-flash、temperature=0、max_tokens=16384、thinking enabled。候选的输入、调用与组合在请求前已经由程序构造；模型主要补上组合后不再适用的预期，并没有在这些请求中完成整套组合发现或patch修复。

## 探索变化的证据强弱

**P7是最直接的程序分析辅助证据。** attempt2已提供完整修改后测试、input_changes和import_bindings。attempt3保持system、offered及上述模型设置相同，prompt增加 `imported_api_contexts`：机械解析 `rs_import_a69107a4` 指向 `pipe`，提供其真实函数体。transform的箭头函数原本就在测试里，新增的不是transform实现或正确预期。

attempt2用完16,384个输出token，全部用于reasoning，没有可用JSON。attempt3使用3,243个输出token（其中3,099为reasoning），给出每层value都为1的正确树。它说明“别名解析→找到真正被调函数→提供调用语义”值得研究；每种条件只运行一次，不能据此证明稳定因果效果。

**P6主要解决任务混淆。** attempt1→attempt2移除了issue后附的benchmark runner操作指令，明确这是没有工具的局部断言判断；prompt从7,600缩至4,613字符。前次只有空白，后次给出5004。没有新增调用/状态依赖事实，不能把这次成功归因于新程序分析。完整序列仍很关键：原实例中先调用两次，迁移后新实例的全局g=5000；数组两个元素应共享捕获状态，后两次结果依次5003、5004。

**N04同时改变了多项条件。** v1与v2都提供5个候选；v1在thinking disabled时认为不需修改预期。v2增加显式输入差异和导入绑定，并启用thinking，正确得到拒绝更新及回滚预期。因此有明确成功结果，但无法分别估计diff、binding和thinking的贡献。

**P1获得直接来源测试证据。** 程序的新组合附上donor测试中CSI 8~映射为End的断言，模型回答也引用这段证据。没有同候选删除donor的对照，不能声称已测量检索收益。

**N05缩小了模型问题，但也绕开了选择困难。** focused请求只包含从已有库存中选出的1个候选；模型正确完成局部推理，证明该候选的预期可得到，并未证明统一调度器能自动选中它。

## Oracle修订如何改变实际结果

| 案例 | 既有实际执行与完整语义 |
| --- | --- |
| P7 | 原组合沿用输入树预期，PASS；新数字树预期FAIL，实际根仍为字符串a，补上了漏检 |
| N04 | 原组合要求成功并存X，PASS；正确拒绝/回滚预期FAIL，实际仍exit0，补上了漏检 |
| P6 | 旧103与实际5003不符，但旧预期本身错误；改为正确5004后仍得到5003，成为可信的共享状态缺陷证据 |
| P1 | 原与修订测试都因没有事件而在解包处失败，尚未执行key断言；a→end的作用是让整个测试语义正确，不能说它首次触发了失败 |
| N05 | 已有独立审查确认旧width100仍期待短ba不适用；正确全字符串比较揭露样式遗漏。warm中原parent未得到可匹配的原生测试记录，不能把它说成该轮完成的前后配对 |

因此oracle既可能修补“错误实现也通过”的弱/过时断言，也可能修补“即使实现正确也会失败”的错误预期。这两种贡献必须分开。N05修订保留了旧诊断消息中的want变量；判定执行语义依据实际比较表达式，不能仅凭报错文本中的短want。

后续固定14请求的上下文/思考对照提供额外机制线索，但它们不是上述5条缓存来源，不应倒算为生成这5条回答的探索。原缓存还保留错误修订，38条cache entry也不代表38条正确测试。

## 本轮新请求中补充确认的贡献

以下来自后续 `uniform_fresh_impact_v3`，与前述历史缓存的五条来源分开统计，不更新那张表的分母。

**P6在本轮完整新请求中再次得到正确5004。** 程序自动构造数组中的两处引用共享同一闭包、整体转移到新实例后依次调用的组合；模型依据本轮请求，把最后的103改为5004。独立审查核对了本轮provider响应、最终发射函数、实际命名Go失败以及通过的源控制，确认这不是历史回答缓存重放。当前实现第二次仍返回5003，因而新预期成为可信的目标缺陷见证。原103也会失败，但不是正确预期；5004的贡献是修复完整测试的语义，不能解释为首次让测试变红。见 `results/relation_search_20260929_v3/evaluation/uniform_fresh_impact_v3/checkpoint_10.json`。

**P7也在本轮新请求中完成完整数字树修订。** 目标候选的首次单候选请求正确修改四个value，保留递归引用身份和非法子节点检查；当前命名测试实际根值仍是字符串，相关源控制通过。它是本轮新回答与新执行，不是历史attempt3回答的缓存复用，但没有在同一目标上另做删依赖证据的配对，因此不能单独归因于新依赖图。

**第二轮又自动补上P1和N04。** P1的新回答将三个事件阶段的键值预期改为End，完整phase检查保留，三个命名实例均因缺少事件失败且同组源控制通过；它修复完整测试语义，没有首次触发失败。N04的新回答联合修订拒绝更新与回滚为one，实际bulk UPDATE仍错误成功，形成正确目标见证。二者均核验了本轮请求、响应、实际发射源码和命名执行链，没有复用历史回答。

本轮最终封存 `checkpoint_14` 为16/17个正确完整目标见证，其中12个保留源断言，4个来自P1/P6/P7/N04的新模型预期；全部17例两轮完成，N05仍无确认合格目标见证。这里的fresh campaign分数不能解释为16个由LLM修订发现的目标，也不能用历史warm17减去它来估计缓存收益。

**N06 的一个新回答将错误预期修成了有效缺陷见证。** 原测试只比较空白差异，因此期待零个编辑操作。程序把同一位置的子标签从 `<a/>` 改成 `<x/>`，仍使用忽略空白和按位置匹配。issue明确按位置对应，所以正确结果应为一次替换；旧的“零次”已经不适用。模型改成一次，候选实现实际返回删除加添加两次，命名原生测试失败，相关源控制通过。旧的零次断言也会在正确实现上失败，不能算可靠报警；新的一次断言才让这个组合成为有效证据。完整审查见 `results/relation_search_20260929_v3/evaluation/extra_issue_detections/N06_position_identity_review.json`。

这条回答证明本轮局部预期推理有实际作用，但带依赖证据与删除该证据的配对请求都得到了正确的“一次”，因此不能归因于新增依赖图。N06此前已有另一条正确目标见证，这个额外issue缺陷不增加17任务检出数。

**N07 的正确回答还揭示了接口限制。** 对四个变体，模型正确联合修订了成功merge后读取不存在的普通文件或 `MERGE_HEAD` 时的error与空内容预期；冻结版本却不允许 `NoError` 改成 `Error`。后来统一重验全部64条已完成Go回答，只新增接纳这四条，独立审查确认完整预期合理。这里没有新推理，也尚未补执行这些新接纳测试，只能记作消除了错误拒收，不能当作新缺陷检出。见[接口重验报告](go_predicate_readmission_v1.md)。

截至已封存的本轮17例34对上下文消融（`evaluation/context_ablation/checkpoint_05_{wire,semantic_reviews}.json`），完整正确预期或明确正确保留为带证据14对、不带证据13对；实际发出的正确修订为9对、8对，输出token耗尽分别9对、6对。P5/P6中的同一空map克隆测试不能视为两个独立语义问题。另一个带证据回答在prompt已经给出完整函数声明的情况下，仍把缺失必需实参误解为运行时undefined；该回答被结构接口拒绝，没有形成报警。这个小样本尚未确立依赖上下文的稳定收益，源码事实是否完整、模型是否正确使用事实、修订是否获接纳以及测试是否有效，需要分开观察。

随后固定每例首条请求的17个三臂对照，完整上下文、无上下文、同一组源码声明的正确判断分别为9、7、9。源码声明臂减少24.1%总token，却产生了N02错误削弱关闭断言的回答，不能称更可靠。这些回答只做预期质量评价，没有回填上述16/17目标结果。完整证据为 `evaluation/source_declarations_semantic_final.json`。

## “每轮最多16个候选”限制什么

它是插件测试搜索中**每个case、每一轮**分给LLM预期判断的不同程序候选数上限。这里的轮次不是agent修复patch的轮次；当时patch固定，搜索两轮测试。16是实验设置的预算值，不是理论要求，也未证明为最佳取值。

```text
程序从原测试构造一批测试变体
       ↓
本轮选择至多128个程序候选
       ├─ 全部保留，按现有断言执行
       └─ 按变换族、来源测试、语法形状轮换，至多16个交给LLM
                  ↓
          通常每请求4个候选
                  ↓
          合法预期修订成为额外测试执行
```

16不限制原trajectory测试总数，不等于16条assertion，也不等于16次API调用。一个候选可以含很多断言；没有可支持断言的候选也可能无法发出请求。格式失败后的单候选拆批可能再次询问同一候选，增加请求数但不增加不同候选覆盖。未进入16的候选仍执行，只是没有这轮LLM修订预期的机会。

上图的“每请求4个”是当时版本的设置。本轮冻结主臂 `7a8ff95` 改为每请求1个完整候选，因此通常至多16次初始请求；16仍然限制不同候选数。新版本也保留未获模型判断的待办候选供后续轮次选择。它们没有自动获得正确预期，不能把排队当作已完成判断。

上图对应旧版的语法多样性轮换。当前冻结主臂改为优先覆盖“修改可能影响实际观察、但预期没有沿同一依赖改变”的观察，再覆盖不同修改位置；每第四项保留语法多样性探索。这个静态依赖只表示可能影响，不能保证所选16项就是最需要修订的16项。此前全池对照中，五个需要新预期的历史目标在前16项的覆盖反而从旧shape的3/5降至impact的2/5，尚无排序收益证据。

### N04的实际预算断点

原测试要求COUNT(*)=1；把name从one更新成X仍满足这个约束，所以源断言期待成功。目标变体把约束改为 `COUNT(*)=1 AND MIN(name)='one'`，随后仍更新同一行的name为X。合理行为应拒绝并回滚，源断言已不适用。

冻结fresh v2第一轮实际有48个程序候选，全部入选；目标在程序队列第33，但语义队列第48。模型只处理前16个，因此没看过这个目标。目标实际沿用旧成功预期执行并PASS，形成漏检。

这16个候选一共含177个断言。4个初始请求之后又有8个单候选拆批请求，共12次调用，仍只覆盖这16个不同候选。它具体说明了候选数、断言数、调用数三者的区别。

冻结版本下一轮仅处理新程序候选，没有当前main后来加入的持久语义待办队列，因此该目标第一轮未获模型判断，第二轮也没有重新排队。不能把后来的修复写成旧实验已经具备的能力。

N05第一轮为174个候选池中选128个程序候选，再选16个交模型；已知目标在程序队列第120、语义队列第127。历史文档的第170来自另外的累计库存，不能混称本轮排名。

## 对下一步方法的含义

已有证据最支持两项工作：一是像P7一样，程序自动补齐模型缺少的真实调用与数据流信息；二是让语义预算优先覆盖“输入或操作已改变，而相关观察的预期仍沿用旧值”的候选。N04说明当前漏检可能发生在问题还没交给模型之前，不能一概归因于模型推理能力不足。

联合推理同一组合中受影响的观察也很关键：N04的exit status和数据库状态、P6的先后两次调用、P7的不同递归层不能孤立判断。以上是从现有成功与失败记录提出的方法方向，尚非已验证的统一新算法。
