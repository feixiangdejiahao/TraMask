# 从 17 条 trajectory 的验证逻辑重新设计方法

2026-09-28。本轮重新阅读 P1–P7、N01–N10 的原始 trajectory、issue 和候选代码，重点检查测试为什么产生、遇到失败后如何变化，以及最后一次验证究竟证明了什么。没有运行新的仓库实验，没有调用模型 provider；旧方法的最好完整结果仍为 **4/17**。17 条 trial 对应 14 个不同 task，不是 17 个独立任务。

**最重要的修正：这批案例不能再统一叙述为“agent 没想到组合”。** 有些交互已经被明确讨论，有些已经执行但接受了错误解释，有些曾通过却在后续修改后失效。下面是原始证据支持的更细分类；类别可以重叠，不拿它们估计真实分布。

## 2. 从证据得到的研究判断

对于**尚未得到判别验证的子问题**，可以研究现有输入和观察为什么让不同的行为解释表现相同。例如，P2 的两个解释在空 text 下相同；N09 的记录级选择和字段级合并在全给/全不给下相同；P6 的两种复制图在只读初始值时相同。这不是全部 17 例的新统一标签：N05 已看到相关行为差异却接受错误解释，N06 已有历史验证却未在最终版本重跑，分别需要 oracle 裁决和验证恢复。

这个共同点仍然只是问题抽象。要变成算法，需要能生成打破这种相同现象的具体程序，而非把“有区分力”留给模型自由判断。新提案因此聚焦于[判别上下文合成](../distinguishing_context_method.md)：输入构造、状态操作、观察共同作为程序搜索对象；以成对执行和反向观察需求约束扩展。

**没有将这条方向宣布为已经成立的新颖贡献。** 普通变异测试、候选补丁等价类、差分执行、类型引导合成本身均是已有工作。值得验证的较窄假设是：对给定的局部行为分歧，基于值、异常出口和别名拓扑的观察需求，能否以更少搜索合成短的可执行判别上下文；trajectory 能否以较低成本提供有价值的分歧。这两个问题分别评价。

## 3. 讨论过而没有直接采用的方案

| 方案 | 有用之处 | 未直接当核心的原因 |
|---|---|---|
| 保留 `(q,ρ)`，换一套关系名字 | 描述目标和评价层次清晰 | 仍未给出关系恢复和程序构造运算 |
| version space + 最大信息增益 | 选择测试目标明确 | Fix2Fit 等已有；所有候选可能共同错误，造出有价值候选仍难 |
| 移动 effect 的作用范围 | guard/loop/exit 上可列有限代码移动 | N09 的逐字段合并不只是移动语句；N07/N08 也不统一 |
| anti-unification 学测试 grammar | 比自由拼接更能保留绑定 | 单靠语法泛化不能产生新 heap topology、SQL 语义和 oracle；旧方法已有片段端口 |
| 从 assertion 反推充分条件并打破 | 可解释 vacuity 和异常出口 | 任意程序 WP 不可直接求；若为每类准备摘要会回到特制规则 |

## 4. 对数据和历史结果的修正范围

- 保留原 case ID、历史失败见证和 4/17 结果，不重写实验。
- N06 应单列为**历史验证恢复/回归检出**；若重放已有脚本发现问题，不能算“新 combination 合成成功”。本轮只核对原成功输出、后续编辑及最终代码，没有重新运行该脚本。
- P2、N02、N04、N05 至少含可见的契约解释问题；其中 N05 已观察到相关行为，不能把补输入当作全部解决办法。
- N04/P7 属于“已有结构，但缺有判别力的运行时验证”；不应只统计操作共现。
- 因此，先前“新增十条都是从未进行合理组合”的强说法需要撤回。这十条是**最终有效验证不足的失败案例**，其中混有输入、观察、oracle 和验证版本失效问题。
- 本轮没有新检出率、误报率或 issue resolution rate 结果。上述成因分类也是已见样本上的回顾性分析。
