# 让组合改变断言所读取的状态来源

本轮的新原型围绕一个可直接计算的对象：**某条原断言读取的字段，在同一对象上由哪处代码最后写入。** 它已经用于静态候选排序，也已经在真实测试中观测；尚未成为覆盖全部 17 个任务的完整搜索算法。

## 一个可以区分有效组合和无效组合的例子

N01 的原测试构造一个 response，消费 JSON，最后检查 `response.is_closed`。初始化把它设为 False，关闭操作把它设为 True。异常输入有两种效果：

```text
普通 JSON：读完数据 → close 写 True → JSON 解析失败 → 测试捕获异常 → 断言读 True
流式 NDJSON：部分数据解析失败 → 测试捕获异常 → 断言读 False；最后写入仍是初始化
```

两种测试都执行了消费操作、捕获了异常，也都到达关闭状态断言。只看到“消费 + 异常 + 断言”无法区分它们。区别在于异常发生时，产生断言状态的关闭写入是否已经执行。原先的 profile 只记录 consumed=True，加上不同的 phase 标签，会把没有改变关闭状态的组合也算成新状态。

这给出一个更具体的搜索方向：**尝试改变原断言读到的写入来源，同时让这个对象仍然到达原断言。** 这里的“来源”是源码位置，不是模型填写的业务解释。

## 已实现的两个程序分析步骤

第一步从原断言反向找字段、局部对象构造和写入位置。解析接收者类型、import/reexport、局部别名及简单 property→storage，找到测试操作到字段 writer 的源码调用路径。对现成组合候选，优先考虑以下条件同时成立的项：原 q 未被改写；新增的异常捕获上下文包围了与 q 相同对象上的操作；该操作到后续 writer 的源码路径上存在可能的异常出口；q 仍在捕获上下文之后。修改后的接收者重新绑定，不能仅因变量名字相同就沿用旧对象的证据。

这只是一个布尔优先条件。未满足的候选保留原顺序，不被删去；同优先级内也不使用目标标签或模型分数。[实现](../experimental/exception_write_priority.py) 和 [16 项局部测试](../tests/test_exception_write_priority.py)覆盖了对象重绑定、同名不同对象、finally、框架符号遮蔽及 q 后重复调用等情况。

第二步在成功字段赋值之后、原 assert 之前记录事件，以实际实例身份连接两者；再把生成测试中的 q 和构造位置映射回原源码。跨运行比较使用原 q、原构造和原 writer 的位置，不使用地址、生成函数名或人工 phase 标签。原 assert AST 保留；不额外求值 property、调用 getter 或执行用户的 repr/比较代码。只有可直接读取的内建标量具有完整值记录，其余是 unknown。

记录的是**插桩范围内最后观测到的直接写入**。它不证明开放 Python 程序中不存在未插桩写入，也不证明组合后应该继续使用原期望。可靠缺陷仍需通过源控制、确认实际断言失败，并独立检查契约。

## 当前证据

固定的八个 Python 源码候选池共有 768 个候选。静态条件支持 N01 的 15/93、N02 的 136/195，其余六例没有支持项。原数组中 N01 目标由第 6 位前移到第 2 位，N02 保持第 1；接入同一公平调度器时，两者分别为 35→2、3→3。这些是不同顺序下的排名，不能与此前 profile 消融中 N01 的累计第 26 次提案混用。[独立静态复核](../results/relation_search_20260929/evaluation/exception_write_priority_review_v2.json)保留了全部候选及对应证据。

随后进行了真实排序消融：所有八个 Python 案例，两臂使用相同源池、相同公平调度器，每例一轮八个提案，保留原断言；没有调用模型或重放语义缓存。已确认检出由原调度的 **3/8（N02、P3、P4）提高到 4/8（新增 N01）**。主驱动的可选 `--writer-priority` 又执行了一遍相同设置，八例的 64 个选中候选完整编辑与独立消融一致，也确认 4/8。独立目标评价登记在[本轮评价](relation_search_evaluation_20260929.md)，不能用原数组排名替代执行结果。[冻结协议](../results/relation_search_20260929/exception_write_ablation_v1/protocol.json)及[执行结果](../results/relation_search_20260929/exception_write_ablation_v1/results.json)可复查。

对 N01/N02 已有首轮全部 32 组测试进行了写入插桩。所有 phase 的逐测试结果与未插桩运行一致。自动审计记录了 331 条有效标量读及 6 条复杂值 unknown；43 个可比较的组内源 q 中有 10 个出现新的 writer。独立复核确认这 10 组 q、73 次新 writer 读取均有通过的同源控制。N01 的关闭断言实际读到了初始化的 False，源控制则读到 close 的 True；N02 也出现相同区别。新 writer 的统计不是正确缺陷数。[原型说明](observed_write_runtime_prototype_20260929.md)及[全部 trace 审计](../results/relation_search_20260929/observed_write_full_analysis_v2/summary.json)记录支持边界。

离线前沿按源 q、源构造、字段、实际 writer 和内建标量值保留代表，14 个新代表中有 7 个完整正确 oracle、6 个沿用失效期望、1 个前提未知；两个已知关闭问题都仍有代表。因此它能压缩部分见证，但并未排除误报。精确标量值域也不是有限域，不能声称获得了有限语义商或完备剪枝。这一步尚未成为在线搜索反馈。[独立复核](../results/relation_search_20260929/evaluation/observed_write_frontier_review_v1.json)保留完整预期判断。

进一步固定全部32组 trace 的处理顺序，**仅从前沿 key 删除 writer，14个代表、原 q 状态数及全部保留决定都没有变化**。独立重算复核了297条决定及原始 trace。因此目前不能声称 writer 身份在动态搜索中优于同一断言的值反馈。writer 路径仍提供静态排序和解释证据，但它与标量变化的增量作用尚未区分。见[独立消融复核](../results/relation_search_20260929/evaluation/observed_writer_key_ablation_review_v1.json)及[学术审查](assertion_writer_academic_review_20260929.md)。

## 这还没有解决什么

N01 静态排序第一名仍是完整读完才解析失败的普通 JSON 组合，真正目标在第二名。这正是需要实际 writer 反馈的原因；源码 may 路径不能替代当前输入的执行顺序。N02 的优先桶也很宽，136 个候选不能被当作 136 个缺陷。

字段分析只绑定了八个 Python 仓库中 4,625 个观察的 243 个，即约 5.25%。P3 等场景可以在同一个 writer 上因输入值不同而暴露问题；仅用写入位置无法处理。跨进程 SQL、Go 序号与 JavaScript 对象构造也没有被这个 Python 原型自动覆盖。因此目前的证据支持一个局部搜索机制，不能将其描述成统一 17 例、无漏报的方法。

Reaching definitions、对象绑定和程序切片都是已有技术。可能的研究贡献需要落在一个可检验的联系上：**用原断言的状态产生路径约束组合，再用真实写入来源检验组合是否改变了该断言能够观察到的状态。** 是否比相同构造器下的一般覆盖或值反馈更有效，仍需成对搜索实验及独立任务检验；名称或一个新 tuple 本身不是创新。
