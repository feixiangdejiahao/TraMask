# 用关系形状指导测试搜索

2026-09-28 设计，2026-09-29 更新实现状态。源代码组合构造器、局部断言修订及 Python 关系探针已有实现和真实任务证据；完整在线反馈搜索尚未接入主驱动。累计正确测试见证 **11/17**，其中本轮生成来源为 **9/17**，不能当作统一预算的端到端算法成绩。旧方法最好完整配置仍为 **4/17**。见[保存检查点](relation_search_checkpoint_20260929.md)与[独立评价](relation_search_evaluation_20260928.md)。本文取代“判别上下文合成”作为待验证方向：不再把获得有用的竞争实现作为搜索前提。

## 先用一个例子解释

N08 的数据库一次提交 n 条记录，占用序号 `[s, s+n)`。旧验证等待 `s`、`s+1`（当 n=2 时均在区间内），也检查过远未来的等待；没有检查非空批次完成后恰好等于该批次 `s+n` 的位置。另一个 future notify 调用虽然出现，却没有检查返回 channel。原轨迹证据见 [N08 重审](trajectory_logic_20260928/go_ts.md#n08-pebble明确知道-exclusive-range却选了内部点和远端点)。

注意：初始化时的 `WaitForDurability(0)`、`DurabilityNotify(0)` 已经经过 `target=high=0`。因此“全局没测过相等”是错误说法。缺口绑定到 **high 由一次非空 batch 的完成更新产生** 这一来源和阶段；初始零状态不能充当其见证。这也是单纯收集比较结果仍不够的具体证据。

把具体数字暂时换成关系：

| 非空批次完成后，等待目标与同一 DB 上界 h 的关系 | 已有验证 | 新搜索目标 |
|---|---|---|
| target < h | 已有区间内测试 | 不优先重复 |
| target = h | 没有这个来源和阶段下的相等端点见证 | 修改等待实参，使它等于实际批次的 s+n |
| target > h | 已有远端等待测试；notify 的观察不充分 | 保留二者的观察区别 |

这张表不是模型猜出来的业务分类。实现中有 `target <= high` 的比较和 `high = start + count` 的更新；AST、定义使用关系及运行值可以提供参与者和来源。类型给出整数的 `<、=、>` 三种基本关系。**判断这些关系哪一种没出现，不需要先知道实现应当用 `<` 还是 `<=`。**

当生成 `target=s+n` 后，即使仍走已有的成功分支，它也取得了关系搜索上的进展。之后才根据“上界是排他的”这一契约判断：当前不应就绪。可靠的 channel 观察必须另外构造或恢复；只调用 notify 不算检出。

这是算法的推演例子，不是新一轮自动成功记录。实际 Go 前端还要把内部的 `durableSeqNum + keyCount` 对应回测试可调用的序号和条数表达式，保留同一 DB、同一已完成批次的绑定。分析恢复不了时应记为输入构造失败，不能预填正确表达式后声称自动发现。

## 核心抽象究竟是什么

**关系形状：在一个具体对象和观察时刻附近，少数程序值之间的联合相对关系。** 它用于给搜索中的测试分组，并决定下一步修改。

- 对数值，看大小和相等，而不是只记录具体整数。
- 对对象，看哪些访问路径指向同一对象，而不是记录地址。
- 对记录/集合，看字段分别来自哪些集合、是否存在，而不是只看整个参数对象是否非空。
- 同时保留参与值的构造来源及具体观察位置；另一个对象上的相等、flush 后的读取不能充当本处的见证。

例如 `target=10, h=12` 与 `target=100, h=102` 都提供 `target<h` 的见证；`target=h` 则是另一种形状。这个归并只用于分配搜索预算，**不表示两份具体测试行为等价**：距离、溢出、字符串内容等仍可能改变结果。

联合关系不能拆成各元素的独立计数。假设一个 record 已有两字段，全给值与全省略都出现过：两个字段各自都经历了“给/不给”，但“只给第一个”仍没出现。真实 N09 的 agent deferred fixture 主要只有一个字段，不能声称仅删除原字段就能产生多字段混合。不过仓库普通路径的 [trait.test.ts](../data/relational_gap_v1/N09/repository/packages/core/tests/trait.test.ts:8) 已有多字段 Position，第 97 行起也有部分参数与默认值的验证。设计可以尝试复用这些构造、改接到 deferred 上下文；只有限定为原单字段种子时，才必须另外扩张结构。跨测试搬运、对象绑定和新观察仍需实现。

可以将核心写成两行：

```text
抽象：把测试映射为局部、带对象和阶段的关系形状。
搜索：优先尝试尚未见过的相邻形状，执行确认后保留新见证。
```

这与旧 `(q,ρ)` 的问题表示有连续性，并非换个名字就获得创新。具体变化是：关系实例从有限的源码实体和类型规则生成；下一步输入编辑有明确规则；由每轮真实执行更新已见集合。旧原型主要按若干关系域提出静态编辑，尚未实现这里的统一反馈循环。

## 已有条件、需要实现的分析和假设

| 类别 | 内容 |
|---|---|
| 已有输入 | candidate、patch、issue、原测试与 trajectory 中的验证代码、可恢复仓库和 harness |
| 已有条件不包含 | 正确参考程序、完整关系规范、完整效果摘要、所有新场景的正确断言 |
| 可明确实现的分析任务 | AST 槽位与定义使用；受支持语言的调用/字段来源；有限运行值和对象身份采样；测试 AST 编辑及重放 |
| 仍需检验的假设 | 有用缺陷中相当部分能由少量参与者的关系体现；已有验证附近有可构造的新形状；这种反馈比普通覆盖更节省搜索预算 |
| 未被这些假设解决的问题 | 任意 DSL 的合法输入生成、复杂异步调度、跨层对象身份、无公开观察/无可信契约 |

将难问题拆成三个局部问题：**选哪些程序实体一起看；怎样改变它们的关系；怎样判断新结果。** 前两项不依赖先知道正确行为，第三项不能用搜索覆盖代替。

## 如何自动选参与者，避免把难题藏在“找相关关系”里

采用有界的、可复现的规则；它是过近似候选生成，不是自动理解所有语义。

1. 从直接 assertion/已知断言 API 提取实际观察 AST 和对象根，保留期望与完整执行前缀。打印只能提供观察，不能自动成为断言。首先在最终 candidate 上重放，以恢复有效种子和已经失效的历史验证。
2. 给调用实参/返回、字段访问、构造器输入标记来源位置及有限访问路径。运行时地址只判定本次执行内的别名，跨运行用来源和路径对应。
3. 从观察根沿测试的定义使用与 receiver/实参绑定，收集一个有界局部范围。加入流入同一个源形参的其他 validation 构件。对该范围内源码已经出现的比较、纯表达式、record 构造/消费记录相应项。深度和数量上界在评价前固定。
4. 在共享资源/构造来源的候选项中枚举小块，默认最多 4 个角色，优先包含实际源码比较的两端，再加入来自其他构造/操作的角色。不能因 candidate 当前未将某字段读入断言就删除该字段；同一 schema 和 params 的静态构造关系仍是候选依据。
5. 按小块轮换预算；先试能用更少 AST 编辑实现的邻居。patch 距离可以作为排序对照，不能把 patch 外的状态完全排除。相同类型本身不充分证明相关，只有同类型却没有来源联系的配对进入低优先级扩展预算。

对状态字段，还记录消费时最后一次定义/更新的源码位置及有界调用来源。例如 N08 的初始化 `high=0` 与 batch 完成后更新 `high=start+count` 有不同的写入来源；只把整个 Wait API 当一个窗口会错误合并它们。记录的是定义位置和来源关系，不是无界累加第几次 commit 的编号。该定义使用/运行时来源分析仍是完整前端需要实现的部分。

缺省实现参数必须全局固定并公开。小块遗漏真实关系是可测的召回损失；扩大范围产生无关关系是可测的搜索成本。不能用 LLM 填写“有语义关系”来掩盖这个取舍。

## 有限表示与相邻形状

给定固定的角色块 B 和观察窗口 c，计算 `φ(B,c,T)`。窗口采用实际 AST 调用前后、正常/异常出口、原断言位置；不要求模型命名业务阶段。

角色与窗口标识在编辑前固定；修改保留原 AST 的来源对应，不能用变异后的行号创建一个新角色。新增 generic 字段只能占用预先有界的匿名字段槽，按结构关系规范化；任意 fresh key 拼写、对象新地址和测试新文件名不制造新颖性。新增公开调用同样受构造模板和上下文深度约束。否则每次重命名都“覆盖新格”，反馈就失去了意义。

| 类型域 | 机械表示 | 一步候选编辑 |
|---|---|---|
| 有序值 | 可比值及选定源码常量/表达式之间的联合 `<,=,>` 矩阵 | 将一个可编辑实参接到另一现成值或源码表达式；整数再试相邻值 |
| 引用 | 访问路径的别名划分和缺席标记 | 改用已有同类型对象，或经已知构造器创建独立对象 |
| record/集合 | 固定字面 key 的存在位；generic key 在各集合中的 membership pattern | 增/删一个输入项；必要时复制 generic schema 项并同步改相关构造 |
| 布尔/枚举 | 源码谓词真值、显式常量、参数缺席与规范化后的值 | 替换现成值、改变已有布尔条件的输入、省略可省略实参 |

源代码特别区分的 key/常量不能随意重命名。同一接口中多个独立布尔值保留联合向量，不能只保存每个布尔值是否都出现过。字段数量、来源深度和结构扩张深度都有限。

相邻形状是搜索偏好，不是目标必可实现的证明：

- 有序块可以试图合并相邻大小组以达到等值，再拆开以探索另一侧。
- 别名块可以试图合并/拆分一个绑定。
- 存在性块可以试图改变一项；若原结构太小，先经通用构造规则扩张。

**实际程序修改发生在测试输入上。** 内部量可直接追溯到实参时改那个槽；可由受支持的纯/仿射表达式恢复时生成表达式；否则尝试有限合法输入变异并重放。对解析产生的复杂内部结构，不提供一个没有实现的 `solve_input(target)` 黑盒。例如 N07 仍需从文本编辑得到期望的 diff hunk，不能直接注入内部 hunk 后计作完整 API 成功。

一个固定的数值角色块只有有限种弱序；4 个无约束角色有 75 种。不需要为所有整数元组分别开新搜索目标。但整仓库所有块的数量仍可能很大，有限不等于低成本。

## 搜索循环与真正的反馈

```text
Q = 在最终 candidate 上可执行的历史验证
Seen = Q 的实际关系形状；另记录实际代码覆盖

while 有预算:
    轮换选择一个观察局部范围及一个源测试
    枚举该测试的一步合法输入/绑定编辑
    优先执行预计能达到未见相邻形状、编辑较小的候选
    在 candidate 上运行候选，重算关系形状和观察值
    若实际增加关系形状或代码覆盖，加入后续搜索队列
    为已见形状保留有限的不同构造来源/具体值代表
    对值得裁决的候选，另行检查观察与期望的依据
```

预计形成某关系、实际到达某关系、发现缺陷是三件事。实际执行失败可能是无效 fixture；测试断言失败可能是错误期望。失败不能全部称为 bug。

“多个代表”很重要：若 x=4、5 被当前抽象合并，后续修改 `x+=3` 会分别得到 7、8，可能只有一个触发缺陷。关系形状不是对所有未来操作封闭的语义商。可以按构造来源和有限具体值多样性保留少量代表，并在已观测到不同后继时拆分搜索桶；仍不保证无遗漏。不得以“每格一个最小代表”声称完备剪枝。

候选没有影响当前断言，也可以增加关系反馈。P6 错误 clone 切断共享；N04 错误 bulk 绕过验证。这时“必须先影响已有断言才保留”的规则会直接删掉需要发现的例子。

## 观察不是附属标签，但也不要求观察先发生变化

已有观察提供资源根、访问路径和取样时刻，用来限制关系块与输入编辑。对于可确认只读的观察，可以在同一资源的正常/异常出口或已有调用前后再次求值。N01/N02 的 `response.is_closed` 可以揭示退出阶段的区别，不能仅观察尚未开始消费时的状态。

这种提升必须满足变量在该出口已定义、对象仍可读、表达式只读；不把任意 getter 当纯函数。不满足时只能在原位置观察，或使用隔离重放。

N04 可独立执行已有的 SQL invariant 查询，以其自身读取字段选择 UPDATE 输入，而不是依赖错误 bulk 路径实际调用 validate。这里仍需 SQL 前端理解读字段和查询执行；“在同一数据库”本身不足以选对字段。

对新场景，保留原断言需要它的契约仍适用。若原断言只读显式字段，就不能用其通过证明缺省字段正确。少量 LLM 可以提出缺失的合法构造片段或依据 issue 给局部期望；核心形状、已见集合、输入编辑记录和运行反馈不依赖模型生成自然语言 schema。模型辅助结果单列，不能把模型建议当证明。

以下是已知证据下的设计审查，不是自动检出结果。17 个 trial 只有 14 个不同 task，全部是已见开发材料。

| N06 | sibling add × descendant text | 历史已有成功脚本，优先在最终版本重放，不计新组合生成 |
| N07 | 同 base 上两 hunk 的四端点联合次序 | 外部文本到内部构型的实现能力 |

## 从 STARS 学到什么，哪些不是创新

[STARS，ISSTA 2026](https://www.software-lab.org/publications/issta2026_STARS.pdf) 的有用示范是：固定测试前缀提供变量和类型，观察方法链形成可以由程序枚举、组合和约束的对象，再由模型承担部分选择与补全。抽象本身要导出实际算法操作。本文借鉴这个设计原则，没有要求把本问题改写成蜕变关系。

但“超过执行覆盖”本身不是贡献。[StorFuzz，ICSE 2026](https://kevin.borgolte.me/files/pdf/icse2026-storfuzz.pdf) 已用存储值多样性保留走相同代码的输入，并允许状态在被后续读取前提供反馈。[InvsCov，USENIX Security 2021](https://www.usenix.org/system/files/sec21-fioraldi.pdf) 已用 likely invariants 的违反指导 fuzzing，包括变量可比性、状态分区及联合违反。按数据类型定义关系也有早期 [relation-based testing](https://doi.org/10.1016/j.jss.2007.05.036) 前例。

因此本设计目前只是**可实现、可否定的研究假说**：已有 validation 提供的观察和构造来源，能否自动把巨大的全局状态空间缩成少量有用的局部联合关系，并指导可执行的输入修改。可能的贡献在这种选取与构造的联系，不在关系名字、覆盖表或新缩写。若相同变异器下不优于已有关系/值反馈，应否定该假说。

## 验证标准与实现状态

真实任务实现位于 `relation_search/` 和 `experimental/relation_search_*.py`。当前结果主要证明若干源代码组合构造可行：一些见证来自收窄的源集合，N07 已确认的严格部分重叠候选仍未进入完整语料的前 128。Python 探针在 N03 观察到了输入对象从不同变为同一个、最终文件数发生变化；这只是实际 profile 提取与离线判新的证据。主驱动尚未接入探针、seed 优先登记与反馈后的候选扩展；以下消融仍是待完成的验证要求。

比较时固定输入构造器、oracle、执行次数和墙钟预算，仅替换搜索反馈：随机/轮换、edge coverage、值反馈、InvsCov 风格关系反馈、本文的来源与观察限定的联合形状。再消融来源约束、joint 关系、观察阶段、结构扩张。不能用更强的专用生成器赢过弱 baseline 后归功于反馈。

分别测量：到达预先封存目标关系的执行次数/时间；计划邻居的实际实现率；有效测试率；保留的无关状态比例；独立确认的缺陷检出与误报。不存在“所有有意义关系”的已知分母，不报告一个伪精确的全局组合覆盖率。检出率提高也不直接等于 issue resolution rate 提高。

独立机制原型位于 [experimental/relation_frontier_demo](../experimental/relation_frontier_demo/README.md)，只演示受限 Python literal 调用上的自动项提取、通用编辑、执行和反馈循环。它不包含 Go/TS、对象/阶段分析、结构构造或完整 oracle；不代表本文完整方法已实现，更不是新 pilot 实验。

原型的 9 项机制检查通过：等值例 74 次执行得到 13 种联合形状，其中有与种子行覆盖完全相同的新等值形状；两个 mapping 的例子 73 次执行得到 16 种联合存在模式；负向控制确认同形状仍可能输出不同。改名、整数和源码锚整体平移的控制保持搜索轨迹一致。这里没有同预算 baseline 优势检验，不能据此宣称搜索更快、误报更少或真实检出提高。
